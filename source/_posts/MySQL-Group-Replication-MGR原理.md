MySQL Group Replication 是 MySQL 官方从 5.7.17 版本开始引入的一套**高可用与多主复制**方案，核心目标是在多个 MySQL 实例之间实现**数据一致性、自动故障转移和组成员管理**。

---

## 一、整体架构

```
┌──────────┐   ┌──────────┐   ┌──────────┐
│  Node 1  │   │  Node 2  │   │  Node 3  │
│  (MySQL)  │   │  (MySQL)  │   │  (MySQL)  │
│          │   │          │   │          │
│ ┌──────┐ │   │ ┌──────┐ │   │ ┌──────┐ │
│ │ GCS  │ │   │ │ GCS  │ │   │ │ GCS  │ │
│ │层     │ │   │ │层     │ │   │ │层     │ │
│ └──┬───┘ │   │ └──┬───┘ │   │ └──┬───┘ │
└────┼─────┘   └────┼─────┘   └────┼─────┘
     │              │              │
     └──────── XCom / Paxos ───────┘
           （组通信引擎）
```

MGR 分为三层：

| 层级 | 组件 | 职责 |
|---|---|---|
| **上层** | MySQL Server 层（插件） | 捕获变更、冲突检测、应用事务 |
| **中间层** | Group Communication System (GCS) | 组成员管理、视图维护、消息广播 |
| **底层** | **XCom** (基于 Paxos 的共识引擎) | 保证消息的全局有序和一致性 |

## 二、核心原理

### 1. 基于 Paxos 的共识协议

MGR 底层使用 **XCom** 组件，它是 Paxos 协议的一种实现：

- 所有事务在提交前必须在**多数节点（N/2 + 1）**上达成共识
- 保证了**分布式环境下的全局事务顺序一致性**
- 少数节点故障不影响集群可用性

```
事务提交流程：

  Client → 本地执行事务 → 生成 Write Set
       → 广播给 Group 所有成员
       → XCom 排序（全局唯一顺序）
       → 所有节点按相同顺序认证 & 应用
       → 多数节点 ACK → 事务提交
```

### 2. Write Set（写集）与冲突检测

MGR 不直接传输 SQL 或 binlog 事件，而是使用 **Write Set**：

```
Write Set = {
    表名,
    主键/唯一键的 hash 值,
    事务标识,
    ...
}
```

**冲突检测流程：**

```
Node A 提交事务 T1（写入 row_id = 100）
        │
        ▼
  广播 Write Set 给 Group
        │
        ▼
  Node B 收到后，检查本地是否有并发事务
  也在修改 row_id = 100
        │
        ├── 无冲突 → 直接认证通过
        │
        └── 有冲突 → 根据认证顺序决定：
              先认证的提交，后认证的回滚
```

### 3. 组成员管理（Group Membership）

```
正常视图（3节点）:
  View = {Node1, Node2, Node3}    主要成员数 = 3

Node3 宕机:
  检测机制 → 心跳超时 / XCom 连接失败
        │
        ▼
  视图变更 → View = {Node1, Node2}    主要成员数 = 2
        │
        ▼
  仍然满足多数（2/3）→ 集群继续服务
  
若再掉一个:
  View = {Node1}    主要成员数 = 1
        │
        ▼
  不满足多数 → 集群变为不可写（UNPROTECTED）
```

关键概念：

| 术语 | 含义 |
|---|---|
| **ONLINE** | 节点正常，可读写 |
| **RECOVERING** | 节点正在从组内其他节点同步数据 |
| **OFFLINE** | 节点已离开组 |
| **UNREACHABLE** | 其他成员无法到达该节点 |
| **多数派（quorum）** | 集群正常工作的必要条件 |

### 4. 两种模式

| | 单主模式 (Single-Primary) | 多主模式 (Multi-Primary) |
|---|---|---|
| **可写节点** | 仅 1 个 Primary | 所有节点都可写 |
| **冲突风险** | 无（单点写入） | 有（需冲突检测） |
| **适用场景** | 绝大多数生产环境 | 特殊读写分离需求 |
| **Primary 选举** | 自动，按 UUID 最小者 | 无需选举 |
| **Secondary 行为** | 只读，自动 `super_read_only` | 可读可写 |

> Primary 宕机后，单主模式会自动选举新 Primary（最小 UUID 的 ONLINE 节点）。

### 5. 数据同步（分布式恢复）

新节点加入或故障节点恢复时：

```
Step 1: 组视图变更，新节点进入 RECOVERING 状态

Step 2: 尝试通过 donor 的 binlog 追赶数据
        │
        ├── 有可用的 binlog → 增量同步
        │
        └── binlog 不可用（差距太大）→ 全量同步
              │
              ▼
        使用 Clone Plugin / mysqldump / xtrabackup 全量复制

Step 3: 追赶到与 Group 相同位置 → 切换为 ONLINE
```

## 三、数据流全景

```
Client 写操作
    │
    ▼
┌─────────────────────────────────┐
│  MySQL Server (Primary Node)     │
│  ① SQL 解析、执行引擎            │
│  ② InnoDB 引擎生成 Undo/Redo     │
│  ③ 提取变更数据 → Write Set      │
│  ④ 冲突检测（Certification）      │
└──────────┬──────────────────────┘
           │
           ▼
┌─────────────────────────────────┐
│  Group Communication (GCS/XCom)  │
│  ⑤ Write Set 广播给所有成员      │
│  ⑥ XCom Paxos 排序，确认多数 ACK │
└──────────┬──────────────────────┘
           │
           ▼
┌─────────────────────────────────┐
│  所有成员 (Primary + Secondary)   │
│  ⑦ 按 XCom 排序的顺序应用事务    │
│  ⑧ 写入本地 InnoDB + binlog      │
└─────────────────────────────────┘
```

## 四、关键特性总结

| 特性 | 说明 |
|---|---|
| **强一致性** | Paxos 多数派共识，不会脑裂 |
| **自动故障转移** | Primary 故障后自动选举新 Primary |
| **自动成员管理** | 节点加入/离开自动感知和视图更新 |
| **冲突处理** | Write Set + Certification 机制 |
| **兼容 InnoDB** | 必须使用 InnoDB 引擎 |
| **基于 Paxos** | 容忍 `(N-1)/2` 个节点故障（3节点容忍1个） |

---

## 五、与其他方案对比

| | MGR | 主从复制 | InnoDB Cluster |
|---|---|---|---|
| **一致性** | 强（Paxos） | 弱（异步/半同步） | 强（底层就是 MGR） |
| **自动选主** | 是 | 否 | 是 |
| **脑裂防护** | 是 | 否 | 是 |
| **多主写入** | 支持 | 不支持 | 支持 |
| **复杂度** | 中等 | 低 | 低（封装了 MGR） |

> **InnoDB Cluster** = MGR + MySQL Shell + MySQL Router，是对 MGR 的上层封装，提供更易用的集群管理体验。
