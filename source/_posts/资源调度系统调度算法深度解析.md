## 一、多级队列调度（Multi-Level Queue Scheduling）

### 1.1 核心思想

多级队列调度的本质是**将不同类型的任务分类放入不同的等待队列，每个队列拥有独立的调度策略和优先级**，调度器按照既定规则在队列间和队列内进行任务选择。

```
┌─────────────────────────────────────────────────┐
│                  调度器 (Scheduler)                │
│                                                   │
│  优先级 0 ──▶ [ 在线推理队列 ] ──▶ 低延迟抢占权    │
│  优先级 1 ──▶ [ 离线训练队列 ] ──▶ 长时间批处理     │
│  优先级 2 ──▶ [ 调试/开发队列 ] ──▶ 弹性资源       │
│                                                   │
│         调度策略：队列间轮转 + 队列内 FIFO/优先级    │
└─────────────────────────────────────────────────┘
```

### 1.2 训练任务 vs 推理任务的本质差异

| 维度 | 训练任务 (Training) | 推理任务 (Inference/Serving) |
|------|---------------------|------------------------------|
| **资源占用时长** | 数小时到数天，持续占用 | 毫秒到秒级，按请求粒度 |
| **GPU 显存模式** | 几乎占满显存（模型 + 梯度 + 优化器状态） | 仅加载模型权重，显存占用相对可控 |
| **延迟敏感度** | 不敏感，关注吞吐量 | 极度敏感，P99 延迟需严格控制 |
| **资源弹性** | 弹性较低，中断代价高（checkpoint 恢复） | 弹性高，可快速水平扩缩容 |
| **通信模式** | 大量 AllReduce / P2P 通信 | 通常单卡或模型并行，通信量小 |

### 1.3 多级队列的具体实现策略

#### 队列划分

```
┌──────────────────────────────────────────────────────────┐
│                    队列层级设计                             │
├──────────────┬──────────┬────────────┬───────────────────┤
│   队列名称    │  优先级   │  调度策略   │     资源保障       │
├──────────────┼──────────┼────────────┼───────────────────┤
│ production    │  P0(最高) │  抢占式     │ 保障 SLA，弹性扩缩 │
│ (在线推理)    │          │            │                   │
├──────────────┼──────────┼────────────┼───────────────────┤
│ training-high │  P1      │  FIFO      │ 资源池保障配额     │
│ (高优先训练)   │          │            │                   │
├──────────────┼──────────┼────────────┼───────────────────┤
│ training-low  │  P2      │  调度窗口制  │ 仅在空闲资源时调度  │
│ (低优先训练)   │          │            │                   │
├──────────────┼──────────┼────────────┼───────────────────┤
│ dev/test      │  P3(最低) │  可被回收   │ 最小资源保障       │
│ (开发调试)    │          │            │                   │
└──────────────┴──────────┴────────────┴───────────────────┘
```

#### 队列间调度策略

**加权公平调度（Weighted Fair Scheduling）**：

```
总GPU资源池 = 100卡

production     → 权重 40% → 最低保障 30 卡，上限 60 卡
training-high  → 权重 35% → 最低保障 25 卡，上限 50 卡
training-low   → 权重 20% → 最低保障 10 卡，上限 40 卡
dev/test       → 权重 5%  → 最低保障 5 卡，  上限 15 卡

当 production 突发流量时：
  → 可从 training-high / training-low "借用"空闲资源
  → 借用的资源在 production 负载下降后归还
```

#### 队列内调度策略

**训练队列**通常采用：

- **FIFO**：先来先服务，简单公平
- **Shortest Job First (SJF)**：短任务优先，减少平均等待时间（需要预估任务时长）
- **Backfilling**：当大任务等待资源时，允许小任务"填缝"执行，提高资源利用率

```
时间线示例（Backfilling）：
───────────────────────────────────────────────▶ 时间
│ 大任务A (需要8卡，等待中)                       │
│ ├─ 小任务B(2卡) ← 填入空闲卡                   │
│ ├─ 小任务C(2卡) ← 填入空闲卡                   │
│ └─ 当剩余4卡空出 → 大任务A开始运行              │
```

**推理队列**通常采用：

- **最少连接（Least Connections）**：将请求分发到当前负载最低的推理实例
- **延迟感知（Latency-Aware）**：根据实时 P99 延迟动态调整路由权重

### 1.4 抢占机制

当高优先级队列资源不足时，可触发抢占：

```
抢占流程：
1. 调度器检测到 P0 队列有未调度的推理请求
2. 选择 P2 队列中占用资源最多的训练任务
3. 向训练任务发送 SIGTERM 信号
4. 训练任务执行 Checkpoint 保存（通常预留 grace period = 60-300s）
5. Checkpoint 完成后释放 GPU 资源
6. 调度器将释放的资源分配给 P0 推理任务
7. P2 训练任务回入队列头部，等待资源重新可用时恢复
```

## 二、亲和性调度（Affinity Scheduling）

### 2.1 为什么需要亲和性

在大规模分布式训练中，**通信开销**是决定训练效率的关键因素之一。不同的物理拓扑位置之间，网络带宽和延迟差异巨大：

```
网络拓扑层级与带宽：
┌──────────────────────────────────────────────┐
│                                              │
│  同一 GPU 之间（NVLink）     ：600 GB/s      │
│  同一节点内 GPU 间（PCIe/NVLink）：64~600 GB/s│
│  同一机架内节点间（RDMA/IB）   ：200~400 Gbps │
│  跨机架节点间（RoCE/以太网）   ：25~100 Gbps  │
│  跨数据中心                   ：1~10 Gbps    │
│                                              │
└──────────────────────────────────────────────┘
```

### 2.2 亲和性调度的层级

亲和性调度可以在多个层级上实施：

#### 节点级亲和（Node Affinity）

将同一分布式训练任务的所有 Worker 调度到**尽可能少的节点**上：

```
场景：8卡分布式训练（数据并行，AllReduce 通信）

不好的调度（跨节点）：
  Node-1: [Worker-0, Worker-1, Worker-2, Worker-3]    ← 4卡
  Node-2: [Worker-4, Worker-5]                         ← 2卡
  Node-3: [Worker-6, Worker-7]                         ← 2卡
  → AllReduce 需要跨 3 个节点通信，受限于网络带宽

好的调度（同节点）：
  Node-1: [Worker-0, Worker-1, Worker-2, Worker-3,
           Worker-4, Worker-5, Worker-6, Worker-7]     ← 8卡
  → AllReduce 全部通过 NVLink/PCIe 完成，带宽高几个数量级
```

#### 机架级亲和（Rack Affinity）

当单节点无法容纳所有 Worker 时，尽量调度到**同一机架**的节点上：

```
场景：32卡分布式训练（跨4个节点）

优先调度到同一机架：
  Rack-1:
    Node-1: [GPU 0-7]  ← 通过机架内 InfiniBand 交换机互联
    Node-2: [GPU 8-15]
    Node-3: [GPU 16-23]
    Node-4: [GPU 24-31]
  
  机架内 IB 延迟 ~1μs，跨机架 IB 延迟 ~3-5μs
```

#### 资源类型亲和（Resource Affinity）

将特定类型的 GPU 调度给特定任务：

```
规则示例：
- A100/H100 优先分配给大模型训练（需要高显存 + NVLink）
- T4/L4 优先分配给推理任务（成本低，适合推理场景）
- 带 NVSwitch 的节点优先分配给张量并行训练任务
```

### 2.3 亲和性的表达方式

现代调度系统（如 Kubernetes）通过 **Label + Selector** 表达亲和性：

```yaml
# 节点亲和性规则
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:  # 硬约束（必须满足）
      nodeSelectorTerms:
      - matchExpressions:
        - key: gpu.nvidia.com/class
          operator: In
          values: ["A100", "H100"]
        - key: topology.kubernetes.io/rack
          operator: In
          values: ["rack-01", "rack-02"]
    preferredDuringSchedulingIgnoredDuringExecution:  # 软约束（尽力满足）
    - weight: 80
      preference:
        matchExpressions:
        - key: topology.kubernetes.io/rack
          operator: In
          values: ["rack-01"]

# Pod 亲和性（让同一训练任务的 Worker Pod 尽量在同一节点）
  podAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - key: job-name
          operator: In
          values: ["llm-training-job-001"]
      topologyKey: kubernetes.io/hostname
```

### 2.4 调度器内部的亲和性评分

调度器在候选节点上计算**亲和性得分**：

```
亲和性评分流程：
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Step 1: 预过滤
  → 排除不满足硬约束的节点（资源不足、Label 不匹配）

Step 2: 对每个候选节点计算得分
  Score(Node) = w₁ × 拓扑亲和分 
              + w₂ × 资源匹配分 
              + w₃ × 通信亲和分

  其中：
    拓扑亲和分 = 已调度的同任务 Worker 在该节点/机架的数量
    资源匹配分 = 可用 GPU 数量与需求的匹配度
    通信亲和分 = 与已调度节点的网络距离评分

Step 3: 选择得分最高的节点
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 三、反亲和性调度（Anti-Affinity Scheduling）

### 3.1 故障域（Failure Domain）概念

反亲和性调度的核心目的是**避免故障域集中**。故障域是一个在物理故障发生时会同时失效的范围：

```
故障域层级：
┌─────────────────────────────────────┐
│           数据中心 (DC)              │
│  ┌───────────────────────────────┐  │
│  │         可用区 (AZ)           │  │
│  │  ┌─────────────────────────┐  │  │
│  │  │      机架 (Rack)        │  │  │
│  │  │  ┌───┐ ┌───┐ ┌───┐    │  │  │
│  │  │  │ N1│ │ N2│ │ N3│    │  │  │
│  │  │  └─┬─┘ └─┬─┘ └─┬─┘    │  │  │
│  │  │    └─────┴─────┘       │  │  │
│  │  │  共享：电源、交换机、散热 │  │  │
│  │  └─────────────────────────┘  │  │
│  └───────────────────────────────┘  │
└─────────────────────────────────────┘
```

### 3.2 典型的反亲和性策略

#### 同一训练任务的多副本跨机架分布

```
场景：训练任务有 3 个 PS（Parameter Server）副本需要高可用

反亲和性调度结果：
  Rack-1: [PS-Replica-0]     ← 各副本分布在不同机架
  Rack-2: [PS-Replica-1]     ← 任意一个机架掉电
  Rack-3: [PS-Replica-2]     ← 其他副本仍可服务
```

#### 推理服务的跨节点分布

```
场景：LLM 推理服务部署 4 个副本

反亲和性调度结果：
  Node-1 (Rack-1): [Inference-Replica-0]
  Node-2 (Rack-2): [Inference-Replica-1]
  Node-3 (Rack-1): [Inference-Replica-2]   ← 同机架不同节点
  Node-4 (Rack-3): [Inference-Replica-3]
  
  即使 Rack-1 整个掉电，仍有 2 个副本可服务
```

#### 避免同一用户的多个任务共用同一 GPU 节点

```
场景：同一团队提交了 5 个独立的训练任务

反亲和性规则：
  "同一 label: team=A 的训练任务，尽量不调度到同一节点"
  
原因：避免团队级别操作失误（如批量取消）导致节点瞬间空闲
```

### 3.3 反亲和性的表达

```yaml
# Pod 反亲和性：同一服务的副本不调度到同一节点
affinity:
  podAntiAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
    - labelSelector:
        matchExpressions:
        - key: app
          operator: In
          values: ["inference-service"]
      topologyKey: kubernetes.io/hostname  # 节点级反亲和
    
    preferredDuringSchedulingIgnoredDuringExecution:
    - weight: 100
      podAffinityTerm:
        labelSelector:
          matchExpressions:
          - key: app
            operator: In
            values: ["inference-service"]
        topologyKey: topology.kubernetes.io/rack  # 机架级反亲和（软约束）
```

### 3.4 亲和性与反亲和性的冲突处理

实际调度中，亲和性和反亲和性可能冲突。调度器通过**加权评分**进行权衡：

```
冲突场景：
  训练任务需要 8 卡，同一节点只有 4 卡空闲
  → 亲和性：希望 8 卡在同一节点（高带宽通信）
  → 反亲和性：希望不与另一个关键推理任务共存

调度器评分：
  方案A：单节点 8 卡（不可能，资源不足）→ 排除
  方案B：同一机架 2 节点各 4 卡
    亲和性得分：80/100（机架级亲和，非节点级）
    反亲和性得分：90/100（与推理任务不在同一节点）
    综合得分：85
  方案C：不同机架 2 节点各 4 卡
    亲和性得分：40/100（跨机架通信开销大）
    反亲和性得分：95/100（故障域完全隔离）
    综合得分：62.5
  
  → 选择方案B
```

## 四、Bin Packing vs Spread

### 4.1 两种策略的本质

这是资源调度中最经典的权衡之一：**资源利用率 vs 故障隔离**。

```
Bin Packing（装箱策略）：
  → 尽量把任务塞满每个节点，用尽可能少的节点
  → 目标：最大化资源利用率，降低空闲碎片
  
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │ ██ ██ ██ ██ │  │ ██ ██ ██    │  │              │
  │ ██ ██ ██ ██ │  │ ██ ██       │  │   (空闲)     │
  │ ██ ██ ██ ██ │  │             │  │              │
  │  节点1: 95%  │  │ 节点2: 60%  │  │  节点3: 0%   │
  └──────────────┘  └──────────────┘  └──────────────┘
    利用率高，节点数量少

Spread（分散策略）：
  → 尽量把任务均匀分布到所有节点
  → 目标：故障影响面最小化，负载均衡
  
  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐
  │ ██ ██ ██    │  │ ██ ██ ██    │  │ ██ ██ ██    │
  │ ██          │  │ ██          │  │ ██          │
  │             │  │             │  │             │
  │  节点1: 40%  │  │  节点2: 40%  │  │  节点3: 40%  │
  └──────────────┘  └──────────────┘  └──────────────┘
    利用率均匀，故障影响面小
```

### 4.2 Bin Packing 深度分析

#### 算法实现

最常见的变体是 **First Fit Decreasing (FFD)**：

```python
def bin_packing_ffd(tasks, nodes):
    # 按资源需求从大到小排序
    sorted_tasks = sorted(tasks, key=lambda t: t.gpu_requirement, reverse=True)
    
    for task in sorted_tasks:
        placed = False
        # 按当前利用率从高到低排序节点（优先填满已热节点）
        sorted_nodes = sorted(nodes, key=lambda n: n.utilization, reverse=True)
        
        for node in sorted_nodes:
            if node.can_fit(task):
                node.schedule(task)
                placed = True
                break
        
        if not placed:
            # 开启新节点
            new_node = allocate_new_node()
            new_node.schedule(task)
```

#### GPU 调度中的 Bin Packing 场景

```
场景：集群有 8 节点 × 8 GPU = 64 GPU

提交的任务：
  Job-A: 4 GPU, 8小时
  Job-B: 2 GPU, 2小时
  Job-C: 6 GPU, 12小时
  Job-D: 2 GPU, 1小时
  Job-E: 1 GPU, 3小时

Bin Packing 调度结果：
  Node-1: [Job-A(4GPU), Job-B(2GPU), Job-E(1GPU)]  → 7/8 GPU 利用
  Node-2: [Job-C(6GPU), Job-D(2GPU)]                → 8/8 GPU 利用
  Node-3~8: 空闲                                     → 0% 利用
  
  → 仅使用 2 个节点，其余 6 个节点可以休眠/分配给其他任务组
  → 节省电力和运维成本
```

#### Bin Packing 的风险

```
风险场景：
  Node-1 集中了 Job-A、Job-B、Job-E（7/8 GPU）
  Node-2 集中了 Job-C、Job-D（8/8 GPU）
  
  如果 Node-1 发生硬件故障：
    → 3 个任务同时中断
    → 需要同时恢复 3 个任务的 checkpoint
    → 队列瞬间涌入 7 个 GPU 的资源需求
```

### 4.3 Spread 深度分析

#### 算法实现

```python
def spread_scheduling(tasks, nodes):
    for task in tasks:
        # 按当前利用率从低到高排序节点（优先选择空闲节点）
        sorted_nodes = sorted(nodes, key=lambda n: n.utilization)
        
        # 可以结合最少任务数选择
        # sorted_nodes = sorted(nodes, key=lambda n: n.task_count)
        
        for node in sorted_nodes:
            if node.can_fit(task):
                node.schedule(task)
                break
```

#### Spread 的优势场景

```
场景：推理服务高可用部署

Spread 策略（跨机架分散）：
  Rack-1 Node-1: [Replica-0]
  Rack-2 Node-2: [Replica-1]
  Rack-3 Node-3: [Replica-2]
  Rack-4 Node-4: [Replica-3]

  任何一个机架故障 → 最多丢失 1 个副本 → 服务降级但不中断
```

#### Spread 的劣势

```
问题：资源碎片化

Spread 调度后：
  Node-1: 3/8 GPU 使用  ← 每个节点都有 5 卡空闲
  Node-2: 3/8 GPU 使用     但没有一个节点能装下
  Node-3: 2/8 GPU 使用     需要 6 GPU 的大任务
  Node-4: 2/8 GPU 使用
  Node-5: 2/8 GPU 使用
  Node-6: 3/8 GPU 使用
  Node-7: 2/8 GPU 使用
  Node-8: 1/8 GPU 使用
  
  → 碎片率极高，集群看似有 54 卡空闲，但无法运行 6 卡任务
  → 所有节点都需要上电，电力成本高
```

### 4.4 实际工程中的混合策略

现实中**不会纯粹使用 Bin Packing 或 Spread**，而是根据任务类型做差异化调度：

```
┌────────────────────────────────────────────────────────┐
│                混合调度策略设计                           │
├────────────────┬───────────────────────────────────────┤
│   任务类型      │         调度策略                       │
├────────────────┼───────────────────────────────────────┤
│ 大规模训练      │ Bin Packing 优先                       │
│ (≥8 GPU)      │ + 反亲和性约束（跨故障域分布）            │
│               │ → 保证资源效率的同时避免单点故障           │
├────────────────┼───────────────────────────────────────┤
│ 中小规模训练    │ Spread 优先                            │
│ (1~4 GPU)     │ + 同任务内亲和（同一节点或机架）          │
│               │ → 资源灵活分配，小任务可快速调度           │
├────────────────┼───────────────────────────────────────┤
│ 在线推理        │ Spread 强制                            │
│ (高可用要求)    │ + 跨机架反亲和                          │
│               │ → 故障隔离优先，资源利用率其次             │
├────────────────┼───────────────────────────────────────┤
│ 离线批处理      │ Bin Packing 强制                       │
│ (低优先级)     │ + 可调度到低利用率节点                   │
│               │ → 充分利用碎片资源，"填缝"执行            │
└────────────────┴───────────────────────────────────────┘
```

### 4.5 混合策略的实现框架

```python
class HybridScheduler:
    def schedule(self, task):
        # Step 1: 确定任务类型
        task_type = self.classify_task(task)  # training / inference / batch
        
        # Step 2: 获取候选节点
        candidates = self.filter_nodes(task)
        
        # Step 3: 根据任务类型选择调度策略
        if task_type == "large_training":
            scores = self.bin_packing_score(candidates, task)
            scores += self.anti_affinity_penalty(candidates, task) * 0.3
        elif task_type == "inference":
            scores = self.spread_score(candidates, task)
            scores += self.anti_affinity_bonus(candidates, task) * 0.5
        elif task_type == "batch":
            scores = self.bin_packing_score(candidates, task)
        else:  # small_training / dev
            scores = self.balanced_score(candidates, task)
        
        # Step 4: 结合亲和性/反亲和性最终评分
        scores += self.affinity_score(candidates, task) * 0.2
        
        # Step 5: 选择最优节点
        best_node = candidates[argmax(scores)]
        return best_node
```
