## 一、容器的本质：一个被约束的 Linux 进程

容器不是虚拟机。它在内核看来就是一个普通的进程（或进程组），只是被以下机制"限制"了视野和能力：

```
容器 = Namespace(隔离视野) + Cgroup(限制资源) + Capabilities(削减权限)
     + Seccomp(限制系统调用) + rootfs(独立文件系统)
```

下面逐个拆解每一个机制的内核实现。

## 二、Namespace 深入

### 2.1 创建过程（系统调用级别）

```c
// runc 创建容器的核心代码（简化）
// 文件：libcontainer/nsenter/nsexec.c

// 第一阶段：clone 创建新进程，同时创建所有 namespace
pid_t child = clone(
    container_main,
    stack_top,
    CLONE_NEWNS    |    // Mount namespace
    CLONE_NEWUTS   |    // UTS namespace
    CLONE_NEWIPC   |    // IPC namespace
    CLONE_NEWUSER  |    // User namespace
    CLONE_NEWPID   |    // PID namespace
    CLONE_NEWNET   |    // Network namespace
    CLONE_NEWCGROUP|    // Cgroup namespace
    SIGCHLD,
    &clone_args
);
```

### 2.2 PID Namespace 嵌套

```
Host PID NS          Container PID NS (level 1)     Nested Container (level 2)
PID 1 (systemd)      
PID 456 (dockerd)    
PID 1000 (shim)      PID 1 (shim)                   PID 1 (shim2)
PID 1001 (runc)      
PID 1002 (app)       PID 2 (app)                    PID 2 (app)
```

```bash
# 查看进程的真实 PID（从宿主机视角）

# 输出：1002

# 进入容器的 namespace 看到的 PID
nsenter -t 1002 -p -n ps aux
# PID 1 → shim 进程
# PID 2 → 用户应用
```

**内核实现细节**：

```c
// 内核源码 kernel/pid.c
// 每个 PID namespace 都有自己的 PID 分配器
struct pid_namespace {
    struct kref kref;
    struct pidmap pidmap[PIDMAP_ENTRIES];  // 位图，标记哪些 PID 已分配
    struct task_struct *child_reaper;       // PID 1，负责回收孤儿进程
    int level;                              // 嵌套层级
    struct pid_namespace *parent;           // 父 namespace
};

// 进程在每个 namespace 层级都有一个 PID
// 内核用 upid 结构存储：
struct pid {
    atomic_t count;
    unsigned int level;            // 最深层级
    struct upid numbers[0];        // 柔性数组
};

struct upid {
    int nr;                        // 在该 namespace 中的 PID 号
    struct pid_namespace *ns;      // 所属 namespace
};
```

### 2.3 Mount Namespace + pivot_root

这是容器拥有独立文件系统的关键：

```bash
# 传统 chroot 的问题：
# - 可以通过 .. 路径逃逸（内核已修复大部分）
# - 不影响挂载点视图
# - 安全性不够

# pivot_root：真正切换根文件系统
# 系统调用：pivot_root(new_root, put_old)
```

**runc 的 rootfs 准备过程**：

```bash
# 步骤 1: 挂载 overlay2（或指定的存储驱动）
mount -t overlay overlay \
  -o lowerdir=/var/lib/docker/overlay2/lower,
          upperdir=/var/lib/docker/overlay2/upper,
          workdir=/var/lib/docker/overlay2/work \
  /var/lib/docker/overlay2/merged

# 步骤 2: bind mount proc, sys, dev 等伪文件系统
mount -t proc proc /var/lib/docker/overlay2/merged/proc
mount -t sysfs sysfs /var/lib/docker/overlay2/merged/sys
mount -t tmpfs tmpfs /var/lib/docker/overlay2/merged/dev

# 步骤 3: 创建 put_old 目录
mkdir /var/lib/docker/overlay2/merged/.old_root

# 步骤 4: 执行 pivot_root
pivot_root /var/lib/docker/overlay2/merged /var/lib/docker/overlay2/merged/.old_root

# 步骤 5: 卸载旧的根文件系统
umount2("/.old_root", MNT_DETACH)
rmdir("/.old_root")

# 此时进程看到的 / 就是容器的 rootfs
```

```c
// 内核源码 fs/namespace.c
SYSCALL_DEFINE2(pivot_root, const char __user *, new_root,
                const char __user *, put_old)
{
    // 1. 验证 new_root 是一个挂载点
    // 2. 验证 put_old 在 new_root 下面
    // 3. 切换当前进程的 root 和 pwd 到 new_root
    // 4. 将旧的 root 移动到 put_old
    // 核心操作：交换两个挂载点在 mount 树中的位置
}
```

## 三、Cgroup v2 深入

### 3.1 核心数据结构

```c
// 内核源码 include/linux/cgroup-defs.h

struct cgroup {
    struct cgroup_subsys_state self;
    unsigned long flags;
    int level;                      // 层级深度
    int max_descendants;            // 最大子 cgroup 数
    int nr_descendants;             // 当前子 cgroup 数
    
    struct cgroup *parent;          // 父 cgroup
    struct list_head sibling;       // 兄弟链表
    struct list_head children;      // 子 cgroup 链表
    
    // cgroup v2 统一层级
    struct cgroup_subsys_state *subsys[CGROUP_SUBSYS_COUNT];
    
    // 关键：进程列表
    struct list_head procs;         // 属于此 cgroup 的线程
    struct list_head rstat_css_list;
};
```

### 3.2 Docker 的 cgroup 配置

```bash
# Docker 创建容器时设置的 cgroup 结构：
/sys/fs/cgroup/system.slice/docker-<container-id>.scope/

# Cgroup v2 统一目录结构：
├── cgroup.controllers        # 可用控制器：cpuset cpu io memory pids
├── cgroup.procs              # 进程 PID 列表
├── cgroup.threads            # 线程 TID 列表
├── cpu.max                   # CPU 限制 "quota period"
│   # 例: "50000 100000" = 50% 单核
├── cpu.weight                # CPU 权重 (1-10000, 默认100)
├── memory.max                # 内存硬限制 (bytes)
├── memory.high               # 内存软限制（触发回收）
├── memory.low                # 内存保护（最低保障）
├── memory.current            # 当前内存使用量
├── memory.swap.max           # swap 限制
├── io.max                    # I/O 带宽限制
│   # 例: "8:0 rbps=10485760 wbps=10485760"
├── pids.max                  # 最大进程数
└── pids.current              # 当前进程数
```

### 3.3 CPU 限制的内核实现

```bash
# Docker 命令：
docker run --cpus=1.5 myapp

# 等价于：
# cpu.max = "150000 100000"  (150ms quota per 100ms period)
```

```c
// 内核调度器的实现 kernel/sched/fair.c

struct cfs_bandwidth {
    u64 quota;              // 配额（纳秒）
    u64 period;             // 周期（纳秒）
    u64 runtime;            // 剩余运行时间
    s64 hierarchical_quota; // 层级配额
    u64 runtime_expires;    // 配额过期时间
    int idle;               // 是否空闲
    int period_active;      // 周期是否激活
    ...
};

// 调度器在每个 tick 检查：
// 1. 当前进程是否在受限 cgroup 中
// 2. cgroup 的 runtime 是否用完
// 3. 用完 → throttle（暂停调度），直到下一个 period 刷新
// 4. 刷新 → runtime = quota，恢复调度
```

```
时间线示例（cpu.max = "150000 100000"，即 1.5 核）：

Period 1: [0ms ──────── 100ms]
           ████████████░░░░░░░  ← 用了 150ms CPU 时间后被 throttle
           ^150ms^

Period 2: [100ms ────── 200ms]
           ████████████░░░░░░░  ← 刷新后又能用 150ms

如果容器只有 1 个 CPU 密集线程 → 它能用满 1 个核
如果有 3 个线程争抢 → 总共只能用 1.5 核，多余的被 throttle
```

### 3.4 Memory 限制的内核实现

```bash
docker run --memory=512m --memory-swap=1g myapp
# memory.max = 536870912
# memory.swap.max = 536870912  (swap 限额 = swap总限额 - 内存限额)
```

```c
// 内核 mm/memcontrol.c

// OOM 触发流程：
// 1. 进程申请内存 → 发现 cgroup memory.max 已满
// 2. 尝试回收（reclaim）→ 回收不够
// 3. 尝试 swap → swap 也满了
// 4. 触发 OOM killer
static int oom_evaluate_tasks(struct oom_control *oc)
{
    // 在 cgroup 内部选择一个进程杀掉
    // 选择标准：oom_badness() 评分最高的
    // 评分 = 进程的 RSS + swap 使用量 + 子进程内存
    // root 进程不加分（不再像以前那样）
}

// memory 阶梯控制：
// memory.low  → "保护线"，低于此值的内存不会被回收
// memory.high → "软限制"，超过后进程被节流（throttle），触发更积极的回收
// memory.max  → "硬限制"，超过后 OOM killer 介入
```

```
内存压力响应图：

使用量     memory.low    memory.high    memory.max
  │           │              │              │
  ▼           ▼              ▼              ▼
  ────────────┼──────────────┼──────────────┤
   正常运行    │   积极回收    │  OOM killer   │
              │   进程被throttle│  杀掉进程     │
              │              │              │
         保护不被回收     软限制          硬限制
```

```c
// 内核 block/blk-cgroup.c
// 使用令牌桶算法（Token Bucket）

struct throtl_grp {
    struct blkg_policy_data pd;
    
    // 每个设备方向的令牌桶
    struct throtl_data {
        uint64_t bytes_per_sec;        // 每秒允许的字节数
```

## 四、Seccomp-BPF 深入

### 4.1 工作原理

```c
// seccomp 使用 BPF (Berkeley Packet Filter) 程序过滤系统调用
// 内核源码 kernel/seccomp.c

// 系统调用入口处的检查：
static int __seccomp_filter(int this_syscall, ...)
{
    // 1. 获取当前进程的 seccomp filter 链
    struct seccomp_filter *f = current->seccomp.filter;
    
    // 2. 用 BPF 程序评估系统调用号和参数
    int ret = seccomp_run_filters(f);
    // BPF 返回值：
    // SECCOMP_RET_KILL   → 立即杀死进程 (SIGSYS)
    // SECCOMP_RET_ERRNO  → 返回错误号
    // SECCOMP_RET_TRACE  → 通知 ptrace tracer
    // SECCOMP_RET_ALLOW  → 允许通过
    // SECCOMP_RET_LOG    → 允许但记录日志
    // SECCOMP_RET_USER_NOTIF → 通知用户态监控进程
    
    return ret;
}
```

```c
// Linux 5.0+ 引入 SECCOMP_RET_USER_NOTIF
// 允许将被拦截的系统调用转发到用户态处理

// 使用场景：
// - sysbox 运行时：在容器内运行 Docker（Docker-in-Docker）
// - 安全审计：监控容器的敏感系统调用

// 2. seccomp filter 返回 SECCOMP_RET_USER_NOTIF

// 5. 监控进程决定：执行真正的 mount() 并返回结果，或拒绝
// 6. 容器内进程收到结果，继续执行
```

## 五、Linux Capabilities 细粒度控制

### 5.1 内核实现

```c
// 每个进程有一个 capability 集合
// 内核 include/uapi/linux/capability.h

// 关键 capability：
#define CAP_DAC_OVERRIDE      1   // 绕过文件读写权限检查
#define CAP_NET_RAW          13   // 使用 RAW socket（ping, 抓包）
#define CAP_NET_ADMIN         12   // 修改网络配置（iptables, 路由）
#define CAP_SYS_ADMIN         21   // 超级能力：mount, namespace, bpf 等
#define CAP_SYS_PTRACE        19   // 跟踪其他进程
#define CAP_SYS_MODULE         16   // 加载内核模块
#define CAP_NET_BIND_SERVICE  10   // 绑定 1024 以下端口

// Docker 默认保留的 capabilities：
static const char *default_caps[] = {
    "CHOWN", "DAC_OVERRIDE", "FSETID", "FOWNER",
    "MKNOD", "NET_RAW", "SETGID", "SETUID",
    "SETFCAP", "SETPCAP", "NET_BIND_SERVICE",
    "SYS_CHROOT", "KILL", "AUDIT_WRITE"
};

// 权限检查（每次涉及特权操作时）：
static bool has_capability_noaudit(struct task_struct *t, int cap)
{
    // 检查进程的 effective capability 集合
    return cap_raised(t->cred->cap_effective, cap);
}

// SYS_ADMIN 被禁止后，容器无法：
// mount/umount          (mount namespace 除外)
// swapon/swapoff
// sethostname
// setdomainname
// pivot_root            (runc 有特殊 workaround)
// bpf() 系统调用
// perf_event_open()
// ...
```

### 5.2 完全剥夺能力的效果

```bash
docker run --cap-drop ALL --cap-add NET_BIND_SERVICE myapp

# 效果：
# - 无法 ping（无 NET_RAW）
# - 无法修改网络配置（无 NET_ADMIN）
# - 无法加载模块（无 SYS_MODULE）
# - 无法 strace（无 SYS_PTRACE）
# - 可以绑定 80 端口（有 NET_BIND_SERVICE）
# - 大多数普通应用只需要这个就能正常运行
```

### 6.2 runc 的容器创建完整流程

```go
// runc/libcontainer/container_linux.go (简化)

func (c *linuxContainer) start(process *Process) error {
    
    // 步骤 1: 创建 cgroup
    // 写入 /sys/fs/cgroup/system.slice/docker-<id>/
    c.cgroupManager.Apply(pid)
    c.cgroupManager.Set(c.config.Resources)
    
    // 步骤 2: 配置网络
    // 创建 veth pair，一端放入容器 netns
    for _, iface := range c.config.NetworkInterfaces {
        createInNetns(iface, containerNetns)
    }
    
    // 步骤 3: 创建子进程（clone + namespace）
    cmd := exec.Command("/proc/self/exe", "init")
    cmd.SysProcAttr = &syscall.SysProcAttr{
        Cloneflags: syscall.CLONE_NEWNS |
                    syscall.CLONE_NEWUTS |
                    syscall.CLONE_NEWIPC |
                    syscall.CLONE_NEWPID |
                    syscall.CLONE_NEWNET |
                    syscall.CLONE_NEWCGROUP,
    }
    
    // 步骤 4: 通过 pipe 同步子进程的准备状态
    parentPipe, childPipe := newPipe()
    cmd.ExtraFiles = []*os.File{childPipe}
    
    // 步骤 5: 启动子进程
    cmd.Start()  // 子进程进入 "init" 模式
    
    // 步骤 6: 子进程的 init 阶段：
    //   a. 配置 hostname (sethostname)
    //   b. 设置 user/group (setuid/setgid)
    //   c. 挂载 /proc, /sys, /dev
    //   d. pivot_root
    //   e. 设置 capabilities (capset)
    //   f. 应用 seccomp filter
    //   g. 设置 rlimits
    //   h. exec 用户进程
    
    // 步骤 7: 等待子进程完成准备
    // 通过 pipe 通信确保所有初始化完成
    
    return nil
}
```

### 6.3 状态机

```
  creating ──→ created ──→ running ──→ stopped
                   │           │
                   │           ▼
                   │        paused ──→ running
                   │
                   └──→ (直接删除)

每个状态的内核含义：
  creating: runc 正在 clone 进程、配置 namespace/cgroup
  created:  进程已创建但未 exec 用户命令（停在 init 阶段）
  running:  exec 完成，用户进程在执行
  paused:   cgroup freezer 冻结所有进程
  stopped:  进程已退出，cgroup 已清理

冻结实现 (cgroup v2):
  echo 1 > /sys/fs/cgroup/.../cgroup.freeze
  # 内核将该 cgroup 内所有进程的状态设为 TASK_FROZEN
  # 它们不会被调度，直到解冻
```

## 七、存储驱动底层细节（Overlay2）

### 7.1 内核 OverlayFS 实现

```c
// 内核 fs/overlayfs/super.c

// OverlayFS 的核心概念：
// upperdir: 可写层（容器层）
// lowerdir: 只读层（镜像层，可以多层叠加）
// workdir:  OverlayFS 内部工作目录
// merged:   合并后的视图

// 读文件：
static int ovl_readpage(struct file *file, struct page *page)
{
    // 1. 先在 upperdir 查找
    // 2. 如果没有，在 lowerdir 查找（从上到下）
    // 3. 找到后读取数据
    realfile = ovl_real_file(file);
    return realfile->f_op->readpage(realfile, page);
}

// 写文件 (Copy-on-Write)：
static int ovl_write_begin(struct file *file, ...)
{
    // 1. 如果文件在 upperdir → 直接写
    // 2. 如果文件在 lowerdir → 先 copy up 到 upperdir，再写
    if (!ovl_is_upper_xxx(dentry)) {
        err = ovl_copy_up(dentry);  // 复制到可写层
    }
    // 然后在 upperdir 的副本上执行写操作
}

// 删除文件 (Whiteout)：
// 不能直接删除 lowerdir 的文件（只读）
// 在 upperdir 创建一个 character device (0,0) 作为 "白障"
// OverlayFS 看到白障后会隐藏 lowerdir 中对应的文件

static int ovl_remove_whiteout(struct dentry *whiteout)
{
    // 创建 mknod(whiteout, S_IFCHR|S_IFWHITEOUT, MKDEV(0,0))
    // 这个特殊文件标记 "此文件已被删除"
}
```

## 八、进程间通信与容器信号处理

### 8.1 PID 1 问题

```bash
# 容器内 PID 1 的特殊行为：
# 1. 内核向 PID 1 发送的信号默认不执行默认动作
#    （没有注册 handler 的信号会被忽略，而不是终止进程）
# 2. 这是为了保护 init 进程（systemd）

# 问题：如果容器的 ENTRYPOINT 没有正确处理信号
docker run myapp  # myapp 是一个 Python 进程，PID 1
docker stop myapp # 发送 SIGTERM
# 等待 10 秒 → Python 没处理 SIGTERM → 发送 SIGKILL → 强制终止

# 解决方案：
# 1. 使用 tini 作为 init 进程
ENTRYPOINT ["tini", "--", "./app"]

# 2. 在应用中正确处理 SIGTERM
# 3. 使用 --init 标志（Docker 内置 tini）
docker run --init myapp

# tini 做的事情：
# - 作为 PID 1 运行
# - 注册所有信号处理
# - 将信号转发给子进程
# - 回收僵尸进程（waitpid）
```

```c
// tini 的核心逻辑（极简版）：
int main() {
    // fork 出真正的用户进程
    pid_t child = fork();
    if (child == 0) {
        execvp(argv[0], argv);  // 执行用户命令
    }
    
    // tini 自身进入循环：
    while (1) {
        int status;
        pid_t pid = wait(&status);  // 回收子进程（避免僵尸）
        
        if (pid == child) {
            // 子进程退出了，tini 用相同的退出码退出
            _exit(WEXITSTATUS(status));
        }
    }
}

// 信号处理：
// SIGTERM/SIGINT → forward 给 child
// child 退出 → tini 退出（保持退出码一致）
```
