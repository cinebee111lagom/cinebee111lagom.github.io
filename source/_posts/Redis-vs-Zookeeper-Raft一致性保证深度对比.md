## Redis vs Zookeeper/Raft 一致性保证深度对比

---

### 一、先明确三种系统的设计目标

```
┌─────────────┬───────────────────────────────────────────┐
│    系统       │  设计目标                                  │
├─────────────┼───────────────────────────────────────────┤
│  Redis       │  极致性能的缓存/KV存储，高可用是附加能力       │
│  Zookeeper   │  分布式协调服务，强一致性是核心目标            │
│  Raft        │  一致性算法本身，不是系统，是被实现的协议       │
└─────────────┴───────────────────────────────────────────┘

本质上是三件不同的事：
  Redis  → "我要快，尽量不丢数据"
  ZK     → "我必须保证数据一致，宁可不可用"
  Raft   → "我是一个数学上被证明正确的一致性协议"
```

---

### 二、复制模型的根本差异

#### Redis：异步复制

```
Client ──SET k v──▶ Master
                     │
                     │ ① 写入本地内存
                     │ ② 立即返回 OK 给客户端 ← 不等Slave
                     │
                     │ 异步发送给 Slave（后台线程）
                     ▼
                   Slave（可能延迟几百ms才收到）

时间线：
  t0: Client 发送 SET
  t1: Master 写入成功 → Client 收到 OK  ← 你认为成功了
  t2: Master 异步发给 Slave
  t3: Slave 收到并写入                  ← 数据才真正有副本

  如果 Master 在 t1~t3 之间宕机：
  → Client 认为成功了
  → Slave 上没有这条数据
  → 数据丢失
```

#### Zookeeper：过半写入（类Raft）

```
Client ──SET k v──▶ Leader (ZK)
                     │
                     │ ① 写入本地日志
                     │ ② 并行发给所有 Follower
                     │
                     ▼
              Follower 1 ──ACK──▶  Leader
              Follower 2 ──ACK──▶  Leader
              Follower 3     （还在路上）
              Follower 4     （还在路上）
                     │
                     │ 收到2个ACK + 自己 = 3/5 过半 ✓
                     │
                     ▼
              提交（Commit）→ 返回 OK 给 Client

时间线：
  t0: Client 发送 SET
  t1: Leader 写入本地日志
  t2: Leader 发给 Follower
  t3: 收到过半 ACK → Commit → Client 收到 OK
  t4: 剩余 Follower 继续同步

  如果 Leader 在 t3 之后宕机：
  → 已经过半确认，数据在多数节点上有副本
  → 新 Leader 一定包含这条数据
  → 零丢失
```

#### Raft 协议本身的复制流程

```
┌─────────────────────────────────────────────────────────┐
│                    Raft 日志复制                          │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  Client ──请求──▶ Leader                                │
│                    │                                    │
│                    ▼                                    │
│            ┌─────────────┐                              │
│            │ Leader 本地   │                              │
│            │ 追加日志条目   │  index=5, term=3, cmd=SET  │
│            └──────┬──────┘                              │
│                   │                                     │
│        ┌──────────┼──────────┐                          │
│        ▼          ▼          ▼                          │
│   Follower1  Follower2  Follower3                       │
│   AppendEntries RPC      (网络慢，还没到)                 │
│        │          │                                     │
│        ▼          ▼                                     │
│      ACK        ACK                                     │
│   index=5     index=5                                    │
│        │          │                                     │
│        └────┬─────┘                                     │
│             ▼                                           │
│   Leader 收到过半 ACK（3/5）                              │
│   commitIndex = 5                                       │
│             │                                           │
│             ▼                                           │
│   应用到状态机 → 返回 Client OK                           │
│             │                                           │
│             ▼                                           │
│   通知 Follower commitIndex=5                           │
│   Follower 3 陆续追上                                    │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

### 三、Leader 选举机制对比

#### Redis Sentinel 选举

```
基于 Raft 变体，但有关键简化：

  ┌─────────────────────────────────────────┐
  │  Sentinel Leader 选举                     │
  ├─────────────────────────────────────────┤
  │                                         │
  │  1. 发现 Master ODOWN                    │
  │  2. 自增配置纪元 configEpoch              │
  │  3. 向其他 Sentinel 拉票                  │
  │     "epoch=5，投我当Leader处理故障转移"    │
  │  4. 每个 Sentinel 每个 epoch 只投一票     │
  │     先到先得                              │
  │  5. 获得 >N/2 票 → 成为 Leader            │
  │  6. Leader 执行故障转移                    │
  │                                         │
  │  简化之处：                                │
  │  - 没有日志复制（Sentinel不存业务数据）      │
  │  - 没有日志匹配（Log Matching）检查         │
  │  - 选举失败后等下一个epoch重试              │
  │  - 没有 Pre-Vote 机制                     │
  └─────────────────────────────────────────┘
```

#### Raft 完整选举

```
┌───────────────────────────────────────────────────────┐
│                    Raft Leader 选举                     │
├───────────────────────────────────────────────────────┤
│                                                       │
│  1. Follower 超时未收到 Leader 心跳                     │
│     electionTimeout = 150~300ms（随机）                 │
│                                                       │
│  2. 转为 Candidate，自增 term                           │
│     term 从 3 → 4                                     │
│                                                       │
│  3. 先投自己一票，然后并发 RequestVote RPC              │
│                                                       │
│  4. 其他节点投票的条件（严格）：                         │
│     ① 我的 term < 你的 term（你的任期更新）             │
│     ② 我还没在当前 term 投过票                          │
│     ③ 你的日志至少和我一样新                             │
│        （比较 lastLogIndex 和 lastLogTerm）             │
│        ← 这个条件保证选出的 Leader 拥有所有已提交日志     │
│                                                       │
│  5. 获得 >N/2 票 → 成为 Leader                         │
│     向所有节点发送心跳，宣告领导权                       │
│                                                       │
│  6. 如果没有 Candidate 获得多数票                       │
│     → 超时 → term +1 → 重新选举                        │
│     （随机超时时间减少活锁概率）                         │
│                                                       │
│  关键保证：                                            │
│  - 任何 term 最多一个 Leader（选举安全性）              │
│  - 日志比较保证已提交条目不会丢失                        │
│  - 随机超时保证最终选出 Leader（活性）                   │
└───────────────────────────────────────────────────────┘
```

#### Zookeeper（ZAB 协议）选举

```
┌───────────────────────────────────────────────────────┐
│                    ZAB 选举（FastLeaderElection）       │
├───────────────────────────────────────────────────────┤
│                                                       │
│  1. 节点启动或发现 Leader 不可达                        │
│     进入 LOOKING 状态                                  │
│                                                       │
│  2. 发送投票 (epoch, zxid, myid)                       │
│     epoch  = 逻辑时钟（类似Raft的term）                 │
│     zxid   = 最新事务ID（越大越新）                     │
│     myid   = 节点唯一标识（用于打破平局）               │
│                                                       │
│  3. 收到其他节点投票后，更新自己的投票                   │
│     优先比较 zxid（事务最新的优先）                      │
│     zxid 相同则比较 myid（大的优先）                    │
│                                                       │
│  4. 这个过程是多轮的（互相交换投票，逐步收敛）            │
│     直到过半节点达成一致                                │
│                                                       │
│  5. 选出 Leader 后：                                   │
│     - Leader 等待 Follower 连接                        │
│     - Follower 与 Leader 同步数据                      │
│     - 同步完成 → 进入正常服务状态                       │
│                                                       │
│  vs Raft 的区别：                                      │
│  - ZAB 是先选再同步，Raft 是边选边检查日志               │
│  - ZAB 用 zxid 比较，Raft 用 lastLogTerm+Index         │
│  - ZAB 的 epoch 收敛是多轮的，Raft 是一锤子投票          │
└───────────────────────────────────────────────────────┘
```

### 四、日志（数据）一致性保证

#### Raft 的日志匹配特性

```
Raft 日志：每条日志有 (term, index)

  Leader:    [1:1] [1:2] [2:3] [3:4] [3:5] [3:6]
              term  term  term  term  term  term

  Follower A: [1:1] [1:2] [2:3] [3:4] [3:5]      ✓ 匹配到5
  Follower B: [1:1] [1:2] [2:3]                   ✓ 匹配到3
  Follower C: [1:1] [1:2] [4:3]                   ✗ 3号位置term不同！

Log Matching Property（日志匹配特性）：
  如果两个日志在某个 index 的 term 相同
  那么该 index 及之前的所有日志都相同

  这个特性怎么保证的？
  ┌─────────────────────────────────────────────────┐
  │ AppendEntries RPC 包含：                          │
  │   - prevLogIndex: 上一条日志的 index               │
  │   - prevLogTerm:  上一条日志的 term                │
  │                                                 │
  │ Follower 收到后：                                 │
  │   检查自己在 prevLogIndex 位置的 term              │
  │   如果不匹配 → 拒绝 → Leader 回退重试             │
  │   如果匹配 → 追加新日志                           │
  │                                                 │
  │ Leader 回退过程：                                  │
  │   nextIndex[Follower] 逐次 -1                     │
  │   直到找到匹配点 → 从该点开始同步                   │
  │   （实践中可以优化为批量回退）                      │
  └─────────────────────────────────────────────────┘
```

#### ZAB 的事务同步

```
ZK 用 zxid（64位）标识事务：
  高32位 = epoch（Leader轮次）
  低32位 = counter（事务计数）

  zxid 越大 = 越新的事务

  Leader:     zxid=3.1, 3.2, 3.3, 3.4
  Follower A: zxid=3.1, 3.2, 3.3          ← 差一个
  Follower B: zxid=2.1, 2.2              ← epoch都不对

  同步过程：
  ① Follower 发送自己的 lastZxid 给 Leader
  ② Leader 判断需要同步多少数据
  ③ 差异小 → 增量同步（DIFF）
  ④ 差异大 → 快照 + 增量（SNAP + TRUNC + DIFF）
  ⑤ 完全无法恢复 → 全量同步

  vs Raft:
  ZAB 的回退粒度更粗（按zxid）
  Raft 的日志匹配检查更精细（逐条检查term+index）
```

#### Redis 的复制

```
Redis 没有"日志"这个概念用于复制

  ┌─────────────────────────────────────────────────┐
  │ Redis 的"日志"有两个：                             │
  │                                                 │
  │ 1. RDB（内存快照）                                │
  │    - fork子进程生成                               │
  │    - 全量数据的二进制序列化                        │
  │    - 用于全量同步                                 │
  │                                                 │
  │ 2. AOF（追加命令日志）                             │
  │    - 类似操作日志                                 │
  │    - 但 AOF 不参与主从复制！                       │
  │    - 主从复制靠的是 repl_backlog                   │
  │                                                 │
  │ 3. repl_backlog（环形缓冲区）                     │
  │    - Master 上的内存缓冲区                        │
  │    - 存储最近的写命令流                            │
  │    - Slave 断开后重连用 offset 增量同步            │
  │    - 如果 offset 被覆盖 → 退化全量同步             │
  └─────────────────────────────────────────────────┘

  关键区别：
  - Raft/ZK 的日志是持久化到磁盘的
  - Redis 的 repl_backlog 是纯内存的环形缓冲区
  - Master 重启后 repl_backlog 就没了
  - Slave 必须全量同步
```

### 五、一致性模型对比

```
┌──────────────┬───────────────┬──────────────┬──────────────┐
│    维度        │    Redis       │  Zookeeper   │    Raft      │
├──────────────┼───────────────┼──────────────┼──────────────┤
│ 一致性强度     │ 最终一致性      │ 线性一致性     │ 线性一致性    │
│              │ （默认）        │（写操作）      │（写操作）     │
├──────────────┼───────────────┼──────────────┼──────────────┤
│ 写入确认       │ 不等Slave      │ 过半确认后    │ 过半确认后    │
│              │ 立即返回OK     │ 才返回OK      │ 才返回OK     │
├──────────────┼───────────────┼──────────────┼──────────────┤
│ 数据丢失可能   │ 有（主从切换时） │ 无（已提交的）│ 无（已提交的）│
├──────────────┼───────────────┼──────────────┼──────────────┤
│ 读一致性       │ 可能读到旧数据   │ 顺序一致性    │ 线性读需要    │
│              │               │ （读Follower）│ 走Leader     │
├──────────────┼───────────────┼──────────────┼──────────────┤
│ Leader宕机后  │ 数据可能丢失    │ 数据不会丢失  │ 数据不会丢失  │
│ 数据安全性     │              │              │              │
└──────────────┴───────────────┴──────────────┴──────────────┘
```

### 六、线性一致性到底是什么

```
线性一致性（Linearizability）= 读你的写（Read Your Writes）

场景：

  Client A: SET k1 v1    ──────── GET k1 = ?
  Client B:                   GET k1 = ?

线性一致性要求：
  如果 Client A 的 SET 在时间 t1 完成
  那么 t1 之后任何 Client 的 GET 都必须返回 v1

  ────────────────────────────────────────────
  时间轴：   t0          t1           t2
             SET k1 v1   完成          GET k1
             ▲                        ▲
             │                        │
             │   Raft/ZK: 返回 v1 ✓   │
             │   Redis: 可能返回 nil ✗ │
             │          或旧值         │
  ────────────────────────────────────────────

为什么 Redis 不满足？
  因为异步复制，写入 Master 后 Slave 可能还没同步
  如果读请求打到 Slave → 读到旧值
  
  即使读 Master，主从切换后新 Master 可能没有这条数据
```

```
Raft 如何保证线性一致性？

  读操作方案一：ReadIndex
  ┌──────────────────────────────────────────────┐
  │  Client ──GET k1──▶ Leader                   │
  │                      │                       │
  │                      │ ① 记录当前 commitIndex │
  │                      │ ② 发心跳确认自己仍是Leader│
  │                      │ ③ 等待 applyIndex ≥ commitIndex│
  │                      │ ④ 执行读，返回结果      │
  │                      ▼                       │
  │  Client ◀── v1 ──── Leader                  │
  │                                               │
  │  代价：每次读要等一次心跳 + apply延迟            │
  └──────────────────────────────────────────────┘

  读操作方案二：Lease Read（租约读）
  ┌──────────────────────────────────────────────┐
  │  Leader 维护一个"租约时间"                      │
  │  在租约有效期内，确认自己仍然是 Leader           │
  │  租约内直接读本地，不需要额外通信                │
  │                                               │
  │  依赖：时钟偏差在可控范围内                      │
  │  性能：最优，和本地读一样快                      │
  └──────────────────────────────────────────────┘

  读操作方案三：Follower Read
  ┌──────────────────────────────────────────────┐
  │  Follower 收到读请求后                         │
  │  向 Leader 请求当前 commitIndex                │
  │  等本地 apply 到该 index 后再读                 │
  │                                               │
  │  优点：读请求可以分散到所有节点                   │
  │  缺点：还是要和 Leader 通信一次                  │
  └──────────────────────────────────────────────┘
```

```
ZK 如何保证？

  ZK 默认读 Follower → 不保证线性一致性（只保证顺序一致性）

  sync() + read 可以实现线性读：
  ┌──────────────────────────────────────────────┐
  │  Client ──sync()──▶ Leader                   │
  │  Leader 将 sync 作为一个事务，追加到日志        │
  │  sync 过半确认后 → 返回                       │
  │  Client 此时再 read → 能读到 sync 之前的所有提交│
  │                                               │
  │  代价：sync 是一次写操作级别的开销               │
  └──────────────────────────────────────────────┘

  实际上 ZK 3.3.0+ 支持 Leader 读模式：
  连接到 Leader 读 → 天然线性一致性
```

### 七、故障恢复时的数据完整性

#### Leader 宕机后的数据完整性证明

```
Raft 的数学证明：

  前提：日志被过半节点存储
  结论：新选出的 Leader 一定拥有所有已提交的日志

  证明思路：
  ┌─────────────────────────────────────────────────┐
  │ 假设日志 E 在 term T 被 Leader L 提交            │
  │ → E 存储在过半节点上                              │
  │                                                 │
  │ 新 Leader L' 在 term T' (T' > T) 当选            │
  │ → L' 获得过半节点的投票                           │
  │                                                 │
  │ 两个"过半"必然有交集                              │
  │ → 至少有一个节点既存了 E 又投了 L'                │
  │                                                 │
  │ 选举规则要求：L' 的日志必须和投票者一样新或更新     │
  │ → L' 必然包含 E                                  │
  │                                                 │
  │ QED: 已提交的日志不会丢失                         │
  └─────────────────────────────────────────────────┘
```

```
Redis 的情况：

  Master 宕机后选新 Master：
  ┌─────────────────────────────────────────────────┐
  │  Sentinel 按优先级选 Slave：                      │
  │  1. slave-priority（可配，默认1）                  │
  │  2. 复制偏移量（replication offset，越大越新）     │
  │  3. runid（随机ID，小的优先）                      │
  │                                                 │
  │  选的是"数据最新的 Slave"                          │
  │  但"最新"≠"完整"                                  │
  │                                                 │
  │  Master: [cmd1][cmd2][cmd3][cmd4][cmd5]          │
  │                              ↑                  │
  │                           异步复制到这里           │
  │  Slave:  [cmd1][cmd2][cmd3]                      │
  │                         ↑                        │
  │                    Slave的offset                  │
  │                                                 │
  │  cmd4、cmd5 只在 Master 上                       │
  │  Master 宕机 → cmd4、cmd5 丢失                   │
  │  没有任何机制能阻止这个丢失                        │
  └─────────────────────────────────────────────────┘
```

### 八、性能 vs 一致性的取舍

```
                    一致性
                      ▲
                      │
          Raft/ZK ────┤──── 线性一致
                      │
                      │
                      │
                      │
          Redis+WAIT ─┤──── 强一致（半同步）
                      │
                      │
                      │
          Redis ──────┤──── 最终一致
                      │
                      └──────────────────────▶ 性能
                                              （吞吐量/延迟）

  Redis 原生：    ~100,000+ QPS，亚毫秒延迟，最终一致
  Redis + WAIT：  ~50,000 QPS，多一次RTT，接近强一致
  Zookeeper：     ~10,000~30,000 OPS，2~10ms延迟，线性一致
  etcd (Raft)：   ~10,000 OPS，几ms延迟，线性一致
```

```
为什么 Raft/ZK 慢这么多？

  ┌───────────────────────────────────────────────┐
  │  Redis 写入路径：                               │
  │                                               │
  │  Client → Master 内存写入 → 返回 OK             │
  │                           全程内存操作，极快     │
  │                                               │
  │  代价：Slave 可能没收到就宕机了                  │
  ├───────────────────────────────────────────────┤
  │  Raft/ZK 写入路径：                             │
  │                                               │
  │  Client → Leader 追加日志到磁盘(fsync)          │
  │         → 并行发给 Follower                     │
  │         → Follower 也 fsync 到磁盘              │
  │         → 收到过半 ACK                          │
  │         → commit → 返回 OK                     │
  │                                               │
  │  额外开销：                                     │
  │  - fsync 磁盘写入（最慢，通常 1~5ms）           │
  │  - 多次网络往返（至少1次RTT）                    │
  │  - 过半确认的等待时间                            │
  │                                               │
  │  代价：吞吐量和延迟都不如 Redis                   │
  │  收益：已提交的数据绝对不会丢                     │
  └───────────────────────────────────────────────┘
```

### 九、特殊场景对比

#### 场景1：Leader 切换期间的请求处理

```
Raft：
  旧 Leader 宕机
  → 选举期间（几百ms~几秒）所有写请求失败
  → 读请求也失败（除非用 Follower Read）
  → 新 Leader 选出后恢复
  → 期间的数据：已提交的不丢，未提交的可能丢（但客户端收到失败）
  
  关键：客户端知道写入失败了 → 可以重试 → 不会有"幽灵数据"

Redis：
  Master 宕机
  → Sentinel 选举（10~30秒）
  → 期间写入到旧 Master 的数据丢失
  → 客户端不知道数据丢了（之前已经返回 OK 了）
  
  关键：客户端认为成功了，但数据没了 → 幽灵数据
```

#### 场景2：网络分区恢复后的数据处理

```
Raft：
  分区A（少数派Leader）    分区B（多数派）
  
  分区A的 Leader：
    - 持续尝试发 AppendEntries
    - 大多数请求超时失败
    - 发现自己的 term 过时了
    - 自动降级为 Follower
    
  分区恢复后：
    - 分区A的旧 Leader 发现 term 更高的 Leader
    - 自动降级
    - 从新 Leader 同步日志
    - 自己分区期间"成功写入"的未提交日志被覆盖
    → 没有数据不一致

Redis：
  分区A（旧Master）       分区B（新Master）
  
  分区A 的 Master：
    - 根本不知道自己被降级了
    - 继续正常接受写入
    - 客户端继续成功写入
    
  分区恢复后：
    - 旧 Master 变成 Slave
    - 清空数据，全量同步
    - 分区期间的写入全部丢失
    → 数据不一致 + 客户端不知情
```

#### 场景3：脑裂后两个节点各自接受写入

```
Raft：
  不可能。
  因为：
  - Leader 必须获得过半投票才能选出
  - 每个 term 最多一个 Leader
  - 分区后少数派选不出 Leader（票数不够）
  - 少数派只能降级为 Follower
  → 数学上保证不会出现双主

ZAB (ZK)：
  同理。
  - Leader 必须获得过半投票
  - 少数派无法选出 Leader
  → 不会出现双主

Redis Sentinel：
  可能出现双主！
  因为：
  - 旧 Master 不需要投票维持身份
  - 旧 Master 只是"没人告诉它不是 Master 了"
  - 它继续以 Master 身份运行
  - 分区B的 Sentinel 选出新 Master
  → 两个 Master 同时存在
  → 数据分叉
```

### 十、本质区别总结

```
┌──────────────────────────────────────────────────────────┐
│                                                          │
│    Redis 的设计哲学：                                      │
│    "我是缓存，我要快，高可用是我努力做到的附加能力"           │
│                                                          │
│    → 复制是尽力而为（Best Effort）                         │
│    → 牺牲一致性换性能                                      │
│    → 用运维手段（min-replicas, WAIT）弥补                  │
│                                                          │
├──────────────────────────────────────────────────────────┤
│                                                          │
│    ZK/Raft 的设计哲学：                                    │
│    "我是协调服务/共识协议，一致性是我的生命线"                │
│                                                          │
│    → 复制是强约束（必须过半确认）                           │
│    → 牺牲性能换一致性                                      │
│    → 算法本身保证正确性                                    │
│                                                          │
├──────────────────────────────────────────────────────────┤
│                                                          │
│    类比：                                                 │
│                                                          │
│    Redis  ≈ 顺风快递：快，偶尔丢件                         │
│    ZK/Raft ≈ 高铁托运：慢一点，但每个包裹都有签收确认       │
│                                                          │
│    你的快递丢了，顺丰说"我尽力了"                           │
│    高铁托运丢了，它不可能丢（理论上）                       │
│                                                          │
└──────────────────────────────────────────────────────────┘
```

### 十一、选型建议

```
需要强一致性？
  ├── 是 → ZK / etcd(Raft) / Consul
  │         用于：分布式锁、选主、配置管理、服务注册
  │
  └── 否 → Redis
            用于：缓存、会话、排行榜、计数器、消息队列

需要 Redis 的性能 + 强一致性？
  ├── Redis + WAIT 命令（半同步，有性能代价）
  ├── Redis + 应用层校验（写后读验证）
  └── 考虑 TiKV（Raft + Redis协议兼容）
      或 Dragonfly、KeyDB 等替代方案

实际架构中常见组合：
  Redis（缓存/热数据） + ZK/etcd（协调/元数据）
  各司其职，互补短板
```

想继续深入哪个方向？比如 Raft 的 PreVote 和 CheckQuorum 机制，或者 ZK 的 Watch 机制，或者 Redis 7.x 对一致性的改进？
