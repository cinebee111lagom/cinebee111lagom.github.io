## 一、RDMA 网络——为什么它如此关键

### 1.1 传统网络 vs RDMA：数据路径的根本差异

传统 TCP/IP 通信中，一次网络收发的数据要经历这样的路径：

```
应用 buffer → 系统调用 → 内核协议栈 → 内核缓冲区 → 网卡驱动 → DMA → 网卡 → 线路
```

这条路径中至少存在 **两次内存拷贝**（用户态→内核态、内核态→网卡 DMA buffer）和 **两次上下文切换**（用户态↔内核态）。对于分布式训练中频繁的梯度同步操作，这些开销被放大到不可忽视的程度。

RDMA 的核心思想是 **"零拷贝、内核旁路"（Zero-Copy, Kernel Bypass）**：

```
应用 buffer → 网卡直接 DMA 读取 → 线路
```

网卡（RNIC, RDMA NIC）拥有自己的处理器和内存管理单元，能够直接解析应用层下发的 **工作请求（Work Request）**，通过 **虚拟地址翻译**（类似 CPU 的 MMU）直接访问用户态注册的内存区域，全程不经过内核。

### 1.2 RDMA 的核心抽象概念

理解 RDMA 需要掌握几个关键概念：

**Queue Pair (QP)：** 每个 RDMA 连接由一对队列组成——Send Queue（SQ）和 Receive Queue（RQ）。应用把工作请求投递到 SQ，完成通知出现在 Completion Queue（CQ）中。

```
┌──────────┐     ┌──────────┐
│ Send Queue│     │Recv Queue│
│  (SQ)     │     │  (RQ)    │
│ WR1       │     │ WR1      │
│ WR2       │     │ WR2      │
│ WR3       │     │          │
└─────┬─────┘     └────┬─────┘
      │                │
      ▼                ▼
   ┌─────────────────────┐
   │   RDMA 网卡 (RNIC)   │
   │   执行实际 DMA 操作    │
   └──────────┬──────────┘
              ▼
      ┌──────────────┐
      │ Completion Q  │
      │    (CQ)       │
      └──────────────┘
```

**Memory Registration (MR)：** 在 RDMA 操作之前，用户态内存必须先注册。内核会将这段虚拟内存 **Pin 住**（锁定物理页面，防止被 swap），并生成一个 **lkey/rkey**（本地/远程密钥），网卡凭此进行 DMA 地址翻译。注册操作本身有一定开销，所以在分布式训练框架中，通常预先注册一大块 memory region 作为缓冲池。

**RDMA 操作类型：**

| 操作 | 特点 | 对端 CPU 是否参与 |
|------|------|--------------------|
| **RDMA Write** | 本端直接写入对端内存 | 不参与（单边操作） |
| **RDMA Read** | 本端直接读取对端内存 | 不参与（单边操作） |
| **Send/Receive** | 本端发送，对端需预先投递 Recv WR | 参与（双边操作） |

在集合通信中，**RDMA Write** 最为常用——因为发送方不需要等接收方准备好，直接写入对方预注册的 buffer 即可。

### 1.3 三种实现的具体差异与选型

**InfiniBand（IB）：**

- 专用协议栈，从物理层到传输层都是独立设计的
- 子网管理器（Subnet Manager, SM）负责路径计算和 LID 分配
- 支持 **可靠连接（RC）、不可靠数据报（UD）、可靠数据报（RD）** 等多种 QP 类型
- 交换延迟极低（~100ns），但整套基础设施成本高
- NVIDIA 的 ConnectX-7 网卡 + Quantum-2 交换机可提供 NDR 400 Gbps

**RoCEv2：**

- 把 IB 的传输层封装在 UDP/IP 之上，可以在标准以太网交换机上跑
- 必须依赖 **无损网络** 才能稳定工作——这就是 PFC 的由来
- RoCEv2 的一个经典问题是 **"PFC 死锁"**：多个优先级队列相互等待对方释放 buffer，导致网络冻结
- 实际部署中需要在交换机上精心配置：ECN 标记阈值、PFC 水线、Buffer 分配

```
RoCEv2 协议栈:
┌─────────────┐
│  IB Transport│  ← 承载 RDMA 操作
├─────────────┤
│    UDP       │  ← 目标端口 4791
├─────────────┤
│    IP        │  ← 可跨三层路由
├─────────────┤
│  Ethernet    │  ← 标准以太网
└─────────────┘
```

**iWARP：**

- 基于 TCP，天然具备拥塞控制和重传能力，不需要无损网络
- 但 TCP 的拥塞控制（如拥塞窗口、慢启动）会引入不确定的延迟抖动
- 单连接性能不如 IB/RoCE，但部署简单，适合中小规模集群
- 在超大规模训练场景中几乎不被采用

### 1.4 RDMA 运维中的深层问题

**PFC 风暴（PFC Storm）：** 当网络中某条链路短暂拥塞时，PFC pause 帧会沿反压路径逐级传递。如果上游也处于高水位，pause 会扩散到整个网络拓扑，形成全局性的吞吐量坍塌。

**ECN 调参的两难：**
- ECN 标记阈值设得太低 → 频繁标记，吞吐量下降
- 设得太高 → 来不及标记，出现丢包，RDMA 重传代价很大

**实际排障流程：**

```bash
# 1. 验证 RDMA 基础连通性
ibping -S          # 服务端
ibping -L <lid>    # 客户端

# 2. 测试带宽和延迟
ib_write_bw -d mlx5_0 -a --report_gbits    # 带宽测试
ib_read_lat -d mlx5_0 -a                    # 延迟测试

# 3. 检查网卡计数器（关键！）
cat /sys/class/infiniband/mlx5_0/ports/1/counters/port_rcv_errors
cat /sys/class/infiniband/mlx5_0/ports/1/counters/port_xmit_discards

# 4. 检查 PFC 计数器
ethtool -S ens1f0 | grep pfc
ethtool -S ens1f0 | grep pause

# 5. 检查 ECN 标记情况
ethtool -S ens1f0 | grep ecn
```

## 二、NCCL 深入机制

### 2.1 NCCL 的架构设计

NCCL 本质上是一个 **单进程多线程** 的通信库。每个 GPU 对应一个 NCCL 线程，这些线程通过共享内存和同步原语协调工作。

```
┌─────────────────────────────────────────────┐
│                 用户进程                      │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐        │
│  │ GPU 0   │ │ GPU 1   │ │ GPU 2   │ ...    │
│  │ Rank 0  │ │ Rank 1  │ │ Rank 2  │        │
│  └────┬────┘ └────┬────┘ └────┬────┘        │
│       │           │           │              │
│  ┌────┴───────────┴───────────┴────┐        │
│  │        NCCL Communicator         │        │
│  │  ┌──────┐  ┌──────┐  ┌──────┐   │        │
│  │  │Ch 0  │  │Ch 1  │  │Ch 2  │   │        │
│  │  │Proxy │  │Proxy │  │Proxy │   │        │
│  │  │Thread│  │Thread│  │Thread│   │        │
│  │  └──────┘  └──────┘  └──────┘   │        │
│  └──────────────────────────────────┘        │
└─────────────────────────────────────────────┘
```

**Proxy Thread：** NCCL 为每个通信通道（Channel）创建一个代理线程，负责实际的网络 I/O。Proxy 线程从 GPU 的环形缓冲区（Ring Buffer）中取出数据，通过 RDMA 操作发送到远端。这种设计让计算 kernel 和通信可以 **重叠（overlap）**。

### 2.2 Ring AllReduce 的精细流程

Ring AllReduce 是理解集合通信的基础。假设有 N 个 GPU，每个 GPU 持有大小为 D 的梯度数据。

**阶段一：ReduceScatter（N-1 轮）**

```
将 D 等分为 N 块，每轮传递一块：

GPU 0: [块0][块1][块2][块3]  ──块3──→  GPU 1
GPU 1: [块0][块1][块2][块3]  ──块3──→  GPU 2
GPU 2: [块0][块1][块2][块3]  ──块3──→  GPU 3
GPU 3: [块0][块1][块2][块3]  ──块3──→  GPU 0

第 i 轮中，GPU j 向 GPU (j+1) mod N 发送第 (j-i) mod N 块
接收方将收到的块与本地对应块做累加
```

经过 N-1 轮后，每块 GPU 持有 **一个完整块** 的聚合结果。

**阶段二：AllGather（N-1 轮）**

类似地，各 GPU 将自己聚合好的块沿环传递，不做累加，只做覆盖。经过 N-1 轮后，每块 GPU 都有完整的聚合结果。

**通信量分析：**
- 每个 GPU 发送和接收的数据量都是 `(N-1)/N × D`
- 总通信量 = `2 × (N-1)/N × D`，与 GPU 数量 N 无关
- 这就是 Ring AllReduce 的 **带宽最优性**

### 2.3 NCCL 的拓扑探测与路径选择

NCCL 在初始化 `ncclCommInitRank` 时会执行拓扑探测：

```c
// NCCL 内部拓扑发现的大致逻辑：
// 1. 读取 NVIDIA GPU 拓扑（nvidia-smi topo -m）
//    - NVLink 连接：最高优先级，带宽 900 GB/s（H100）
//    - PCIe 连接：中等优先级，带宽 64 GB/s（PCIe 5.0 x16）
// 2. 读取网络拓扑
//    - /sys/class/infiniband/ 下的设备信息
//    - 每张网卡的 NUMA affinity
// 3. 构建拓扑图，计算最优通信树/环
```

**关键决策逻辑：**

```
同一节点内：
  ├── 2 GPU 通过 NVLink 直连 → 直接 NVLink P2P
  ├── 4 GPU 同一 PCIe switch → 通过 PCIe P2P  
  └── 8 GPU 跨 PCIe switch → 可能通过共享内存 + NVLink 混合

跨节点：
  ├── 网卡和 GPU 在同一 NUMA node → 最优路径
  └── 网卡和 GPU 在不同 NUMA node → 跨 NUMA 内存访问，性能下降
```

**NCCL 的通信算法选择：**

NCCL 不只用 Ring，还支持多种算法：

| 算法 | 适用场景 | 特点 |
|------|---------|------|
| **Ring** | 节点数多、带宽敏感 | 带宽最优，延迟随节点数线性增长 |
| **Tree** | 延迟敏感的小规模操作 | 延迟 O(logN)，带宽不如 Ring |
| **CollNet** | 跨节点用网络交换机硬件做 Reduce | 需要 SHARP 支持 |
| **NVLS** | 节点内 NVLink Switch | H100 NVSwitch 的 NVLink SHARP |

可以通过环境变量调优：
```bash
# 强制使用 Tree 算法
NCCL_ALGO=Tree

# 强制使用 Ring 算法  
NCCL_ALGO=Ring

# 使用 NVLink SHARP（仅 H100）
NCCL_ALGO=NVLSTree

# 查看 NCCL 选择了什么算法和拓扑
NCCL_DEBUG=INFO NCCL_DEBUG_SUBSYS=GRAPH python train.py
```

### 2.4 NCCL 的分层通信模型（Channels + Rings/Trees）

NCCL 在一个 Communicator 内部不会只建一个 Ring/Tree，而是建立 **多个 Channel**，每个 Channel 有自己独立的 Ring 或 Tree：

```
Channel 0: GPU0 → GPU1 → GPU2 → GPU3 → GPU0
Channel 1: GPU0 → GPU2 → GPU3 → GPU1 → GPU0
Channel 2: GPU0 → GPU3 → GPU1 → GPU2 → GPU0
...
```

不同 Channel 使用不同的 Ring 顺序，目的是 **充分利用多条网络路径**，避免单一路径成为瓶颈。NCCL 默认使用 32 个 Channel（`NCCL_NCHANNELS_PER_NET_PEER`）。

### 2.5 常见错误的深层原因与排查

**Bus Error / Shared Memory 不足：**

```bash
# 查看当前 /dev/shm 使用情况
df -h /dev/shm

# NCCL 需要的共享内存大小取决于 GPU 数量和 buffer 配置
# 默认 /dev/shm 大小通常是物理内存的 50%
# Docker 容器中默认只有 64MB，必须显式挂载：

docker run --shm-size=1g ...
# 或
docker run --ipc=host ...
```

NCCL 使用 `/dev/shm` 存放：
- 进程间的同步信号量
- Ring Buffer 的元数据
- Proxy 线程间的通信结构

当节点内 GPU 数量增加（如 8 卡），每对 GPU 之间都需要共享内存通道，空间需求迅速增长。

**Timeout 的典型模式：**

```bash
# NCCL 默认超时环境变量
NCCL_TIMEOUT=1800  # 30 分钟

# 常见 timeout 原因排序：
# 1. 防火墙阻断 RDMA 流量
iptables -L -n | grep 4791    # RoCEv2 的 UDP 端口

# 2. 某张网卡/某条链路故障
dmesg | grep -i "mlx\|infiniband\|error"

# 3. PFC 死锁导致网络冻结
# 此时所有 GPU 都在等待网络 I/O 完成

# 4. NCCL 版本与 CUDA/驱动不兼容
# 检查兼容矩阵：docs.nvidia.com/deeplearning/nccl/
```

**性能不达标的排查路径：**

```
性能不达标
├── 1. 确认拓扑识别正确
│   └── NCCL_DEBUG=INFO 查看 NET/IB 设备选择
├── 2. 确认走了 RDMA 而不是 TCP fallback
│   └── 搜索 "NET/Socket" vs "NET/IB" 
├── 3. 确认 NVLink 没有降速
│   └── nvidia-smi nvlink -s 查看 NVLink 状态
├── 4. 确认 PCIe 带宽正常
│   └── lspci -vvv 查看 LnkSta（实际协商速率）
├── 5. 确认 GPUDirect RDMA 开启
│   └── GPU 和网卡需在同一 NUMA，peer_mem 模块加载
├── 6. 确认 NVLink 拓扑没走 QPI/UPI 跨 socket
│   └── nvidia-smi topo -m 查看 GPU-to-GPU 路径
└── 7. Profile
    └── nsight systems 查看通信时间占比
```

### 2.6 GPUDirect RDMA：关键的性能优化

普通 RDMA 需要这样传输 GPU 数据：

```
GPU 显存 → (PCIe) → CPU 内存 → (DMA) → 网卡 → 线路
```

**GPUDirect RDMA（GDR）** 允许网卡直接 DMA 读写 GPU 显存：

```
GPU 显存 → (PCIe) → 网卡 → 线路
```

省去了一次 CPU 内存中转，延迟降低约 30-50%，带宽提升约 10-20%。

```bash
# 检查 GDR 是否可用
lsmod | grep nv_peer_mem    # 或 nvidia-peermem（新版驱动）

# 如果没有加载：
modprobe nv_peer_mem

# NCCL 中默认开启 GDR，可以通过以下方式确认：
NCCL_DEBUG=INFO  # 搜索 "NET/IB : Using GPUDirect"
```

## 三、实际大规模训练中的通信优化策略

### 3.1 梯度分桶（Gradient Bucketing）

PyTorch DDP 不会每个参数单独做 AllReduce，而是将梯度 **按大小分桶**（默认 25MB），逐桶触发通信。这样可以让小梯度合并为大块传输，提高网络利用率。

```python
# PyTorch DDP 相关配置
model = DistributedDataParallel(
    model,
    bucket_cap_mb=25,           # 桶大小
    gradient_as_bucket_view=True,  # 避免额外拷贝
    static_graph=True,           # 图结构不变时可优化
)
```

### 3.2 计算-通信重叠

```
时间线：
GPU 0: [Layer_N 计算] [Layer_N-1 通信 ∥ Layer_N-2 计算] [Layer_N-2 通信 ∥ Layer_N-3 计算]
                                              ↑
                                    前一层梯度的 AllReduce 
                                    和下一层的前向计算并行
```

这要求框架能反向传播到某一层时就立即触发该层梯度的通信，而不是等所有梯度都算完。PyTorch DDP 的 `static_graph=True` 配合 `find_unused_parameters=False` 可以实现这种流水线。

### 3.3 多网卡绑定与 Rail-Optimized 拓扑

在 H100 集群中，典型配置是 **8 GPU + 8 网卡**，每张网卡通过 PCIe 直连一张 GPU（避免跨 NUMA 路径）：

```
Node:
  GPU0 ── PCIe ── NIC0 ── IB ── Switch Port 0
  GPU1 ── PCIe ── NIC1 ── IB ── Switch Port 1
  GPU2 ── PCIe ── NIC2 ── IB ── Switch Port 2
  ...
  GPU7 ── PCIe ── NIC7 ── IB ── Switch Port 7
```

NCCL 的 Rail-Optimized 算法让每张 GPU 只通过自己直连的网卡通信，避免跨 PCIe 路径。环境变量：

```bash
NCCL_NET_GDR_LEVEL=5       # 设置 GDR 的 NUMA 级别
NCCL_CROSS_NIC=0            # 禁止跨网卡，使用 rail-optimized
NCCL_SOCKET_NTHREADS=1      # 每个 socket 连接一个线程
NCCL_NSOCKS_PERTHREAD=1
```

---

这些底层细节共同决定了分布式训练的实际吞吐量。在万亿参数模型的训练中，通信效率哪怕提升 5%，在数周的训练周期里也意味着节省数天的 GPU 时间和对应的电力成本。
