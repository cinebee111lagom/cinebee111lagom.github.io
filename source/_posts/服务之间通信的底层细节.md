## 一、从一次 HTTP 调用说起

当 Order Service 调用 User Service 获取用户信息时，表面上只是一行 `restTemplate.getForEntity()`，但底层经历了一个漫长的过程：

```
Order Service Pod (10.244.1.5)
      │
      │ ① DNS 解析 / 服务发现
      │ ② 建立 TCP 连接（三次握手）
      │ ③ TLS 握手（如果有 HTTPS）
      │ ④ 序列化请求对象 → 二进制/JSON
      │ ⑤ 构造 HTTP 请求报文
      │ ⑥ 内核协议栈封装 → TCP Segment → IP Packet → Frame
      │ ⑦ 网卡发送（经 CNI 插件路由）
      │
      ▼
User Service Pod (10.244.2.8)
      │
      │ ⑧ 网卡接收 → 内核协议栈解封
      │ ⑨ 内核 TCP 栈将数据放入 Socket 接收缓冲区
      │ ⑩ 应用层 epoll/select 唤醒线程
      │ ⑪ 读取字节流 → 反序列化为 HTTP 请求
      │ ⑫ DispatcherServlet 路由到 Controller
      │ ⑬ 执行业务逻辑 → 返回响应
      │ ⑭ 响应原路返回
```

## 二、每一层的底层细节

### 第①层：服务发现与 DNS 解析

**方式一：Nacos 客户端服务发现**

```java
// Nacos 客户端内部做的事：
// 1. 启动时向 Nacos Server 发送注册请求（HTTP POST /nacos/v1/ns/instance）
// 2. 定期发送心跳（每 5 秒 PUT /nacos/v1/ns/instance/beat）
// 3. 服务发现时拉取实例列表（HTTP GET /nacos/v1/ns/instance/list）
// 4. 本地缓存实例列表 + UDP 推送变更

// Ribbon/Spring Cloud LoadBalancer 从 Nacos 拿到的实例列表：
List<ServiceInstance> instances = discoveryClient.getInstances("user-service");
// 返回：
// [Instance{ip='10.244.2.8', port=8080, weight=1.0, healthy=true},
//  Instance{ip='10.244.2.9', port=8080, weight=1.0, healthy=true},
//  Instance{ip='10.244.3.5', port=8080, weight=1.0, healthy=true}]
```

**Nacos 推送机制的底层：**

```
服务实例变更
    │
    ▼
Nacos Server 内存中 InstanceList 发生变化
    │
    ├──→ 方式一：UDP Push（主动推送）
    │    Nacos Server 向所有订阅该服务的客户端发送 UDP 包
    │    客户端收到后更新本地缓存
    │    缺点：UDP 不可靠，可能丢失
    │
    ├──→ 方式二：Long Polling（长轮询，兜底）
    │    客户端发起 HTTP 请求，服务端 hold 住连接 30 秒
    │    如果 30 秒内有变更 → 立即响应
    │    如果 30 秒内无变更 → 超时返回空，客户端重新发起
    │
    └──→ 方式三：本地文件缓存（断线恢复）
         ~/.nacos/naming/ 下有实例列表的本地快照
         如果 Nacos Server 不可达，使用本地缓存兜底
```

```java
// Nacos 客户端 Long Polling 的核心代码（简化）
public class NamingProxy {
    public ServiceInfo getServiceInfo(String serviceName, String clusters) {
        // 先查本地缓存
        ServiceInfo serviceInfo = serviceInfoMap.get(serviceName + "@" + clusters);
        if (serviceInfo != null) {
            return serviceInfo;
        }
        // 缓存没有，向 Nacos Server 发起长轮询
        String result = reqAPI(UtilAndComs.nacosUrlBase, params);
        return JSON.parseObject(result, ServiceInfo.class);
    }
}
```

**方式二：K8s DNS 解析**

```
Order Service 调用 http://user-service:8080/api/user/1
                          │
                          ▼
             Pod 内 /etc/resolv.conf
             nameserver 10.96.0.10    ← CoreDNS 的 ClusterIP
             search microservice.svc.cluster.local svc.cluster.local
                          │
                          ▼
         内核 DNS 解析器构造 FQDN:
         user-service.microservice.svc.cluster.local
                          │
                          ▼
         发送 DNS 查询到 CoreDNS (UDP 53)
                          │
                          ▼
         CoreDNS 查询 kube-apiserver 的 Service/Endpoints
         返回 ClusterIP: 10.97.15.200
                          │
                          ▼
         kube-proxy 已经在每个节点的 iptables/IPVS 中
         设置了转发规则：
         10.97.15.200:8080 → DNAT → Pod IP (轮询/随机)
```

**iptables 规则示例（kube-proxy 维护）：**

```bash
# 查看 kube-proxy 创建的 iptables 规则
iptables -t nat -L KUBE-SERVICES -n

# user-service 的 ClusterIP 10.97.15.200 被 DNAT 到后端 Pod
-A KUBE-SERVICES -d 10.97.15.200/32 -p tcp -m tcp --dport 8080 \
  -j KUBE-SVC-XXXXX

# 后端 Pod 列表（概率轮询）
-A KUBE-SVC-XXXXX -m statistic --mode random --probability 0.3333 \
  -j KUBE-SEP-AAA  # → DNAT to 10.244.2.8:8080
-A KUBE-SVC-XXXXX -m statistic --mode random --probability 0.5000 \
  -j KUBE-SEP-BBB  # → DNAT to 10.244.2.9:8080
-A KUBE-SVC-XXXXX \
  -j KUBE-SEP-CCC  # → DNAT to 10.244.3.5:8080
```

### 第②层：TCP 连接建立

当确定目标 IP:Port 后，内核开始建立 TCP 连接：

```
Order Service Pod (10.244.1.5)          User Service Pod (10.244.2.8)
        │                                        │
        │──── SYN seq=1000 ──────────────────→   │  第一次握手
        │                                        │
        │←─── SYN+ACK seq=2000, ack=1001 ─────  │  第二次握手
        │                                        │
        │──── ACK ack=2001 ──────────────────→   │  第三次握手
        │                                        │
        │         连接建立完成（ESTABLISHED）        │
```

**Java 层面，这个过程发生在：**

```java
// RestTemplate / OpenFeign 底层使用 HttpClient

// Apache HttpClient 默认行为：
CloseableHttpClient httpClient = HttpClients.custom()
    .setMaxConnTotal(200)           // 总连接池大小
    .setMaxConnPerRoute(50)         // 每个目标 host:port 最大连接数
    .setConnectionTimeToLive(60, TimeUnit.SECONDS)  // 连接最大存活时间
    .setDefaultRequestConfig(RequestConfig.custom()
        .setConnectTimeout(5000)    // TCP 连接超时（SYN 等待时间）
        .setSocketTimeout(30000)    // 读超时（等待响应数据的时间）
        .setConnectionRequestTimeout(3000)  // 从连接池获取连接的超时
        .build())
    .build();

// OKHttp 默认行为（Spring Boot 3 默认 HTTP 客户端）：
OkHttpClient client = new OkHttpClient.Builder()
    .connectTimeout(10, TimeUnit.SECONDS)
    .readTimeout(30, TimeUnit.SECONDS)
    .connectionPool(new ConnectionPool(5, 5, TimeUnit.MINUTES))
    .build();
```

**内核级别的 TCP 连接细节：**

```bash
# 查看 Pod 内的 TCP 连接状态
# 进入容器
kubectl exec -it order-service-pod -- sh

# 查看所有 TCP 连接
cat /proc/net/tcp
#  sl  local_address rem_address   st tx_queue rx_queue ...
#   0: 0501F40A:C2A0 0802F40A:1F90  01 00000000:00000000 ...
#       ↑ 10.244.1.5:49824    ↑ 10.244.2.8:8080   ESTABLISHED

# 查看 TCP 统计
ss -tnp  # 类似 netstat，但更快
# State   Recv-Q  Send-Q  Local Address:Port  Peer Address:Port
# ESTAB   0       0       10.244.1.5:49824     10.244.2.8:8080
```

**TCP 内核参数调优（K8s 中通过 initContainer 或 sysctl）：**

```yaml
# 在 Pod Spec 中设置内核参数
spec:
  securityContext:
    sysctls:
      - name: net.core.somaxconn
        value: "1024"          # TCP 连接队列长度
      - name: net.ipv4.tcp_max_syn_backlog
        value: "1024"          # SYN 队列长度
      - name: net.ipv4.tcp_tw_reuse
        value: "1"             # 允许复用 TIME_WAIT 连接
      - name: net.ipv4.tcp_fin_timeout
        value: "30"            # FIN_WAIT2 超时时间
      - name: net.core.netdev_max_backlog
        value: "2000"          # 网卡接收队列长度
```

**TCP 三次握手在 Java 中的体现：**

```java
// 当 HttpClient 发起新连接时，底层调用链：
// Java Socket → OS connect() 系统调用 → 内核 TCP 协议栈

// 从 JVM 到内核的调用路径：
java.net.Socket.connect(address, timeout)
  → sun.nio.ch.SocketChannelImpl.connect()
    → Native Linux connect(fd, sockaddr, addrlen)   // JNI 调用
      → 内核 tcp_v4_connect()
        → 发送 SYN 包
        → 等待 SYN+ACK
        → 发送 ACK
        → 连接进入 ESTABLISHED 状态
```

### 第③层：TLS 握手（HTTPS 场景）

如果服务间使用 mTLS（双向 TLS，Service Mesh 中常见）：

```
Client                                      Server
  │                                           │
  │── ClientHello (TLS版本、加密套件列表) ───→  │
  │                                           │
  │←── ServerHello (选定加密套件) ───────────  │
  │←── Certificate (服务端证书) ─────────────  │
  │←── CertificateRequest (要求客户端证书) ──  │
  │←── ServerHelloDone ─────────────────────  │
  │                                           │
  │── Certificate (客户端证书) ──────────────→ │
  │── ClientKeyExchange (预主密钥) ─────────→ │
  │── CertificateVerify (签名证明) ─────────→ │
  │── [ChangeCipherSpec] ───────────────────→ │
  │── Finished (加密验证) ──────────────────→ │
  │                                           │
  │←── [ChangeCipherSpec] ─────────────────  │
  │←── Finished (加密验证) ────────────────  │
  │                                           │
  │       TLS 握手完成，后续数据加密传输        │
```

**Java 中 TLS 的底层实现：**

```java
// Java 的 SSL/TLS 实现在 JSSE (Java Secure Socket Extension) 中
SSLContext context = SSLContext.getInstance("TLSv1.3");

// 加载信任库和服务端证书
KeyStore trustStore = KeyStore.getInstance("PKCS12");
trustStore.load(new FileInputStream("truststore.p12"), password.toCharArray());

KeyManagerFactory kmf = KeyManagerFactory.getInstance("SunX509");
kmf.init(keyStore, clientKeyPassword);

TrustManagerFactory tmf = TrustManagerFactory.getInstance("SunX509");
tmf.init(trustStore);

context.init(kmf.getKeyManagers(), tmf.getTrustManagers(), new SecureRandom());

// 在 HTTPS 连接中使用
HttpsURLConnection conn = (HttpsURLConnection) url.openConnection();
conn.setSSLSocketFactory(context.getSocketFactory());

// TLS 握手发生在 conn.connect() 时
// 底层调用链：
// SSLSocketImpl.startHandshake()
//   → TLS 1.3: 完成 1-RTT 握手（比 TLS 1.2 少一个往返）
//   → 生成 Session Ticket 用于后续 0-RTT 恢复
```

### 第④层：序列化与反序列化

这是影响通信性能的关键层。请求对象必须转换为字节流才能发送。

```
Java Object → 序列化 → byte[] → 网络传输 → byte[] → 反序列化 → Java Object
```

**常见序列化方案对比：**

```java
// ========== 1. JSON（Spring 默认） ==========
// 使用 Jackson
ObjectMapper mapper = new ObjectMapper();

UserDTO user = new UserDTO(1L, "张三", "zhangsan@example.com");
byte[] json = mapper.writeValueAsBytes(user);
// {"id":1,"name":"张三","email":"zhangsan@example.com"}
// 大小：~60 bytes
// 速度：中等

// ========== 2. Protobuf（gRPC 使用） ==========
// 需要 .proto 文件定义
// message UserDTO {
//   int64 id = 1;
//   string name = 2;
//   string email = 3;
// }

UserDTO user = UserDTO.newBuilder()
    .setId(1)
    .setName("张三")
    .setEmail("zhangsan@example.com")
    .build();
byte[] protobuf = user.toByteArray();
// 二进制编码，不可读
// 大小：~25 bytes
// 速度：非常快

// ========== 3. Hessian（Dubbo 默认） ==========
Hessian2Output output = new Hessian2Output(baos);
output.writeObject(user);
output.flush();
// 大小：~40 bytes
// 速度：较快

// ========== 4. Kryo（高性能场景） ==========
Kryo kryo = new Kryo();
kryo.register(UserDTO.class);
Output output = new Output(new ByteArrayOutputStream());
kryo.writeObject(output, user);
output.close();
// 大小：~30 bytes
// 速度：最快
```

**Jackson JSON 序列化的底层细节：**

```java
// Jackson 序列化一个 UserDTO 对象的过程：
ObjectMapper mapper = new ObjectMapper();

// 1. 查找/创建 Serializer
//    - 从 ConcurrentHashMap<Class, JsonSerializer> 缓存中查找
//    - 没有则通过 AnnotationIntrospector 扫描类的注解和字段
//    - 创建 BeanSerializer

// 2. 创建 JsonGenerator（底层是 UTF-8 编码器）
//    - 使用 OutputStreamBasedJsonGenerator
//    - 内部维护一个 byte[] 缓冲区（默认 8KB）

// 3. 遍历 Bean 的属性，逐个写入
//    - 反射获取 getter 方法（首次后缓存 Method 对象）
//    - getter.invoke(obj) 获取值
//    - 字符串做 UTF-8 编码（ASCII 字符 1 byte，中文 3 bytes）
//    - 写入 JSON token: {"id":1,"name":"\u5f20\u4e09",...}

String json = mapper.writeValueAsString(user);
// 内部调用链：
// ObjectMapper.writeValueAsString()
//   → _configAndWriteValue()
//     → _serializerProvider().findValueSerializer(UserDTO.class)
//     → serializer.serialize(user, jsonGenerator, serializerProvider)
//       → BeanSerializer.serialize()
//         → 遍历 BeanPropertyWriter[]
//           → writer.get(user)    // 反射调用 getter
//           → jsonGenerator.writeFieldName("id")
//           → jsonGenerator.writeNumber(1)
//           → jsonGenerator.writeFieldName("name")
//           → jsonGenerator.writeString("张三")
```

**Protobuf 编码的底层（Varint 编码）：**

```
以 id=300 为例：
  300 的二进制 = 100101100
  Varint 编码：每个字节的最高位为标记位
    字节1: 10101100  (最高位1 = 后续还有字节)
    字节2: 00000010  (最高位0 = 最后一个字节)
  解码时拼接：00000010 0101100 = 100101100 = 300

  JSON 表示 "300" 需要 3 bytes
  Protobuf 表示 300 只需 2 bytes
```

### 第⑤⑥层：HTTP 报文构造与内核协议栈封装

**HTTP 请求报文的构造：**

```
POST /api/user/getById HTTP/1.1\r\n          ← 请求行
Host: user-service:8080\r\n                    ← 请求头
Content-Type: application/json\r\n
Content-Length: 60\r\n
Authorization: Bearer eyJhbGci...\r\n
X-Request-Id: a1b2c3d4\r\n                    ← 链路追踪 ID
X-Trace-Id: span-xyz-789\r\n
\r\n                                            ← 空行（头部结束）
{"id":1,"name":"张三","email":"zhangsan@..."}  ← Body
```

**Java 中构造 HTTP 请求的底层：**

```java
// Spring 的 RestTemplate → Interceptor Chain → HttpClient

// 拦截器链的执行顺序：
ClientHttpRequestInterceptor chain = new ArrayList<>();
chain.add(new MicrometerHttpRequestInterceptor());  // 指标采集
chain.add(new TracingHttpRequestInterceptor());      // 链路追踪注入
chain.add(new LoadBalancerInterceptor());            // 负载均衡选择实例
chain.add(new RetryInterceptor());                   // 重试逻辑
chain.add(new CircuitBreakerInterceptor());          // 熔断判断

// 最终由 HttpClient 写入 Socket：
// OutputStream os = socket.getOutputStream();
// os.write(httpRequestBytes);  → 系统调用 write(fd, buf, len)
```

**内核协议栈的封装过程：**

```
应用层数据 (HTTP 报文，假设 200 bytes)
      │
      ▼
┌─────────────────────────────────────────┐
│ TCP 层（内核 tcp_sendmsg）              │
│                                         │
│ 添加 TCP 头部 (20 bytes)                │
│ ├── Source Port: 49824                  │
│ ├── Dest Port: 8080                     │
│ ├── Seq Number: 12345                   │
│ ├── Ack Number: 67890                   │
│ ├── Window Size: 65535                  │
│ └── Checksum                           │
│                                         │
│ MSS 分片（如果数据 > MSS 1460 bytes）    │
│ Nagle 算法（小包合并）                    │
│ 拥塞控制（cwnd/ssthresh）               │
│ TCP 缓冲区 → 写入发送队列                │
└────────────────┬────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────┐
│ IP 层（内核 ip_output）                 │
│                                         │
│ 添加 IP 头部 (20 bytes)                 │
│ ├── Version: 4                          │
│ ├── TTL: 64                             │
│ ├── Protocol: TCP (6)                   │
│ ├── Source IP: 10.244.1.5               │
│ └── Dest IP: 10.244.2.8                 │
│                                         │
│ 路由查找（ip_route_output）              │
│ → 查 FIB 路由表                         │
│ → 确定下一跳和出接口                     │
└────────────────┬────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────┐
│ Netfilter/iptables（K8s kube-proxy）    │
│                                         │
│ PREROUTING → FORWARD → POSTROUTING      │
│ DNAT 规则（如果经过 Service）             │
│                                         │
│ 但 Pod 直连 Pod 时可能跳过 DNAT          │
└────────────────┬────────────────────────┘
                 │
                 ▼
┌─────────────────────────────────────────┐
│ 二层（ARP + 封装以太网帧）               │
│                                         │
│ ARP 解析下一跳 MAC 地址：                │
│ 10.244.2.8 是同子网还是需要网关？         │
│                                         │
│ K8s Pod 网络通常是扁平的：               │
│ 所有 Pod 在同一个大子网（如 10.244.0.0/16）│
│ CNI 插件负责跨节点路由                    │
│                                         │
│ 添加以太网帧头 (14 bytes)               │
│ ├── Dest MAC: 目标 Pod 或网关 MAC        │
│ ├── Source MAC: 本机网卡 MAC             │
│ └── EtherType: 0x0800 (IPv4)           │
└────────────────┬────────────────────────┘
                 │
                 ▼
         网卡发送（DMA → 物理线路）
```

### 第⑦层：K8s 网络（CNI 插件）

**Flannel VXLAN 模式（跨节点通信）：**

```
发送方节点 Node A (192.168.1.10)           接收方节点 Node B (192.168.1.20)
┌──────────────────────┐                  ┌──────────────────────┐
│  Pod A               │                  │  Pod B               │
│  10.244.1.5          │                  │  10.244.2.8          │
│  ┌────────────────┐  │                  │  ┌────────────────┐  │
│  │ eth0 (veth)    │  │                  │  │ eth0 (veth)    │  │
│  └───────┬────────┘  │                  │  └───────▲────────┘  │
│          │           │                  │          │           │
│  ┌───────▼────────┐  │                  │  ┌───────┴────────┐  │
│  │ cni0 (bridge)  │  │                  │  │ cni0 (bridge)  │  │
│  └───────┬────────┘  │                  │  └───────▲────────┘  │
│          │           │                  │          │           │
│  ┌───────▼────────┐  │                  │  ┌───────┴────────┐  │
│  │ flannel.1(VXLAN)│ │   VXLAN 隧道     │  │ flannel.1(VXLAN)│ │
│  │ VNI=1          │──┼──────────────────┼──│ VNI=1          │  │
│  └───────┬────────┘  │                  │  └───────▲────────┘  │
│          │           │                  │          │           │
│  ┌───────▼────────┐  │                  │  ┌───────┴────────┐  │
│  │ eth0 (物理网卡) │  │                  │  │ eth0 (物理网卡) │  │
│  │192.168.1.10    │──┼────────物理网络──┼──│192.168.1.20    │  │
│  └────────────────┘  │                  │  └────────────────┘  │
└──────────────────────┘                  └──────────────────────┘
```

**VXLAN 封装过程：**

```
原始以太网帧:
  [Dest MAC][Src MAC][IP Packet...]
       │
       ▼  VXLAN 封装（flannel.1 虚拟接口）
  [外层 Ethernet Header]
  [外层 IP Header (192.168.1.10 → 192.168.1.20)]
  [UDP Header (Src Port: 随机, Dst Port: 8472)]
  [VXLAN Header (VNI=1)]
  [原始以太网帧] ← 内层，Pod 间的通信
  
  总开销：50 bytes（外层头 + VXLAN 头）
  MTU 影响：物理 MTU 1500 → 内层 MTU 只能 1450
```

### 第第⑧⑨⑩层：接收端内核处理

```
网卡收到数据包（DMA 写入 Ring Buffer）
      │
      ▼
硬件中断 → NAPI（中断 + 轮询混合模式）
      │
      ▼
netif_receive_skb() → 协议栈分发
      │
      ├──→ ARP 处理（如果是 ARP 包）
      │
      ▼
IP 层：ip_rcv()
  → 校验和验证
  → 路由判断（本机接收 or 转发）
  → Netfilter PREROUTING
  → 送入 TCP 层
      │
      ▼
TCP 层：tcp_v4_rcv()
  → 查找 Socket（根据 src/dst IP + Port 四元组）
  → tcp_rcv_established()（已建立连接的处理）
  → 校验 TCP 序列号、校验和
  → 数据放入 Socket 接收缓冲区（sk_buff → sk_receive_queue）
  → 唤醒等待在 recv()/read() 上的应用线程
      │
      ▼
应用层（Java NIO）：
  → Selector.select() 返回（epoll_wait 系统调用被唤醒）
  → SocketChannel.read(ByteBuffer)（read 系统调用）
  → 内核从 Socket 接收缓冲区拷贝数据到用户空间
```

**Java NIO 在这个过程中的角色：**

```java
// Spring Boot 内嵌 Tomcat 的请求处理模型
// （Reactor 模式 + 线程池）

// 1. Acceptor 线程（通常 1 个）
//    监听 ServerSocketChannel，accept 新连接
//    → 系统调用 accept(fd) → 返回新 Socket 的 fd

// 2. Poller 线程（通常 1-2 个）
//    使用 Selector (epoll) 监听所有连接的可读事件
//    → epoll_wait() 阻塞等待
//    → 当某个连接有数据到达，内核返回该 fd

// 3. Executor 线程池（默认 maxThreads=200）
//    从 Poller 拿到就绪的连接，执行 HTTP 解析和业务逻辑
//    → SocketChannel.read(buffer)
//    → Http11Processor 解析 HTTP 报文
//    → CoyoteAdapter 适配为 Servlet 请求
//    → DispatcherServlet 路由

// Tomcat NIO 的核心代码结构：
public class NioEndpoint {
    private Selector selector;  // epoll 实例
    private Executor executor;  // 业务线程池
    
    // Poller 线程
    class Poller implements Runnable {
        public void run() {
            while (running) {
                // 阻塞等待事件（Linux 上就是 epoll_wait）
                selector.select(1000);
                Iterator<SelectionKey> it = selector.selectedKeys().iterator();
                while (it.hasNext()) {
                    SelectionKey key = it.next();
                    if (key.isReadable()) {
                        // 将就绪的连接提交给线程池处理
                        executor.execute(new SocketProcessor(key));
                    }
                    it.remove();
                }
            }
        }
    }
}
```

## 三、连接复用（HTTP Keep-Alive & 连接池）

如果每次请求都走一遍 TCP 三次握手，开销巨大。连接池是必须的：

```
没有连接池的场景：
  请求1: SYN → SYN+ACK → ACK → HTTP Request → Response → FIN (关闭)
  请求2: SYN → SYN+ACK → ACK → HTTP Request → Response → FIN (关闭)
  每次都要 1.5 RTT 建立连接 + 0.5 RTT 关闭连接

有连接池 + Keep-Alive:
  请求1: SYN → SYN+ACK → ACK → HTTP Request → Response (连接保留)
  请求2:                   直接 HTTP Request → Response (复用连接)
  请求3:                   直接 HTTP Request → Response (复用连接)
  只需 1 次 TCP 握手
```

**Spring Cloud OpenFeign 的连接池配置：**

```java
@Configuration
public class FeignClientConfig {
    
    @Bean
    public okhttp3.OkHttpClient feignClient() {
        return new OkHttpClient.Builder()
            // 连接池
            .connectionPool(new ConnectionPool(
                50,                    // 最大空闲连接数
                5, TimeUnit.MINUTES    // 空闲连接存活时间
            ))
            .connectTimeout(5, TimeUnit.SECONDS)
            .readTimeout(30, TimeUnit.SECONDS)
            .retryOnConnectionFailure(true)
            // HTTP/2 支持（如果服务端支持，多路复用）
            .protocols(Arrays.asList(Protocol.HTTP_2, Protocol.HTTP_1_1))
            .build();
    }
}
```

**HTTP/2 多路复用 vs HTTP/1.1 Keep-Alive：**

```
HTTP/1.1 Keep-Alive:
  连接1: [请求1]──等待──[响应1] [请求2]──等待──[响应2]
  连接2: [请求3]──等待──[响应3] [请求4]──等待──[响应4]
  问题：同一个连接上的请求必须排队（队头阻塞）

HTTP/2 多路复用:
  连接1: [请求1] [请求2] [请求3] [请求4]  ← 混合发送
         [响应1] [响应3] [响应2] [响应4]  ← 按序号重组
  优势：一个 TCP 连接上可以并行多个请求流（Stream）
        没有队头阻塞（HTTP 层面）
```

**gRPC（HTTP/2 + Protobuf）的底层通信模型：**

```java
// gRPC 客户端建立连接时：
ManagedChannel channel = ManagedChannelBuilder
    .forAddress("user-service", 8080)
    .usePlaintext()                    // 或 .useTransportSecurity() for TLS
    .enableRetry()                     // 自动重试
    .maxRetryAttempts(3)
    .keepAliveTime(30, TimeUnit.SECONDS)
    .build();

// 底层发生的事：
// 1. DNS 解析得到目标地址
// 2. 建立一个 TCP 连接
// 3. HTTP/2 协商（h2c 明文 or h2 TLS-ALPN）
// 4. 发送 HTTP/2 SETTINGS 帧
// 5. 后续所有 RPC 调用复用这一个 TCP 连接
//    每个 RPC = 一个 HTTP/2 Stream
//    Stream 之间独立，不互相阻塞

// gRPC 一次 Unary RPC 的网络帧序列：
// Client → Server: HEADERS帧 (stream_id=1, :method=POST, :path=/UserService/GetUser)
// Client → Server: DATA帧 (stream_id=1, body=Protobuf编码的请求)
// Client → Server: DATA帧 (END_STREAM=true)
// Server → Client: HEADERS帧 (stream_id=1, :status=200)
// Server → Client: DATA帧 (stream_id=1, body=Protobuf编码的响应)
// Server → Client: DATA帧 (END_STREAM=true)
```

## 四、服务间通信的完整延迟分解

一次微服务调用的端到端延迟：

```
总延迟 ≈ 2-50ms（同集群内）

延迟分解：
┌─────────────────────────────┬──────────────┐
│ 环节                        │ 耗时         │
├─────────────────────────────┼──────────────┤
│ 服务发现（从本地缓存）        │ <0.1ms       │
│ 服务发现（触发网络请求）      │ 1-5ms        │
│ 连接池获取连接（复用）        │ <0.01ms      │
│ TCP 建连（新建连接）          │ 0.2-0.5ms    │
│ TLS 握手（新建连接）          │ 1-5ms        │
│ 序列化（JSON）               │ 0.1-0.5ms    │
│ 序列化（Protobuf）           │ 0.01-0.1ms   │
│ HTTP 报文构造                │ <0.1ms       │
│ 内核协议栈处理               │ 0.01-0.05ms  │
│ 网络传输（同节点）            │ <0.1ms       │
│ 网络传输（跨节点）            │ 0.1-0.5ms    │
│ CNI/VXLAN 封装解封装          │ 0.01-0.05ms  │
│ 接收端内核处理               │ 0.01-0.05ms  │
│ HTTP 解析                    │ <0.1ms       │
│ 反序列化                     │ 0.1-0.5ms    │
│ 业务逻辑执行                 │ 1-50ms       │
│ 响应序列化 + 返回             │ 同上         │
└─────────────────────────────┴──────────────┘
```

**优化方向优先级：**

```
最高优先级（收益最大）：
  1. 连接池复用 → 省掉 TCP/TLS 建连开销
  2. 异步非阻式（WebClient / gRPC）→ 减少线程阻塞
  3. 批量请求合并 → 减少网络往返次数

中等优先级：
  4. Protobuf 替代 JSON → 减少序列化时间和包大小
  5. HTTP/2 多路复用 → 减少连接数
  6. 缓存热点数据 → 避免网络调用

低优先级（同集群场景下不明显）：
  7. TCP 参数调优
  8. 内核旁路（DPDK/XDP，除非极端性能要求）
```

## 五、gRPC 与 REST 底层对比

```
┌─────────────────┬────────────────────────┬────────────────────────┐
│ 维度            │ REST (HTTP/1.1 + JSON) │ gRPC (HTTP/2 + Protobuf)│
├─────────────────┼────────────────────────┼────────────────────────┤
│ 连接模型        │ 一请求一连接（或复用）    │ 一个连接多路复用         │
│ 头部压缩        │ 无                     │ HPACK 压缩              │
│ 流式传输        │ 不原生支持              │ 原生支持双向流           │
│ 序列化大小      │ 大（JSON 文本）          │ 小（Protobuf 二进制）    │
│ 序列化速度      │ 中等                   │ 极快                    │
│ 类型安全        │ 弱（运行时解析）         │ 强（编译时生成代码）     │
│ 浏览器直接调用  │ 是                     │ 需要 grpc-web 代理       │
│ 调试可见性      │ 高（人可读 JSON）        │ 低（二进制不可读）       │
└─────────────────┴────────────────────────┴────────────────────────┘
```

## 总结

服务间通信的底层，本质上就是：

```
应用对象 → 序列化为字节 → 构造应用层协议(HTTP/gRPC) → 
TCP 分段 → IP 封包 → 二层帧封装 → 网卡 DMA 发送 → 
物理网络传输(经 CNI/SDN) → 接收端内核协议栈逐层解封 → 
Socket 缓冲区 → 应用 read → 反序列化为对象 → 业务处理
```

每一层都有性能损耗和优化空间。理解这些底层细节，才能在出现延迟问题、丢包问题、OOM 问题时快速定位根因，而不是停留在"加机器"的表面解决方式。
