---

## 一、服务发现：互联的基石

### 1.1 Kubernetes 原生机制：Service + CoreDNS

```
Pod A  ──HTTP请求──▶  my-service.default.svc.cluster.local  ──▶  CoreDNS 解析
                                                                    │
                                                              ClusterIP (虚拟 IP)
                                                                    │
                                                              iptables / IPVS 规则
                                                                    │
                                                              Pod B (Endpoint)
```

**底层细节：**

- **ClusterIP** 是一个虚拟 IP，不存在于任何网卡上，完全由 **iptables** 或 **IPVS** 规则在 Node 内核态实现 DNAT 转换。
- **kube-proxy** 监听 API Server 的 Service/Endpoints 变更事件，实时刷新每个 Node 上的转发规则。
- **CoreDNS** 以 Deployment 方式运行，监听 Kubernetes API，为每个 Service 生成 A 记录（`<svc-name>.<ns>.svc.cluster.local → ClusterIP`）。

```bash
# 查看 iptables 中 Service 的 DNAT 规则
iptables -t nat -L KUBE-SERVICES -n | grep my-service

# 查看 Endpoints 是否就绪
kubectl get endpoints my-service -n default
```

### 1.2 Headless Service 与 StatefulSet

当 `.spec.clusterIP: None` 时，DNS 直接返回所有 Pod IP，绕过虚拟 IP 层：

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-db
spec:
  clusterIP: None          # Headless
  selector:
    app: my-db
  ports:
    - port: 5432
```

DNS 查询 `my-db.default.svc.cluster.local` 会返回 **所有 Pod 的 A 记录**，客户端可自行做负载均衡（常用于数据库、消息队列等有状态服务）。

## 二、网络模型：Pod 之间如何互通

### 2.1 CNI 插件的数据平面

Kubernetes 要求**任意 Pod 可直接访问任意 Pod（扁平网络）**，这由 CNI 插件实现：

| CNI 插件 | 封装方式 | 底层机制 | 适用场景 |
|---|---|---|---|
| **Calico** | 无封装（BGP）或 IPIP/VXLAN | 路由表 + eBPF/iptables | 大规模集群、高性能 |
| **Flannel** | VXLAN | UDP 封装 overlay | 小型集群、快速部署 |
| **Cilium** | VXLAN/Geneve 或原生路由 | **eBPF** 直接在内核态处理 | 高性能、可观测性 |
| **Weave** | VXLAN + 加密 | sleeve 封装 | 跨云、需要加密 |

**以 Calico BGP 模式为例的底层数据流：**

```
Pod A (10.244.1.5)
  │  veth pair
  ▼
Node A 网桥 (cbr0 / caliXXX)
  │  路由查找 → 10.244.2.0/24 via Node B
  │  BGP 协议已将路由同步到 FIB
  ▼
物理网卡 eth0 → Node B eth0
  │  路由查找 → 10.244.2.8 dev caliYYY
  ▼
Pod B (10.244.2.8)
```

```bash
# 查看 Node 上 Pod 的路由
ip route show | grep 10.244
# 10.244.2.0/24 via 192.168.1.12 dev eth0 proto bird

# 查看 BGP 对等状态（Calico）
calicoctl node status
```

### 2.2 NetworkPolicy 的内核实现

NetworkPolicy 不是"建议"，而是由 CNI 在内核态用 **iptables / eBPF / nftables** 强制执行的：

```yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-frontend
  namespace: production
spec:
  podSelector:
    matchLabels:
      app: backend
  ingress:
    - from:
        - podSelector:
            matchLabels:
              app: frontend
      ports:
        - port: 8080
```

**Calico 的实现**：在每个 Pod 的 veth 上挂载 iptables chain（`cali-pi-<policyname>`），精确控制入站/出站流量。

**Cilium 的实现**：用 eBPF 程序直接附加到 Pod 的 TC（Traffic Control）hook 点，绕过 iptables，性能更高。

## 三、服务间通信协议层

### 3.1 L4：TCP 连接的建立

```
Pod A                          Pod B
  │                              │
  │──── SYN (srcPort:43210) ───▶│  经过 kube-proxy DNAT
  │◀─── SYN+ACK ───────────────│  Pod B 看到的源 IP 是 Pod A 的真实 IP
  │──── ACK ───────────────────▶│
  │                              │
  │  HTTP/gRPC 数据流开始         │
```

关键点：Kubernetes 扁平网络下，Pod B 收到的源 IP **是 Pod A 的真实 IP**（非 NAT 后的 ClusterIP），这意味着服务端可以做基于源 IP 的审计和限流。

### 3.2 L7：gRPC / HTTP2 在 K8s 中的特殊问题

gRPC 基于 HTTP/2，而 HTTP/2 使用**长连接多路复用**。这导致了一个经典陷阱：

```
┌─────────────┐        ┌──────────────┐        ┌────────────┐
│  Pod A      │────────▶│  ClusterIP   │────────▶│  Pod B     │
│  (gRPC客户端)│  L4 LB  │  kube-proxy  │ DNAT   │  (gRPC服务端)│
│             │         │              │        │            │
│  只建立了一条 │         │  第一个包:    │        │ Pod B 崩溃  │
│  HTTP/2 连接 │         │  正确转发 ✅   │        │ 重启       │
│             │         │  后续包:      │        │ 新 Pod IP  │
│             │         │  继续发到旧IP ❌│        │            │
└─────────────┘        └──────────────┘        └────────────┘
```

**问题**：kube-proxy 工作在 L4（TCP 层），一旦连接建立，后续流量会持续发往同一个后端 Pod。如果该 Pod 重启（新 IP），连接断开前客户端不会感知。

**解决：需要 L7 服务网格或 L7 Ingress Controller。**

## 四、服务网格：L7 互联的底层细节

### 4.1 Sidecar Proxy 模式（Istio / Envoy）

```
┌───── Pod ──────────────────────────┐
│                                    │
│  ┌──────────┐    ┌──────────────┐  │
│  │  App容器   │◀──▶│ Envoy Sidecar│  │
│  │ (业务代码) │    │  (L7代理)     │  │
│  │ 127.0.0.1 │    │              │  │
│  │ :8080     │    │ eth0: Pod IP │  │
│  └──────────┘    └──────┬───────┘  │
│                         │          │
└─────────────────────────┼──────────┘
                          │
                    物理网络（Pod IP 可路由）
```

**底层机制：Istio 使用 `iptables` 拦截**

```bash
# init 容器执行的 iptables 规则（简化）
iptables -t nat -A PREROUTING -j ISTIO_INBOUND
iptables -t nat -A ISTIO_INBOUND -p tcp --dport 8080 -j ISTIO_IN_REDIRECT
iptables -t nat -A ISTIO_IN_REDIRECT -p tcp -j REDIRECT --to-port 15006  # Envoy 入站

iptables -t nat -A OUTPUT -j ISTIO_OUTPUT
iptables -t nat -A ISTIO_OUTPUT -d 127.0.0.1/32 -j RETURN  # 本机流量放行
iptables -t nat -A ISTIO_OUTPUT -j ISTIO_REDIRECT
iptables -t nat -A ISTIO_REDIRECT -p tcp -j REDIRECT --to-port 15001  # Envoy 出站
```

**完整请求路径：**

```
App容器 → localhost:8080（原始目的地被 iptables 记录）
     │
     ▼ iptables REDIRECT
Envoy 出站端口 15001
     │ 读取 SO_ORIGINAL_DST 获取真实目的地
     │ 查询 Istio 推送的 xDS 路由配置
     │ 执行：mTLS加密 → 负载均衡 → 故障注入 → 重试 → 熔断
     ▼
Envoy 入站端口 15006（目标Pod）
     │ mTLS 解密 → RBAC鉴权
     ▼
目标 App容器 localhost:8080
```

### 4.2 eBPF 模式（Cilium Service Mesh）

Cilium 用 eBPF 替代 sidecar，直接在内核态处理 L7 流量：

```
┌───── Pod ─────────────┐
│  ┌──────────┐         │
│  │  App容器   │         │    无需 Sidecar！
│  │ (业务代码) │         │
│  └──────────┘         │
└────────┬──────────────┘
         │  eBPF 程序附加在 TC hook / socket 层
         │  直接解析 HTTP/gRPC 协议头
         ▼
    内核态 L7 路由/负载均衡/mTLS (通过 WireGuard)
```

**优势**：零额外延迟、无 sidecar 资源开销、单 Pod 故障不影响旁路。

## 五、DNS 解析的完整底层链路

一次完整的 `curl http://order-service.production.svc.cluster.local:8080/api/order` 背后：

```
1. App 调用 getaddrinfo()
      │
2. libc 读取 /etc/resolv.conf
   nameserver 10.96.0.10  (CoreDNS ClusterIP)
   ndots:5                (搜索域策略)
      │
3. DNS 查询发往 CoreDNS Pod (经 kube-proxy DNAT)
      │
4. CoreDNS 查询 kubernetes 插件（内存缓存，watch API Server）
   返回 A 记录: 10.97.42.15 (order-service ClusterIP)
      │
5. App 发起 TCP 连接到 10.97.42.15:8080
      │
6. iptables/IPVS DNAT → 10.244.3.7:8080 (某个 order-service Pod)
      │
7. CNI 路由转发（Calico BGP / Flannel VXLAN）
      │
8. 目标 Pod 收到请求
```

**常见 DNS 问题排查：**

```bash
# CoreDNS 日志
kubectl logs -n kube-system -l k8s-app=kube-dns

# DNS 解析延迟测试
kubectl run dnstest --image=busybox:1.36 --rm -it -- nslookup order-service.production.svc.cluster.local

# ndots 导致的性能问题
# ndots:5 意味着域名少于5个"."时，会依次尝试所有 search domains
# 解决：在 Pod spec 中设置 dnsConfig 缩小 ndots
```

```yaml
dnsConfig:
  options:
    - name: ndots
      value: "2"
```

## 六、可观测性：追踪互联链路

### 6.1 关键指标

```bash
# 连接级指标（kube-proxy）
conntrack -L | grep 10.244 | wc -l   # 当前活跃连接数

# Service 级指标
kubectl get --raw /metrics | grep apiserver_request_latency

# 如果用 Istio
istioctl proxy-config routes <pod-name>  # 查看 Envoy 路由表
istioctl dashboard kiali                  # 服务拓扑可视化
```

### 6.2 链路追踪注入

服务网格自动注入 `x-request-id`、`x-b3-traceid` 等 header，无需修改业务代码。没有网格时，需要在应用层手动集成 OpenTelemetry SDK。

## 总结：微服务互联的七层全景

```
┌─────────────────────────────────────────────────────────┐
│  L7  应用协议：HTTP/1.1, HTTP/2, gRPC, WebSocket        │
├─────────────────────────────────────────────────────────┤
│  L7  服务网格：Istio/Linkerd/Cilium (路由、重试、熔断、mTLS) │
├─────────────────────────────────────────────────────────┤
│  L5-L6 会话/表示：TLS 终止、协议协商                        │
├─────────────────────────────────────────────────────────┤
│  L4  传输：TCP/UDP, kube-proxy (iptables/IPVS)          │
├─────────────────────────────────────────────────────────┤
│  L3  网络：CNI 插件 (Pod IP 路由, VXLAN/BGP/eBPF)       │
├─────────────────────────────────────────────────────────┤
│  L2  数据链路：veth pair, Linux Bridge, 网卡驱动          │
├─────────────────────────────────────────────────────────┤
│  L0  服务发现：CoreDNS + K8s Service API                │
└─────────────────────────────────────────────────────────┘
```

每一层都有对应的故障模式和排查手段。作为 K8s 管理员，理解这些底层细节不是可选项——当生产环境凌晨三点告警时，正是这些知识决定了你是能在 5 分钟定位问题，还是在 5 小时后还在翻日志。

有任何具体场景需要深入展开的，随时提问。
