选型错误是 Redis 生产事故的头号原因。按业务需求对号入座。

## 四种架构

| 架构 | 可用性 | 扩展性 | 复杂度 | 适用 |
|------|--------|--------|--------|------|
| 单机 | 低 | 垂直 | 低 | 开发、非核心缓存 |
| 主从 | 中（需手动切换） | 读扩展 | 低 | 读多写少、可接受短中断 |
| 哨兵 | 高（自动 failover） | 读扩展 | 中 | 中小规模生产 |
| Cluster | 高 | 水平分片 | 高 | 大数据量、高 QPS |

## 决策树

```
数据量 > 单机内存 80%？
  ├─ 是 → Cluster 或 分片中间件（Codis/Twemproxy）
  └─ 否 → 需要自动故障转移？
           ├─ 是 → Sentinel（≤ 3 主 规模）或 Cluster
           └─ 否 → 主从 或 单机 + 冷备
```

## 云托管 vs 自建

| | 云托管 | 自建 |
|---|--------|------|
| 运维负担 | 低 | 高 |
| 定制能力 | 受限 | 完全 |
| 成本 | 按规格 | 机器 + 人力 |
| 合规 | 看云资质 | 自控 |

## 常见误选

- **小数据量上 Cluster**：运维成本高，MOVED/ASK 增加客户端复杂度
- **核心库只用单机**：无 HA，磁盘/进程挂即全挂
- **哨兵 + 超大实例**：单主内存过大，RDB fork 阻塞、重启慢
