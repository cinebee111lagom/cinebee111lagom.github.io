## 什么是 OLTP

**OLTP（Online Transaction Processing，在线事务处理）** 是一种面向事务的数据库操作模式，核心特征是**高频、短时、并发**的读写操作。

---

## 读写特征对比

| 维度 | 写操作 | 读操作 |
|------|--------|--------|
| **典型语句** | INSERT / UPDATE / DELETE | SELECT（基于主键或索引） |
| **数据量** | 单次少量（几行） | 单次少量（精确查询） |
| **延迟要求** | 极低（毫秒级） | 极低（毫秒级） |
| **并发量** | 高 | 非常高 |
| **一致性要求** | 强一致性（ACID） | 强一致性（读已提交/可重复读） |

---

## 典型读写流程

### 写路径（Write Path）

```
客户端请求
  → 解析 SQL
  → 获取行锁（Row Lock）
  → 写 Redo Log（WAL，Write-Ahead Logging）
  → 写 Undo Log（用于回滚）
  → 修改 Buffer Pool 中的数据页
  → 提交（Commit）→ Redo Log 持久化
  → 后台异步刷脏页到磁盘
```

**关键点**：
- **先写日志，再写数据**（WAL 机制），保证崩溃恢复
- 行级锁 + MVCC 实现高并发写入
- 事务提交时只需保证 Redo Log 落盘，不等脏页刷盘

### 读路径（Read Path）

```
客户端请求
  → 解析 SQL
  → 优化器选择执行计划
  → 通过索引定位数据页
  → 在 Buffer Pool 中查找
    → 命中：直接返回
    → 未命中：从磁盘加载到 Buffer Pool → 返回
  → 通过 MVCC 读取正确版本（Read View）
```

**关键点**：
- 绝大多数读操作在内存（Buffer Pool）中完成
- MVCC 使得读操作**不加锁**，读写互不阻塞
- 走索引是性能关键（避免全表扫描）

## 核心机制

### 1. ACID 保障
```
A（原子性）  ← Undo Log 回滚
C（一致性）  ← 应用层 + 约束
I（隔离性）  ← 锁 + MVCC
D（持久性）  ← Redo Log
```

### 2. MVCC（多版本并发控制）
- 每行数据维护隐藏列：`trx_id`（事务ID）、`roll_pointer`（指向 Undo Log）
- 读操作根据 **Read View** 判断可见性
- 实现**快照读**：不加锁，读写并行

### 3. Buffer Pool
- 热数据常驻内存，减少磁盘 I/O
- LRU 变体算法管理页面淘汰
- 命中率通常 > 99%

## 常见瓶颈与优化

### 读瓶颈
| 问题 | 解决方案 |
|------|----------|
| 索引缺失导致全表扫描 | 添加合适的索引 |
| 热点行竞争 | 缓存层（Redis）+ 读写分离 |
| Buffer Pool 命中率低 | 增大内存、优化查询 |
| 锁等待 | 减小事务粒度、优化隔离级别 |

### 写瓶颈
| 问题 | 解决方案 |
|------|----------|
| Redo Log 成为瓶颈 | 增大 Redo Log 文件、分组提交 |
| 锁冲突严重 | 拆分热点行、队列化写入 |
| 主键自增竞争 | 雪花ID、批量分配 |
| 刷脏页导致性能抖动 | 控制刷脏节奏、增大 Buffer Pool |

## OLTP vs OLAP 简要对比

```
OLTP                              OLAP
├── 高并发小事务                   ├── 低并发大查询
├── 行存为主                       ├── 列存为主
├── 读写混合                       ├── 读多写少
├── 强调延迟（ms）                 ├── 强调吞吐量
└── 银行交易、电商下单              └── 报表分析、数据挖掘
```

## 实践建议

1. **事务尽量短** — 持锁时间越短，并发能力越强
2. **查询必须走索引** — OLTP 场景下全表扫描是灾难
3. **批量操作拆小批** — 避免长事务阻塞其他会话
4. **合理选择隔离级别** — 多数场景 `READ COMMITTED` 已足够
5. **读写分离** — 主库写、从库读，水平扩展读能力
