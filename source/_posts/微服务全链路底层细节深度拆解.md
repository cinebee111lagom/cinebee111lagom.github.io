### 链路总览

```
外部用户 → CDN/LB → Ingress Controller → gateway-service
  → user-service  → order-service → pay-service
  → Nacos（服务注册 + 配置中心）
  → MySQL（持久化存储）
  → Redis（缓存/分布式锁）
  → Kafka（异步消息）
```

## 第一层：外部请求 → Ingress Controller

### 1.1 外部流量进入集群的物理路径

```
用户的浏览器/手机 App
    │
    ▼
DNS 解析 api.example.com → 公网 IP（如 47.100.x.x）
    │
    ▼
云厂商 SLB/CLB（四层负载均衡）
    │  将 TCP:443 流量转发到 K8s 节点的 NodePort
    │
    ▼
Node 的 NodePort（范围 30000-32767）
    │
    ▼
kube-proxy 维护的 iptables/IPVS 规则
    │  将 NodePort 流量 → Ingress Controller Pod
    │
    ▼
Ingress Controller Pod（如 Nginx Ingress）
    │
    ▼
根据 Ingress 资源规则匹配 Host + Path
    │
    ▼
转发到后端 Service（gateway-service）
```

### 1.2 Ingress 资源的底层定义

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: gateway-ingress
  namespace: production
  annotations:
    # Nginx Ingress 特有注解
    nginx.ingress.kubernetes.io/ssl-redirect: "true"
    nginx.ingress.kubernetes.io/proxy-body-size: "50m"
    nginx.ingress.kubernetes.io/proxy-connect-timeout: "10"
    nginx.ingress.kubernetes.io/proxy-read-timeout: "60"
    nginx.ingress.kubernetes.io/proxy-send-timeout: "60"
    # 限流
    nginx.ingress.kubernetes.io/limit-rps: "100"
    # 重写路径
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  ingressClassName: nginx
  tls:
  - hosts:
    - api.example.com
    secretName: api-tls-secret    # 存放证书的 Secret
  rules:
  - host: api.example.com
    http:
      paths:
      - path: /api/user(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: gateway-service
            port:
              number: 8080
      - path: /api/order(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: gateway-service
            port:
              number: 8080
```

### 1.3 Nginx Ingress Controller 的底层工作机制

```
┌──────────────────────────────────────────────────────────────┐
│              Nginx Ingress Controller Pod                     │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  Ingress Controller 进程（Go 程序）                     │   │
│  │                                                      │   │
│  │  1. watch K8s APIServer:                             │   │
│  │     - Ingress 资源变化                                │   │
│  │     - Service 变化                                    │   │
│  │     - Endpoints 变化（Pod IP 增减）                    │   │
│  │     - Secret 变化（TLS 证书）                         │   │
│  │                                                      │   │
│  │  2. 将 K8s 资源翻译为 nginx.conf                       │   │
│  │     - 每个 Ingress rule → 一个 location 块             │   │
│  │     - 每个 backend Service → 一组 upstream server      │   │
│  │                                                      │   │
│  │  3. 执行 nginx -s reload 热加载配置                    │   │
│  └──────────────────────────────────────────────────────┘   │
│                                                              │
│  ┌──────────────────────────────────────────────────────┐   │
│  │  Nginx 主进程 + Worker 进程                           │   │
│  │                                                      │   │
│  │  实际处理 HTTP/HTTPS 流量：                            │   │
│  │  - TLS 终止（解密 HTTPS）                             │   │
│  │  - 基于 Host + Path 路由                              │   │
│  │  - 连接后端 upstream（gateway-service 的 Pod IP）      │   │
│  │  - WebSocket 代理                                     │   │
│  │  - 限流、IP 黑白名单                                  │   │
│  └──────────────────────────────────────────────────────┘   │
└──────────────────────────────────────────────────────────────┘
```

**自动生成的 nginx.conf 片段**（由 Controller 基于 Ingress 资源生成）：

```nginx
# TLS 服务器块
server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /etc/ingress-controller/ssl/default-api-tls-secret.crt;
    ssl_certificate_key /etc/ingress-controller/ssl/default-api-tls-secret.key;

    # 路由规则 → location 块
    location /api/user/ {
        set $proxy_upstream_name "production-gateway-service-8080";

        proxy_pass http://upstream_balancer;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /api/order/ {
        set $proxy_upstream_name "production-gateway-service-8080";
        # ... 同上
    }
}

# upstream 由 Endpoints 动态生成
upstream production-gateway-service-8080 {
    # 负载均衡策略（默认 round_robin）
    server 10.244.1.10:8080;    # gateway-service Pod 1
    server 10.244.2.15:8080;    # gateway-service Pod 2

    keepalive 32;  # 长连接池
}
```

**关键细节**：Ingress Controller 直接 watch **Endpoints**（而非 Service），所以当 Pod 扩缩容时，nginx.conf 中的 upstream 列表会实时更新，延迟仅 1-2 秒。

### 1.4 TLS 终止的底层

```
客户端 ──TLS握手──► Ingress Controller ──明文HTTP──► gateway Pod
                     │
                     ├── TLS 证书从 Secret 挂载
                     │   Secret 类型: kubernetes.io/tls
                     │   包含: tls.crt + tls.key
                     │
                     ├── 支持自动证书管理:
                     │   cert-manager → Let's Encrypt → 自动签发/续期
                     │
                     └── TLS Session 复用:
                         Nginx 缓存 TLS Session，避免重复握手
```

## 第二层：Ingress Controller → gateway-service

### 2.1 gateway-service 的 Service 定义

```yaml
apiVersion: v1
kind: Service
metadata:
  name: gateway-service
  namespace: production
spec:
  selector:
    app: gateway-service
  ports:
  - name: http
    port: 8080
    targetPort: 8080
  type: ClusterIP
```

### 2.2 流量从 Ingress Controller 到 Gateway Pod 的底层

```
Nginx Worker 进程
    │
    │ upstream 中选择 server 10.244.1.10:8080（round_robin）
    │
    ▼
TCP 三次握手（Nginx → Pod IP）
    │
    ▼
注意：Nginx 这里直接连 Pod IP，没有经过 Service ClusterIP！
    │  因为 Ingress Controller watch 的是 Endpoints，直接写 Pod IP 到 upstream
    │
    ▼
数据包经由 Pod 网络：
    │  Nginx Pod 网络命名空间 → veth pair → Node bridge
    │  → 同节点：直接 bridge 转发到目标 veth
    │  → 跨节点：CNI 封装（VXLAN/BGP）→ 目标 Node → 目标 Pod
    │
    ▼
gateway-service Pod 的 8080 端口接收 HTTP 请求
```

### 2.3 Spring Cloud Gateway Pod 内部处理

```
gateway-service Pod（Spring Cloud Gateway）
    │
    │  收到请求: POST https://api.example.com/api/user/login
    │  经过 Nginx TLS 终止后变为: POST http://gateway:8080/api/user/login
    │
    ▼
① Gateway Filter Chain（路由过滤器链）
    │
    ├── GlobalFilter: 请求日志记录
    ├── GlobalFilter: 鉴权（JWT Token 校验）
    ├── GlobalFilter: 限流（Redis + Lua 或 Sentinel）
    │
    ▼
② RoutePredicateHandlerMapping（路由匹配）
    │  根据 Path=/api/user/** 匹配到 user-service 路由
    │
    ▼
③ LoadBalancerClientFilter（负载均衡）
    │  解析 lb://user-service → 从 K8s 获取 Service Endpoints
    │
    ▼
④ Netty HttpClient 发起请求到 user-service Pod
```

**Gateway 的路由配置**：

```yaml
spring:
  cloud:
    gateway:
      routes:
      - id: user-service
        uri: lb://user-service     # lb = 负载均衡
        predicates:
        - Path=/api/user/**
        filters:
        - StripPrefix=2            # 去掉 /api/user 前缀
        - name: CircuitBreaker
          args:
            name: userServiceCB
            fallbackUri: forward:/fallback/user

      - id: order-service
        uri: lb://order-service
        predicates:
        - Path=/api/order/**
        filters:
        - StripPrefix=2

      - id: pay-service
        uri: lb://pay-service
        predicates:
        - Path=/api/pay/**
        filters:
        - StripPrefix=2
```

## 第三层：gateway-service → user-service

### 3.1 Spring Cloud LoadBalancer + K8s 的服务发现底层

```
Gateway 的 LoadBalancerClientFilter
    │
    ▼
Spring Cloud Kubernetes Discovery Client
    │  实现了 ServiceInstanceListSupplier 接口
    │
    ▼
调用 K8s API：
    GET /api/v1/namespaces/production/endpoints/user-service
    │
    ▼
K8s APIServer 返回 Endpoints 对象：
{
  "subsets": [{
    "addresses": [
      {"ip": "10.244.1.12", "nodeName": "node-1", "targetRef": {"name": "user-service-pod-1"}},
      {"ip": "10.244.2.18", "nodeName": "node-2", "targetRef": {"name": "user-service-pod-2"}},
      {"ip": "10.244.3.7",  "nodeName": "node-3", "targetRef": {"name": "user-service-pod-3"}}
    ],
    "ports": [{"port": 8080, "protocol": "TCP"}]
  }]
}
    │
    ▼
Spring Cloud LoadBalancer 缓存 Endpoints 列表
    │  定期刷新（默认 30s）
    │
    ▼
负载均衡算法选择一个 Pod IP：
    round_robin / random / 自定义
    │
    ▼
HTTP 请求: GET http://10.244.2.18:8080/login
```

### 3.2 直连 Pod IP vs 通过 Service ClusterIP

| 方式 | 路径 | 优点 | 缺点 |
|---|---|---|---|
| **直连 Pod IP**（Spring Cloud LB 默认） | Gateway → Pod IP | 少一跳；客户端感知全部 Pod | 需要 RBAC 授权访问 Endpoints |
| **通过 ClusterIP** | Gateway → Service ClusterIP → iptables DNAT → Pod | 简单；不依赖 K8s API | 多一跳；kube-proxy 更新有延迟 |

**RBAC 配置**（Spring Cloud Kubernetes 需要）：

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: endpoints-reader
  namespace: production
rules:
- apiGroups: [""]
  resources: ["endpoints", "services", "pods"]
  verbs: ["get", "list", "watch"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: gateway-endpoints-reader
  namespace: production
subjects:
- kind: ServiceAccount
  name: gateway-service     # Gateway Pod 使用的 ServiceAccount
  namespace: production
roleRef:
  kind: Role
  name: endpoints-reader
  apiGroup: rbac.authorization.k8s.io
```

### 3.3 完整的网络数据包流转

```
┌──────────┐     ┌──────────┐     ┌──────────────────────┐
│ gateway  │     │  user-   │     │   Node-2 网络栈      │
│ Pod      │     │  service │     │                      │
│ (Node-1) │     │  Pod     │     │  eth0 ◄── VXLAN ──┐ │
│          │     │ (Node-2) │     │    │               │ │
│ Netty ───┼──►  │          │     │  veth──► Pod      │ │
│ Client   │ TCP │  Netty   │     │                      │ │
│          │ SYN │  Server  │     └──────────────────────┘ │
│ Pod NIC  │─────┼──►:8080  │            ▲                │
│ veth0    │     │          │            │                │
└────┬─────┘     └──────────┘            │                │
     │                                   │                │
     │  Node-1 网络栈                     │                │
     │  veth0 → bridge → calico          │                │
     │  → VXLAN 封装 ───────────────────┘                │
     │    外层: Node1-IP → Node2-IP                       │
     │    内层: Pod1-IP → Pod2-IP                         │
```

**VXLAN 封装的底层**：

```
原始数据包:
  [Ethernet Header][IP Header(src:10.244.1.12, dst:10.244.2.18)][TCP][HTTP Data]

VXLAN 封装后:
  [Outer Eth][Outer IP(src:192.168.1.1, dst:192.168.1.2)]
  [Outer UDP(dport:4789)]
  [VXLAN Header(VNI:42)]
  [原始 Ethernet Header]
  [原始 IP Header(src:10.244.1.12, dst:10.244.2.18)]
  [TCP][HTTP Data]
```

## 第四层：user-service → order-service

### 4.1 服务间调用代码层面

```java
@FeignClient(
    name = "order-service",
    url = "${ORDER_SERVICE_URL:}",  // 可通过环境变量覆盖
    fallbackFactory = OrderServiceFallbackFactory.class
)
public interface OrderServiceClient {

    @GetMapping("/api/orders/{userId}")
    List<Order> getOrdersByUserId(@PathVariable String userId);

    @PostMapping("/api/orders")
    Order createOrder(@RequestBody CreateOrderRequest request);
}
```

### 4.2 Feign 调用在 K8s 上的底层时序

```
user-service Pod 的 JVM 进程
    │
    │  OrderServiceClient.getOrdersByUserId("user123")
    │
    ▼
① Feign 代理拦截方法调用
    │
    ▼
② Spring Cloud LoadBalancer 选择实例
    │  从缓存中取 order-service 的 Endpoints
    │  round_robin 选中 10.244.2.20:8080
    │
    ▼
③ 构建 HTTP 请求
    │  GET http://10.244.2.20:8080/api/orders/user123
    │  Headers:
    │    Content-Type: application/json
    │    X-Request-ID: <自动生成的追踪ID>
    │    X-Forwarded-For: 10.244.1.12
    │
    ▼
④ Apache HttpClient / OkHttp 发起 TCP 连接
    │  → Linux 内核 TCP/IP 协议栈
    │  → Pod 网络命名空间 → veth pair → bridge/CNI
    │
    ▼
⑤ order-service Pod 接收请求
    │  Spring MVC DispatcherServlet 处理
    │  → HandlerMapping → HandlerAdapter → Controller
    │
    ▼
⑥ 业务逻辑执行
    │
    ▼
⑦ HTTP 响应返回
    │  状态码: 200
    │  Body: [{"orderId":"ORD001","amount":99.9}, ...]
    │
    ▼
⑧ Feign 反序列化为 Java 对象
    │
    ▼
⑨ 返回给调用方
```

### 4.3 超时与重试的底层配置

```yaml
# Feign 配置
feign:
  client:
    config:
      default:
        connectTimeout: 3000      # TCP 连接超时 3s
        readTimeout: 5000         # 读取响应超时 5s
        loggerLevel: BASIC

# Spring Cloud LoadBalancer 配置
spring:
  cloud:
    loadbalancer:
      retry:
        enabled: true
        max-retries-on-same-service-instance: 0  # 同实例不重试
        max-retries-on-next-service-instance: 2  # 换实例最多重试2次

# 底层重试行为：
# 请求到 Pod-A 超时
#   → 换 Pod-B 重试
#   → 仍然超时
#   → 换 Pod-C 重试
#   → 全部失败 → 抛出异常 / 触发 Fallback
```

### 4.4 熔断器的底层（Resilience4j）

```yaml
resilience4j:
  circuitbreaker:
    instances:
      orderService:
        slidingWindowSize: 10           # 统计窗口：最近10次调用
        failureRateThreshold: 50        # 失败率 ≥ 50% → 开路
        slowCallRateThreshold: 80       # 慢调用率 ≥ 80% → 开路
        slowCallDurationThreshold: 2s   # 超过2s算慢调用
        waitDurationInOpenState: 30s    # 开路后等30s → 半开
        permittedNumberOfCallsInHalfOpenState: 3  # 半开放行3次
```

**状态机的底层**：

```
              失败率 < 50%
         ┌──────────────────┐
         │                  │
         ▼                  │
    ┌─────────┐  失败率 ≥ 50%  ┌──────────┐
    │ CLOSED  │ ────────────► │   OPEN   │
    │ (正常)  │               │ (熔断)    │
    └─────────┘               └────┬─────┘
         ▲                         │
         │  3次调用全部成功          │ 等待 30s
         │                         ▼
         │                   ┌───────────┐
         └───────────────────│ HALF-OPEN │
                             │ (半开放)   │
                             └───────────┘
                               │ 3次调用有失败
                               ▼
                             OPEN（重新熔断）
```

## 第五层：微服务 → Nacos（服务注册 + 配置中心）

### 5.1 服务注册的底层机制

```
user-service Pod 启动
    │
    ▼
① Spring Cloud Alibaba Nacos Discovery 自动配置
    │  读取环境变量: NACOS_SERVER_ADDR=nacos-headless.middleware:8848
    │
    ▼
② Nacos Client 发送注册 HTTP 请求
    │  POST http://nacos-headless.middleware:8848/nacos/v1/ns/instance
    │  参数:
    │    serviceName=user-service
    │    ip=10.244.1.12          ← Pod IP（从 Downward API 或网卡获取）
    │    port=8080
    │    namespaceId=production
    │    groupName=DEFAULT_GROUP
    │    metadata={"preserved.register.source":"SPRING_CLOUD"}
    │
    ▼
③ Nacos Server 存储实例信息
    │  内存 Map + 持久化到 Derby/MySQL
    │
    ▼
④ 心跳机制（每 5 秒）
    │  PUT http://nacos-headless.middleware:8848/nacos/v1/ns/instance/beat
    │  参数: serviceName, ip, port, beat={JSON}
    │
    ▼
⑤ 如果 15 秒没收到心跳 → 实例标记为不健康
   如果 30 秒没收到心跳 → 实例被删除
```

### 5.2 Nacos 在 K8s 中的部署方式

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: nacos
  namespace: middleware
spec:
  serviceName: nacos-headless
  replicas: 3
  selector:
    matchLabels:
      app: nacos
  template:
    metadata:
      labels:
        app: nacos
    spec:
      containers:
      - name: nacos
        image: nacos/nacos-server:v2.2.3
        ports:
        - containerPort: 8848    # HTTP API
        - containerPort: 9848    # gRPC（Nacos 2.x 通信）
        - containerPort: 9849    # gRPC Raft
        env:
        - name: MODE
          value: "cluster"
        - name: NACOS_SERVERS
          value: "nacos-0.nacos-headless.middleware:8848 nacos-1.nacos-headless.middleware:8848 nacos-2.nacos-headless.middleware:8848"
        - name: SPRING_DATASOURCE_PLATFORM
          value: "mysql"
        - name: MYSQL_SERVICE_HOST
          value: "mysql.middleware"
        - name: MYSQL_SERVICE_DB_NAME
          value: "nacos_config"
        volumeMounts:
        - name: nacos-data
          mountPath: /home/nacos/data
  volumeClaimTemplates:
  - metadata:
      name: nacos-data
    spec:
      accessModes: ["ReadWriteOnce"]
      storageClassName: "ssd"
      resources:
        requests:
          storage: 20Gi
---
apiVersion: v1
kind: Service
metadata:
  name: nacos-headless
  namespace: middleware
spec:
  clusterIP: None                # Headless！
  selector:
    app: nacos
  ports:
  - port: 8848
  - port: 9848
  - port: 9849
```

**为什么用 Headless Service**：
- Nacos 集群节点之间需要直接通信（Raft 选举）
- 每个 Nacos Pod 需要有稳定的网络标识（`nacos-0.nacos-headless.middleware`）
- StatefulSet + Headless Service 提供了这个能力

### 5.3 微服务读取 Nacos 配置的底层

```
Pod 启动 → Spring Boot 初始化
    │
    ▼
① Bootstrap 阶段加载 bootstrap.yml
    │  spring.cloud.nacos.config.server-addr=nacos-headless.middleware:8848
    │
    ▼
② Nacos Config Client 向 Nacos Server 拉取配置
    │  GET http://nacos-headless.middleware:8848/nacos/v1/cs/configs
    │  参数: dataId=user-service.yml, group=DEFAULT_GROUP, tenant=production
    │
    ▼
③ Nacos Server 返回配置内容（YAML/JSON/Properties）
    │
    ▼
④ 配置注入 Spring Environment
    │  优先级: Nacos 配置 > application.yml > 默认值
    │
    ▼
⑤ 长轮询监听配置变化（每 30s）
    │  GET http://nacos-headless.middleware:8848/nacos/v1/cs/configs/listener
    │  超时时间: 30s（Long Polling）
    │  如果配置变化 → 立即返回 → 重新拉取 → 刷新 Bean
```

## 第六层：微服务 → MySQL

### 6.1 MySQL 在 K8s 中的部署

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: mysql
  namespace: middleware
spec:
  serviceName: mysql-headless
  replicas: 1                     # 单实例（主从用 Operator）
  selector:
    matchLabels:
      app: mysql
  template:
    spec:
      containers:
      - name: mysql

### 6.2 PVC 的底层机制

```
Pod 创建时请求 PVC
    │
    ▼
PV Controller 发现 PVC 未绑定
    │
    ▼
查找匹配的 PV（或由 StorageClass 动态创建）
    │
    ▼
CSI Driver 调用云厂商 API 创建磁盘

    │

    ▼

### 6.3 微服务连接 MySQL 的底层

```yaml
# user-service 的数据源配置
env:
- name: SPRING_DATASOURCE_URL
  value: "jdbc:mysql://mysql-headless.middleware:3306/user_db?useSSL=false&serverTimezone=Asia/Shanghai&characterEncoding=utf8mb4"
- name: SPRING_DATASOURCE_USERNAME
  value: "user_service"
- name: SPRING_DATASOURCE_PASSWORD
  valueFrom:
    secretKeyRef:
      name: user-db-credentials
      key: password
```

**JDBC 连接的底层数据链路**：

```
user-service Pod (JVM)
    │
    │  JDBC URL: mysql-headless.middleware:3306
    │
    ▼
① DNS 解析 mysql-headless.middleware.svc.cluster.local
    │  → Headless Service → 返回 MySQL Pod IP: 10.244.3.100
    │
    ▼
② TCP 三次握手: user-service Pod → MySQL Pod:3306
    │  经 VXLAN/BGP 路由
    │
    ▼
③ MySQL 协议握手
    │  Server: MySQL 8.0.x → 发送 auth_plugin (caching_sha2_password)
    │  Client: 发送认证数据（密码哈希）
    │  Server: OK → 连接建立
    │
    ▼
④ HikariCP 连接池管理
    │  minimumIdle: 5      最小空闲连接
    │  maximumPoolSize: 20  最大连接数
    │  connectionTimeout: 30000  获取连接超时
    │  idleTimeout: 600000  空闲连接回收
    │  maxLifetime: 1800000 连接最大存活时间
    │
    ▼
⑤ SQL 执行
    │  PreparedStatement → MySQL 解析/优化/执行 → ResultSet
    │
    ▼
⑥ 连接归还到连接池（不是关闭 TCP 连接！）
```

**连接池参数的底层影响**：

```
假设 3 个 user-service Pod × 最大 20 连接 = 60 个连接到 MySQL
假设 3 个 order-service Pod × 最大 20 连接 = 60 个连接
假设 2 个 pay-service Pod × 最大 20 连接 = 40 个连接

总计: 160 个连接到单个 MySQL 实例

MySQL 默认 max_connections: 151

→ 可能出现 "Too many connections" 错误！

解决方案：
1. 调大 MySQL max_connections
2. 使用 ProxySQL 做连接复用
3. 合理降低各服务的连接池大小
```

┌──────────────────────────────────────────────────────────────────┐
│  生产者: pay-service Pod                                          │

│  ① KafkaProducer.send(ProducerRecord)                           │
│     │                                                            │

│     │                                                            │
│     ▼                                                            │

│     - 指定 key → hash(key) % numPartitions → 分区号              │

│     │                                                            │
│     ▼                                                            │

│     ▼                                                            │

│     │                                                            │
│     ▼                                                            │

```

```

    │
    │  用户支付成功
    │
    ▼

┌──────────────────────────────────────────────────┐
│              Kafka Broker Cluster                 │
│                                                  │
│  Topic: payment-success-events                   │
│  Partition-0: [msg1, msg2, msg3, ...]            │
│  Partition-1: [msg4, msg5, msg6, ...]            │
│  Partition-2: [msg7, msg8, msg9, ...]            │

### 链路追踪 Header 的传播

```
外部请求
    │
    ▼

    │

gateway-service:
    生成 TraceID: 00-trace001-span001-01
    生成 SpanID: span001
    注入 Header: traceparent: 00-trace001-span001-01

    从 Header 读取 traceparent
    生成新 SpanID: span002
    traceparent: 00-trace001-span002-01

    │
    ▼
order-service:
    从 Header 读取 traceparent
    生成新 SpanID: span003
    traceparent: 00-trace001-span003-01
    parentSpanID: span002
    │
    ▼
pay-service → Kafka → notify-service
    traceparent 通过 Kafka Message Header 传播
    → 即使是异步链路也能追踪
```
