## 一、容器镜像（Image）的底层细节

### 1.1 镜像的分层结构

容器镜像不是一个单一文件，而是由多个**只读层（Layer）**叠加而成的：

```
┌──────────────────────────────────┐
│   可写层 (Container Layer)        │  ← 容器运行时才有，写时复制
├──────────────────────────────────┤
│   Layer 5: COPY app.jar /app/    │  ← Spring Boot jar（最常变动）
│   Layer 4: COPY config/ /etc/    │  ← 配置文件
│   Layer 3: RUN apt-get install   │  ← 安装依赖
│   Layer 2: ENV JAVA_VERSION=17   │  ← 环境变量
│   Layer 1: FROM eclipse-temurin  │  ← 基础镜像（几乎不变）
└──────────────────────────────────┘
```

**关键底层机制**：
- 每个 Layer 对应一个 **SHA256 哈希**，相同的 Layer 在不同镜像之间**共享存储**
- kubelet 拉镜像时，只拉取本地缺失的 Layer（增量拉取）
- UnionFS（如 overlay2）将所有层合并为一个统一的文件系统视图

### 1.2 企业级 Dockerfile 最佳实践

```dockerfile
# ========== 阶段一：构建 ==========
FROM maven:3.9-eclipse-temurin-17 AS builder
WORKDIR /build
# 利用 Docker 缓存：先复制 pom.xml，下载依赖
COPY pom.xml .
RUN mvn dependency:go-offline -B
# 再复制源码编译
COPY src/ ./src/
RUN mvn package -DskipTests -B

# ========== 阶段二：运行 ==========
FROM eclipse-temurin:17-jre-jammy
# 安全加固：不用 root 运行
RUN groupadd -r appuser && useradd -r -g appuser appuser

# 设置时区（很多中国企业的隐性需求）
RUN ln -sf /usr/share/zoneinfo/Asia/Shanghai /etc/localtime

WORKDIR /app
# 只复制构建产物
COPY --from=builder /build/target/*.jar app.jar

# 文件归属
RUN chown -R appuser:appuser /app
USER appuser

# 暴露端口（声明性，不影响实际网络）
EXPOSE 8080

# JVM 启动命令
ENTRYPOINT ["java", \
  "-XX:+UseContainerSupport", \
  "-XX:MaxRAMPercentage=75.0", \
  "-XX:+HeapDumpOnOutOfMemoryError", \
  "-XX:HeapDumpPath=/app/logs/heapdump.hprof", \
  "-jar", "app.jar"]
```

**多阶段构建的底层优势**：

| 对比项 | 单阶段 | 多阶段 |
|---|---|---|
| 镜像大小 | ~800MB（含 Maven + 源码） | ~250MB（仅 JRE + jar） |
| 安全风险 | 编译工具暴露在运行时 | 运行时镜像极简 |
| 构建缓存 | 源码改动 → 全部重来 | 依赖层缓存命中 → 只重建应用层 |

### 1.3 镜像拉取策略（imagePullPolicy）

```yaml
containers:
- name: order-service
  image: registry.example.com/order-service:v2.1.0
  imagePullPolicy: IfNotPresent  # ← 这个参数的底层行为
```

三种策略的底层行为：

```
imagePullPolicy: Always
  → kubelet 每次创建容器前都向 registry 发 HEAD 请求
  → 检查 manifest 的 digest 是否变化
  → 如果变化 → 拉取新 Layer
  → 适合：latest 标签（不推荐生产使用）

imagePullPolicy: IfNotPresent
  → kubelet 先检查本地（containerd 的 content store）
  → 本地有 → 直接用
  → 本地没有 → 拉取
  → 适合：tag 语义化版本（如 v2.1.0）

imagePullPolicy: Never
  → 纯本地，不存在就报错
  → 适合：本地开发测试
```

**生产环境的隐性问题**：当使用 `IfNotPresent` 并且 tag 不变（如 `latest` 或同一个版本号反复覆盖推送），kubelet 不会拉取新镜像。解决方案：

```yaml
# 方案一：使用不可变 tag（推荐）
image: registry.example.com/order-service:v2.1.0-build.456

# 方案二：使用 digest
image: registry.example.com/order-service@sha256:a1b2c3d4...

# 方案三：使用 CI/CD 变量注入唯一 tag
image: registry.example.com/order-service:${CI_COMMIT_SHA:0:8}
```

### 1.4 私有仓库认证的底层机制

```yaml
# 1. 创建 Secret
# kubectl create secret docker-registry regcred \
#   --docker-server=registry.example.com \
#   --docker-username=admin \
#   --docker-password=xxx

apiVersion: v1
kind: Pod
spec:
  imagePullSecrets:
  - name: regcred        # ← kubelet 使用这个 Secret 拉取私有镜像
  containers:
  - name: app
    image: registry.example.com/order-service:v2.1.0
```

**底层流程**：
```
kubelet 发现 imagePullSecrets
    │
    ▼
从 Secret 中读取 .dockerconfigjson
    │
    ▼
base64 解码 → 得到 registry URL + username + password
    │
    ▼
containerd 向 registry 发起认证请求
    │
    ▼
registry 返回 token → containerd 缓存 token
    │
    ▼
用 token 拉取镜像 Layers
```

**企业级做法**：使用 **Harbor** 作为私有镜像仓库，配合 K8s 的 `ServiceAccount` 自动注入 `imagePullSecrets`：

```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: default
  namespace: production
imagePullSecrets:
- name: harbor-pull-secret   # 命名空间级别的默认拉取凭证
```

## 二、环境变量（Env）配置的底层细节

### 2.1 环境变量注入的四种方式

#### 方式一：直接硬编码

```yaml
env:
- name: SPRING_PROFILES_ACTIVE
  value: "production,k8s"
```

底层：kubelet 通过 CRI 的 `CreateContainer` 请求，将 env 传给 containerd → runc → 在容器进程的 `environ` 文件中写入。

#### 方式二：从 ConfigMap 引用

```yaml
env:
- name: NACOS_SERVER_ADDR
  valueFrom:
    configMapKeyRef:
      name: common-config      # ConfigMap 名称
      key: nacos-addr          # ConfigMap 中的 key
      optional: true           # 不存在时不阻止 Pod 启动
```

**底层机制**：
```
kubelet watch 到 Pod 调度到本节点
    │
    ▼
kubelet 调用 APIServer 获取 ConfigMap "common-config"
    │
    ▼
从 ConfigMap.data["nacos-addr"] 取值
    │
    ▼
注入到容器进程的环境变量
    │
    ▼
进程启动时通过 System.getenv("NACOS_SERVER_ADDR") 读取
```

**关键限制**：环境变量注入是在**容器创建时**完成的，**ConfigMap 后续修改不会反映到已运行的容器中**（这和 Volume 挂载不同）。

#### 方式三：从 Secret 引用

```yaml
env:
- name: DB_PASSWORD
  valueFrom:
    secretKeyRef:
      name: db-credentials
      key: password
```

**底层安全机制**：
- Secret 存储在 etcd 中，默认以 base64 编码（不是加密！）
- 启用 `EncryptionConfiguration` 后，etcd 中存储的是加密后的数据
- kubelet 通过 **Node 上的 tmpfs** 挂载 Secret，不落盘到 node 的文件系统
- 环境变量注入后，`/proc/<pid>/environ` 文件中是**明文**（安全隐患！）

**因此企业级建议**：敏感配置（密码、Token）优先用 **Volume 挂载 Secret 文件**，而不是环境变量：

```yaml
# 更安全的做法
volumes:
- name: secret-volume
  secret:
    secretName: db-credentials
containers:
- volumeMounts:
  - name: secret-volume
    mountPath: /etc/secrets
    readOnly: true
```

#### 方式四：Downward API（从 Pod 自身元数据注入）

```yaml
env:
- name: POD_NAME
  valueFrom:
    fieldRef:
      fieldPath: metadata.name
- name: POD_IP
  valueFrom:
    fieldRef:
      fieldPath: status.podIP
- name: NODE_NAME
  valueFrom:
    fieldRef:
      fieldPath: spec.nodeName
- name: POD_NAMESPACE
  valueFrom:
    fieldRef:
      fieldPath: metadata.namespace
```

**Spring Cloud 中的实际用途**：

```yaml
env:
- name: POD_NAME
  valueFrom:
    fieldRef:
      fieldPath: metadata.name
# Spring Boot 日志中标识具体 Pod
- name: LOGGING_PATTERN_CONSOLE
  value: "%d{HH:mm:ss} [${POD_NAME}] %-5level %logger{36} - %msg%n"
```

### 2.2 环境变量优先级与覆盖机制

```
Spring Boot 应用读取配置的优先级（从高到低）：

1. 命令行参数    --server.port=9090
2. 环境变量      SERVER_PORT=9090     ← K8s env 注入的
3. application-{profile}.yml
4. application.yml
5. @PropertySource 注解
6. 默认值
```

**K8s env 的命名转换规则**：

```yaml
# K8s 中的环境变量
env:
- name: SPRING_DATASOURCE_URL
  value: "jdbc:mysql://mysql:3306/order"
```

Spring Boot 会自动将 `SPRING_DATASOURCE_URL` 映射为 `spring.datasource.url`：
- 大写 → 小写
- 下划线 `_` → 点 `.`

这意味着你**不需要修改任何 application.yml**，直接通过 K8s 环境变量就能覆盖 Spring Boot 的任何配置。

## 三、多微服务互相连接的底层细节

这是最关键的部分。在 K8s 上，多个 Spring Cloud 微服务之间的通信涉及好几层机制。

### 3.1 服务发现：K8s Service 的底层原理

```yaml
apiVersion: v1
kind: Service
metadata:
  name: order-service
  namespace: production
spec:
  selector:
    app: order-service          # ← 匹配 Pod 的 label
  ports:
  - port: 8080                  # Service 端口
    targetPort: 8080            # Pod 端口
    protocol: TCP
  type: ClusterIP               # 默认类型，集群内部访问
```

**底层数据链路（iptables 模式）**：

```
Step 1: Endpoints Controller（运行在 Controller Manager 中）
        watch Service 和 Pod 变化
        维护 Endpoints 对象（记录所有健康 Pod 的 IP:Port）

Step 2: kube-proxy watch Endpoints 变化
        更新 Node 上的 iptables 规则

Step 3: 当 Pod-A 调用 order-service
        Pod-A → DNS 解析 order-service.production.svc.cluster.local → 10.96.0.100 (ClusterIP)
        → iptables PREROUTING 链匹配
        → DNAT 到某个真实 Pod IP（如 10.244.1.5:8080）
        → 经 CNI 网络插件路由到目标 Pod
```

**iptables 规则的底层（kube-proxy 实际写入的内容）**：

```bash
# 在每个 Node 上，kube-proxy 维护了这些链
-A KUBE-SERVICES -d 10.96.0.100/32 -p tcp --dport 8080 \
  -j KUBE-SEP-XXXXX    # SEP = Service EndPoint

# KUBE-SEP-XXXXX 链（概率选择后端）
-A KUBE-SEP-XXXXX -p tcp -j DNAT --to-destination 10.244.1.5:8080
-A KUBE-SEP-YYYYY -p tcp -j DNAT --to-destination 10.244.2.8:8080
-A KUBE-SEP-ZZZZZ -p tcp -j DNAT --to-destination 10.244.3.3:8080
```

### 3.2 DNS 解析的底层流程

```
Pod 内 /etc/resolv.conf：
nameserver 10.96.0.10      ← ClusterIP of CoreDNS
search production.svc.cluster.local svc.cluster.local cluster.local
ndots:5
```

当应用代码发起 `http://order-service:8080/api/orders`：

```
Java DNS 解析 "order-service"
    │
    ▼
Linux glibc 按 search 域名依次尝试：
    1. order-service.production.svc.cluster.local  ← 命中！
    2. order-service.svc.cluster.local
    3. order-service.cluster.local
    4. order-service（外部 DNS）
    │
    ▼
请求发到 CoreDNS (10.96.0.10)
    │
    ▼
CoreDNS 查询本地缓存 → 返回 ClusterIP 10.96.0.100
    │
    ▼
TTL 由 CoreDNS 配置决定（默认 5s 或 30s）
    │
    ▼
Java 进程缓存 DNS 结果（受 JVM networkaddress.cache.ttl 控制）
```

**JVM DNS 缓存陷阱**：
```java
// JVM 默认永久缓存 DNS！Service IP 变了但 JVM 还在用旧 IP
// 必须在启动时设置：
-Dnetworkaddress.cache.ttl=30        // 成功解析缓存 30 秒
-Dnetworkaddress.cache.negative.ttl=10  // 失败缓存 10 秒
```

### 3.3 一次完整的微服务调用链路（Spring Cloud Feign + K8s）

假设 `user-service` 通过 Feign 调用 `order-service`：

```
┌──────────────────────────────────────────────────────────────────┐
│                        user-service Pod                          │
│                                                                  │
│  ① @FeignClient("order-service")                               │
│     │                                                            │
│     ▼                                                            │
│  ② Spring Cloud LoadBalancer                                    │
│     从 K8s Service endpoints 获取 Pod IP 列表                    │
│     （或直接 DNS 解析到 ClusterIP）                               │
│     │                                                            │
│     ▼                                                            │
│  ③ HTTP 请求: GET http://order-service:8080/api/orders          │
│     │                                                            │
│     ▼                                                            │
│  ④ Java DNS 解析 → ClusterIP 10.96.0.100                       │
│     │                                                            │
│     ▼                                                            │
│  ⑤ Linux TCP 连接 → Pod 网络命名空间 → veth pair → bridge       │
│     │                                                            │
│     ▼                                                            │
│  ⑥ iptables DNAT → 真实 Pod IP 10.244.1.5:8080                 │
│     │                                                            │
│     ▼                                                            │
│  ⑦ CNI 路由（Calico/Flannel）                                  │
│     │  - 同节点：直接 bridge 转发                                │
│     │  - 跨节点：VXLAN 封装 / BGP 路由                           │
│     │                                                            │
│     ▼                                                            │
│  ⑧ 目标 order-service Pod 接收请求                               │
│     │                                                            │
│     ▼                                                            │
│  ⑨ 处理业务 → 返回 JSON 响应                                    │
│     │                                                            │
│     ▼                                                            │
│  ⑩ 响应原路返回                                                  │
└──────────────────────────────────────────────────────────────────┘
```

### 3.4 Service Mesh（Istio）下的连接底层

当引入 Istio 后，每个 Pod 中会注入 **Envoy sidecar**：

```
┌─────────────────────────────────────────────────┐
│  Pod: user-service                               │
│                                                  │
│  ┌──────────┐     ┌──────────────────────────┐  │
│  │ Spring   │     │   Envoy Sidecar          │  │
│  │ Boot App │     │                          │  │
│  │          │     │  inbound: 15006          │  │
│  │ 8080 ◄─────iptables──────┐               │  │
│  │          │     │          │               │  │
│  │          │     │  outbound: 15001         │  │
│  │    ────────iptables──────┐               │  │
│  └──────────┘     │          │               │  │
│                   └──────────┼───────────────┘  │
└──────────────────────────────┼──────────────────┘
                               │
                    mTLS 加密 + 负载均衡
                               │
                    ┌──────────▼──────────────────┐
                    │  Pod: order-service          │
                    │  ┌──────────┐ ┌───────────┐ │
                    │  │ Spring   │ │  Envoy    │ │
                    │  │ Boot ◄─────inbound:15006│ │
                    │  │ 8080     │ │           │ │
                    │  └──────────┘ └───────────┘ │
                    └─────────────────────────────┘
```

**iptables 拦截规则（Istio 注入时自动设置）**：

```bash
# 出站流量拦截（所有 TCP 出站流量 → Envoy）
-A ISTIO_OUTPUT -j ISTIO_REDIRECT
-A ISTIO_REDIRECT -p tcp -j REDIRECT --to-ports 15001

# 入站流量拦截（所有 TCP 入站流量 → Envoy）
-A ISTIO_IN_REDIRECT -p tcp -j REDIRECT --to-ports 15006
-A PREROUTING -j ISTIO_INBOUND
-A ISTIO_INBOUND -p tcp --dport 8080 -j ISTIO_IN_REDIRECT
```

**Envoy 做了什么**：
- 服务发现：从 Istiod（控制平面）获取服务端点列表
- 负载均衡：算法可选 round_robin、least_conn、random
- mTLS：自动对服务间流量加密
- 重试/超时/熔断：在 L7 层实现
- 分布式追踪：自动注入 trace headers

### 3.5 服务间通信的网络延迟分析

| 路径 | 延迟 | 原因 |
|---|---|---|
| 同节点 Pod → Pod（无 mesh） | ~0.1ms | bridge 转发 |
| 跨节点 Pod → Pod（无 mesh） | ~0.3-1ms | VXLAN 封装 / BGP |
| Service ClusterIP → Pod | +0.05ms | iptables DNAT 开销极小 |
| Istio sidecar → sidecar | +1-3ms | 两次 Envoy 代理 + mTLS 握手（长连接后 ~0.5ms） |

### 3.6 Headless Service（直连 Pod IP 场景）

某些场景下需要绕过 ClusterIP 直连 Pod：

```yaml
apiVersion: v1
kind: Service
metadata:
  name: order-service-headless
spec:
  clusterIP: None          # ← Headless！
  selector:
    app: order-service
  ports:
  - port: 8080
```

**DNS 解析行为变化**：
```
# 普通 Service → 返回 ClusterIP
nslookup order-service → 10.96.0.100

# Headless Service → 返回所有 Pod IP
nslookup order-service-headless →
  10.244.1.5
  10.244.2.8
  10.244.3.3
```

**使用场景**：有状态服务（如数据库集群、MQ 集群）、需要客户端自定义负载均衡策略的场景、Spring Cloud LoadBalancer 直接获取 Pod IP 做客户端负载均衡。

**服务间调用链**：
```
外部请求 → Ingress Controller → gateway-service
  → user-service  (K8s Service /order-service)
  → order-service (K8s Service /user-service)
  → pay-service   (K8s Service /pay-service)
  → Nacos (服务注册 + 配置)
  → MySQL / Redis / Kafka
```
