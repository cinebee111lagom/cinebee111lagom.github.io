## 一、Megatron-LM — 训练框架深度解析

### 1. Tensor Parallelism（TP）— 单层内的参数切分

**核心思想：** 将单个 Transformer 层的权重矩阵沿某个维度切分到多张 GPU 上，每张 GPU 只持有部分参数，通过集合通信（AllReduce / AllGather）拼回完整结果。

#### MLP 层的切分方式

```
一个标准 MLP 层：Y = GeLU(X · W1) · W2

# 第一个线性层 W1 —— 按列切分（Column Parallel）
W1 ∈ R^{h × 4h}  切分为 [W1_a, W1_b]，各 ∈ R^{h × 2h}
GPU_0 计算: Y_a = GeLU(X · W1_a)    # 无需通信，GeLU 可以逐元素计算
GPU_1 计算: Y_b = GeLU(X · W1_b)

# 第二个线性层 W2 —— 按行切分（Row Parallel）
W2 ∈ R^{4h × h}  切分为上下两块，各 ∈ R^{2h × h}
GPU_0 计算: Z_a = Y_a · W2_a
GPU_1 计算: Z_b = Y_b · W2_b

# 最终结果：Z = Z_a + Z_b（一次 AllReduce 即可）
```

**为什么这样设计？** 如果 W1 按行切分，那 GeLU(非线性激活)就无法直接计算了——需要先 AllGather 完整的中间结果，通信量大幅增加。**Column-then-Row 的配对模式保证每层只需一次 AllReduce。**

#### Self-Attention 层的切分方式

```
Q, K, V 的投影矩阵 W_Q, W_K, W_V ∈ R^{h × h}

# 按 head 维度切分（本质是按列切分）
假设 32 个 head，TP=8，则每张 GPU 负责 4 个 head

GPU_0: Q_0, K_0, V_0 → 注意力计算 → O_0
GPU_1: Q_1, K_1, V_1 → 注意力计算 → O_1
...
# 输出投影 W_O 按行切分
GPU_i 计算 O_i · W_O_i，再 AllReduce 求和
```

**关键细节：** Attention 的 dropout mask 在所有 TP rank 上必须一致，否则 AllReduce 后结果错误。Megatron 通过固定随机种子解决。

#### 通信开销分析

```
单层 TP 通信量：
  Forward:  1 次 AllReduce（MLP） + 1 次 AllReduce（Attention）= 2 次
  Backward: 同样 2 次 AllReduce
  每次 AllReduce 通信量 = 2 × (N-1)/N × 数据量（Ring AllReduce）

数据量 = batch_size × seq_len × hidden_dim × sizeof(fp16)
例如: 4 × 2048 × 4096 × 2B = 64MB per AllReduce

NVLink 600GB/s → 单次 AllReduce(8 GPU, Ring) 约 0.15ms
PCIe 64GB/s   → 同样情况约 1.5ms（慢 10 倍）
```

这就是为什么 **TP 只在节点内使用**——它每层都要通信，对带宽极其敏感。

### 2. Pipeline Parallelism（PP）— 跨层切分

**核心思想：** 将模型的 N 层均分到 P 个 stage，每个 stage 在不同 GPU 上。

#### Pipeline 调度——以 1F1B 为例

```
假设 4 个 stage (S0, S1, S2, S3)，8 个 micro-batch

经典 GPipe（先全部 Forward，再全部 Backward）：
时间 →  [F1][F2][F3][F4][F5][F6][F7][F8] ..... [B8][B7][B6][B5][B4][B3][B2][B1]
        ↑ 中间全是 bubble（气泡），GPU 空等

1F1B 调度（Megatron 的选择）：
Warmup 阶段：逐步填满 pipeline
Steady 阶段：交替执行 1 次 Forward + 1 次 Backward

S0: [F1][F2][F3][F4] [B1][F5][B2][F6][B3][F7][B4][F8] [B5][B6][B7][B8]
S1: ___[F1][F2][F3] [B1][F4][B2][F5][B3][F6][B4][F7] [B5][B6][B7][B8]
S2: ______[F1][F2] [B1][F3][B2][F4][B3][F5][B4][F6] [B5][B6][B7][B8]
S3: ________[F1] [B1][F2][B2][F3][B3][F4][B4][F5] [B5][B6][B7][B8]

Bubble 比例 = (P-1) / (P-1 + 2×M)
  P=stage数, M=micro-batch数
  M=8, P=4 → bubble率 = 3/19 ≈ 15.8%
  M=32, P=4 → bubble率 = 3/67 ≈ 4.5%（micro-batch 越多越高效）
```

#### 通信模式

```
PP 的通信发生在相邻 stage 之间：
  Forward: stage_i → stage_{i+1}  发送 activation tensor
  Backward: stage_{i+1} → stage_i  发送 gradient tensor

通信量 = batch_size × seq_len × hidden_dim × sizeof(fp16)
通信模式 = Point-to-Point（P2P send/recv），不是集合通信

可以用异步通信重叠：
  stage_i 发送 activation 给 stage_{i+1} 的同时
  stage_i 可以开始处理下一个 micro-batch 的 backward
```

#### 虚拟 Pipeline Parallelism

```
传统 PP：每层只属于一个 stage
  问题：stage 数增加时 bubble 急剧增长

虚拟 PP（Megatron 的优化）：
  将模型分成更多更小的 chunk，交替调度
  
  例如 24 层 / 4 stage = 每 stage 6 层
  虚拟 PP=2 → 每 stage 变成 2 个 chunk，每个 3 层
  调度变为交替发送 2 个 chunk 的 F/B
  
  Bubble 率降低，但通信次数增加（trade-off）
```

### 3. Data Parallelism（DP）— 最朴素但有优化

#### ZeRO（Megatron 也集成了类似优化）

```
传统 DP：
  每张 GPU 持有完整模型副本
  8 GPU 训练 7B 模型 → 每卡需约 14GB 参数(fp16) + 优化器状态 ≈ 56GB

ZeRO-1: 切分优化器状态（Adam 的 m 和 v）
  每卡只保存 1/8 的优化器状态，计算完梯度后 AllReduce 梯度
  
ZeRO-2: + 切分梯度
  每卡只保存自己负责那部分参数的梯度
  
ZeRO-3: + 切分参数
  每卡只保存 1/P 的模型参数，Forward/Backward 时动态 AllGather

通信量对比：
  DP:     每步 AllReduce 梯度，通信量 = 2 × model_size
  ZeRO-3: 每步 AllGather 参数 × 2(F+B) + ReduceScatter 梯度
          通信量 = 3 × model_size（多了 1.5 倍，但显存大幅降低）
```

#### 3D 并行的实际配置

```
以 256 GPU 训练 175B 模型为例：
  TP=8（节点内 8 GPU，NVLink 互联）
  PP=16（16 个 stage，跨节点）
  DP=2（2 路数据并行）
  8 × 16 × 2 = 256 GPU ✓

通信拓扑：
  TP 通信：节点内 NVLink（600GB/s）  ← 最频繁，要求最高带宽
  PP 通信：跨节点 IB（400Gbps）      ← P2P，频率中等
  DP 通信：跨节点 IB + NVSwitch      ← AllReduce，可以和计算重叠
```

### 4. Sequence Parallelism（SP）

```
问题：LayerNorm 和 Dropout 在 TP 下仍然需要完整的 activation
  每张 GPU 都存储完整序列的 LN 输出 → 显存浪费

SP 的方案：
  将 TP 切分之外的部分（LN, Dropout, 残差连接）沿序列维度切分
  
  TP 区域（Attention, MLP）：每卡有完整序列，部分 head/FFN
  SP 区域（LN, Dropout）：每卡有完整 hidden，部分 sequence

通信变化：
  原来 TP 边界是 AllReduce（ReduceScatter + AllGather）
  现在拆开：
    Forward 进入 TP 区域前：AllGather sequence 维度
    Forward 离开 TP 区域后：ReduceScatter sequence 维度
  等价替换，通信量相同，但显存节省（LN 的 activation 只存 1/TP）

显存节省比例：
  激活值中的 LN + Dropout 占比约 10-15%
  SP 将这部分除以 TP 度数
```

### 5. 训练中的工程细节

#### 混合精度训练

```
Forward/Backward: FP16 计算
参数更新: FP32 master copy

为什么？
  梯度可能非常小（如 1e-7），FP16 的最小正数 ~6e-8
  直接用 FP16 更新 → 小梯度被截断 → 训练不稳定

Loss Scaling：
  FP16 的动态范围有限，梯度容易下溢
  先乘以 scale factor（如 1024），计算完梯度再除回去
  动态调整 scale：连续 N 步无 overflow → scale × 2
                   出现 overflow → scale / 2, 跳过本步更新
```

#### FlashAttention 在 Megatron 中的集成

```
标准 Attention 计算：
  S = Q · K^T          → 存储 N×N 的注意力矩阵（显存爆炸）
  P = softmax(S)
  O = P · V

FlashAttention（分块计算）：
  将 Q, K, V 按 block 切分
  对每个 Q block，遍历所有 K/V block：
    计算局部 S_ij
    在线更新 softmax（用 running max 和 running sum）
    累加局部输出 O_i += P_ij · V_j
  
  关键：不需要存储完整的 N×N 注意力矩阵
  显存从 O(N²) 降到 O(N)
  计算量相同，但 IO 减少（HBM 访问减少）→ 实际速度更快
```

## 二、vLLM — 推理框架深度解析

### 1. PagedAttention 核心机制

#### 传统 KV Cache 的问题

```
场景：一个请求最大长度 2048，模型 32 层，64 头，head_dim=128

传统方式预分配：
  单请求 KV Cache = 2(K+V) × 32层 × 64头 × 128维 × 2048序列 × 2B(fp16)
                  = 2 × 32 × 64 × 128 × 2048 × 2 = 2.15 GB
  
  80GB A100 → 只能同时处理 ~30 个请求
  但实际平均长度可能只有 256 tokens → 87.5% 显存浪费！
```

#### PagedAttention 的实现

```
Block 设计：
  block_size = 16 tokens（可配置，通常 16 或 32）
  一个 block 存储 16 个 token 的 KV Cache
  结构：[num_layers=2, 2(K+V), num_heads=64, block_size=16, head_dim=128]
  
  单 block 显存 = 2 × 2 × 64 × 16 × 128 × 2B = 1MB

Block Table（页表）：
  类似操作系统的页表，每个请求维护一个 block_table
  逻辑上连续的 token → 物理上分散的 GPU 显存块

  请求 "Hello world how are you today"
  block_table = [42, 17, 89, ...]  （物理 block 编号）
  token 0-15 → 物理 block 42
  token 16-31 → 物理 block 17
  ...

内存池管理：
  初始化时预分配一大块显存，切成固定大小的 block
  维护一个 free_blocks 列表
  
  分配：从 free_blocks 弹出 → 加入请求的 block_table
  释放：从 block_table 取出 → 放回 free_blocks
  没有碎片化问题（所有 block 大小相同）
```

#### PagedAttention 的计算内核

```python
# 伪代码：带 PagedAttention 的 Attention 计算

def paged_attention(query, key_cache, value_cache, block_table, context_len):
    """
    query: [num_heads, head_dim]  当前 token 的 Q
    key_cache: [num_blocks, block_size, num_heads, head_dim]  全局 KV 池
    value_cache: 同上
    block_table: [max_num_blocks]  当前请求的物理 block 映射
    """
    output = zeros(num_heads, head_dim)
    max_score = -inf
    exp_sum = 0
    
    num_blocks = ceil(context_len / block_size)
    
    for i in range(num_blocks):
        physical_block_idx = block_table[i]
        
        # 从物理 block 取出 K/V
        k_block = key_cache[physical_block_idx]    # [block_size, num_heads, head_dim]
        v_block = value_cache[physical_block_idx]
        
        # 计算局部注意力分数
        scores = query @ k_block.T / sqrt(head_dim)  # [num_heads, block_size]
        
        # 在线 softmax（FlashAttention 思想）
        block_max = max(scores)
        new_max = max(max_score, block_max)
        
        # 修正之前的累积值
        correction = exp(max_score - new_max)
        exp_sum = exp_sum * correction + sum(exp(scores - new_max))
        output = output * correction + exp(scores - new_max) @ v_block
        max_score = new_max
    
    output /= exp_sum
    return output
```

#### Copy-on-Write（CoW）—— Beam Search 共享

```
Beam Search 场景：
  一个 prompt 生成 4 个 beam
  所有 beam 的 prompt 部分 KV Cache 完全相同

PagedAttention 的做法：
  4 个 beam 的 block_table 指向相同的物理 block
  并增加引用计数 ref_count[block_id] += 1

  当某个 beam 需要修改（如生成了不同的 token）：
    检测到 ref_count > 1 → 复制该 block（CoW）
    新 beam 使用复制后的 block
    ref_count[block_id] -= 1, ref_count[new_block_id] = 1

  节省：prompt 长 1024 tokens, beam=4
    传统：4 × 1024 tokens KV Cache
    PagedAttention：1 × 1024 tokens + 各 beam 独立部分
```

### 2. Continuous Batching（连续批处理）

#### 传统 Static Batching 的问题

```
Static Batching（朴素方式）：
  
  时间 →  [Req1: ████████████]   ← 长请求
          [Req2: ██████          ]   ← 短请求，但必须等 Req1 完成
          [Req3: █████████       ]   ← 排队等待
  
  问题：
  1. 短请求等长请求 → 延迟高
  2. 请求完成后 batch 变小 → GPU 利用率下降
  3. 新请求必须等整个 batch 完成 → 排队延迟
```

#### Continuous Batching 的实现

```
核心概念：iteration 级别的调度，而非 request 级别

每个 iteration（生成 1 个 token）后，调度器做决策：
  1. 检查哪些请求完成了（遇到 EOS 或达到 max_tokens）→ 移出 batch
  2. 检查 waiting queue 中有没有新请求 → 满足条件则加入 batch
  3. 重新组装 batch，继续下一个 iteration

时间 →
  Iter 1: [R1(tok1), R2(tok1), R3(tok1)]           ← 3 个请求 prefill
  Iter 2: [R1(tok2), R2(tok2), R3(tok2), R4(tok1)] ← R4 加入
  Iter 3: [R1(tok3), R2(tok3), R3(tok3), R4(tok2)]
  Iter 4: [R1(tok4), R2(DONE), R3(tok4), R4(tok3)] ← R2 完成
  Iter 5: [R1(tok5), R3(tok5), R4(tok4), R5(tok1)] ← R5 替换 R2
```

#### Prefill vs Decode 分离

```
Prefill 阶段（处理 prompt）：
  计算密集型：prompt 可能有数千 tokens，矩阵乘法大
  使用 GEMM kernel，GPU 利用率高
  一次性计算所有 prompt token 的 KV Cache

Decode 阶段（逐 token 生成）：
  访存密集型：每步只计算 1 个新 token，batch_size × hidden 的 GEMV
  大量时间花在读取 KV Cache（HBM 带宽瓶颈）
  GPU 计算单元利用率很低

vLLM 的处理：
  将 prefill 请求和 decode 请求分开处理
  Chunked Prefill：长 prompt 分成多个 chunk，与 decode 请求交错执行
  避免一个长 prefill 阻塞所有 decode 请求
  
  Iteration 级别调度决策：
    如果有 GPU 显存预算 + waiting queue 有请求：
      优先处理 prefill（吞吐优先）
      或优先保障 decode（延迟优先，可配置）
```

### 3. Preemption（抢占机制）

```
场景：显存不足，无法容纳新请求的 KV Cache

方案 1 — Swap（换出到 CPU）：
  选择优先级最低的请求（如最长等待时间的反直觉策略 → 选最短的？不）
  通常选择：已经生成最多 token 的请求（接近完成，换出代价大但回来后很快完成）
  或者：最少剩余生成量的请求？策略可配置
  
  执行步骤：
    1. 将该请求的所有 KV Cache block 内容复制到 CPU 内存（pinned memory）
    2. 释放 GPU block（加入 free_blocks）
    3. 为新请求分配 block
  
  恢复步骤：
    GPU 有空间时，将 CPU 上的 KV Cache 复制回来
    重新分配 GPU block，填充数据，继续 decode

方案 2 — Recompute（重新计算）：
  直接丢弃 KV Cache
  恢复时从 prompt 重新 prefill
  适合短 prompt 场景（重计算代价 < 换出/换入的 PCIe 传输代价）

选择策略：
  Swap: prompt 长，重计算代价大，CPU 内存充足
  Recompute: prompt 短，PCIe 带宽紧张，CPU 内存也紧张
```

### 4. 调度器的内存管理器细节

```python
class BlockSpaceManager:
    def __init__(self, num_gpu_blocks, num_cpu_blocks, block_size):
        self.block_size = block_size
        # GPU 上的空闲 block 队列
        self.gpu_free_blocks = list(range(num_gpu_blocks))
        # CPU 上的空闲 block 队列（用于 swap）
        self.cpu_free_blocks = list(range(num_cpu_blocks))
        # 每个请求的 block_table: req_id -> [物理block列表]
        self.block_tables = {}
    
    def can_allocate(self, num_tokens):
        needed = ceil(num_tokens / self.block_size)
        return len(self.gpu_free_blocks) >= needed
    
    def allocate(self, req_id, num_tokens):
        needed = ceil(num_tokens / self.block_size)
        blocks = []
        for _ in range(needed):
            block_id = self.gpu_free_blocks.pop()
            blocks.append(block_id)
        self.block_tables[req_id] = blocks
    
    def append_token(self, req_id):
        """生成新 token 时，可能需要分配新 block"""
        table = self.block_tables[req_id]
        # 检查最后一个 block 是否已满
        if len(table) * self.block_size == table[-1].used_slots + 1:
            # 需要新 block
            new_block = self.gpu_free_blocks.pop()
            table.append(new_block)
    
    def swap_out(self, req_id):
        """将请求的 KV Cache 换出到 CPU"""
        gpu_blocks = self.block_tables[req_id]
        cpu_blocks = []
        for g_block in gpu_blocks:
            c_block = self.cpu_free_blocks.pop()
            # 异步复制 GPU → CPU
            copy_block_gpu_to_cpu(g_block, c_block)
            self.gpu_free_blocks.append(g_block)
            cpu_blocks.append(c_block)
        self.block_tables[req_id] = cpu_blocks  # 标记在 CPU 上
    
    def swap_in(self, req_id):
        """将请求的 KV Cache 换入到 GPU"""
        cpu_blocks = self.block_tables[req_id]
        gpu_blocks = []
        for c_block in cpu_blocks:
            g_block = self.gpu_free_blocks.pop()
            copy_block_cpu_to_gpu(c_block, g_block)
            self.cpu_free_blocks.append(c_block)
            gpu_blocks.append(g_block)
        self.block_tables[req_id] = gpu_blocks
```

### 5. vLLM 的 Kernel 层优化

```
1. 融合的 KV Cache 写入 kernel：
   每次 decode 生成新 token 的 K, V 向量
   需要写入对应 block 的正确位置
   融合了：位置计算 + block_table 查找 + scatter write
   
2. 融合的 Attention kernel（支持 PagedAttention）：
   基于 FlashAttention 思想的分块计算
   额外增加了 block_table 的间接寻址
   支持 variable-length（不同请求长度不同，在一个 kernel 中处理）

3. 量化推理 kernel：
   AWQ / GPTQ / FP8 量化矩阵乘法
   权重反量化和 GEMM 融合，减少中间结果的显存读写

4. CUDA Graph：
   Decode 阶段计算图固定（batch_size 固定时）
   提前录制 CUDA Graph → 消除 kernel launch overhead
   问题：batch_size 变化时需要重新录制
   vLLM 维护多个 batch_size 的 CUDA Graph 缓存
   超出预设范围时 fallback 到普通执行
```

### 6. Prefix Caching（前缀缓存）

```
场景：大量请求共享相同的 system prompt
  System prompt: "You are a helpful assistant..." (500 tokens)
  每个请求都需要重新计算这 500 tokens 的 KV Cache

vLLM 的 RadixAttention：
  用 Radix Tree（基数树）索引 token 序列
  相同前缀的请求共享 KV Cache block
  
  请求1: [system_prompt(500) + user_query_A(50)]
  请求2: [system_prompt(500) + user_query_B(30)]
  
  Radix Tree:
    root
    └── system_prompt (500 tokens) → block [10, 11, 12, ...] ref_count=2
        ├── user_query_A (50 tokens) → block [30, 31] ref_count=1
        └── user_query_B (30 tokens) → block [50] ref_count=1
  
  请求2 完全跳过 system prompt 的 prefill → 延迟降低 80%+
  
  驱逐策略：LRU
    当 GPU block 不足时，驱逐最久未被使用的前缀缓存
    引用计数为 0 的 block 优先被驱逐
```

### 7. 请求调度优先级

```
vLLM 的 Scheduler 维护两个队列：
  waiting_queue: 等待 prefill 的新请求
  running_queue: 正在 decode 的请求

调度策略（可配置）：
  1. FCFS（先来先服务）：默认策略
  2. SJF（最短作业优先）：根据 prompt 长度排序，短的先 prefill
  3. 终止概率优先：估算请求的完成概率，接近完成的优先处理

调度循环：
  while True:
      # 1. 检查 running 中完成的请求 → 输出结果，释放 block
      # 2. 检查能否 prefill waiting 中的请求
      #    条件：(a) 有足够 GPU block (b) 不超过 batch_size 上限
      # 3. 执行一个 iteration（所有 running 请求生成 1 个 token）
      # 4. 检查是否需要 swap 或 recompute
```
