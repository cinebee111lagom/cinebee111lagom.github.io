## 二、类加载子系统（ClassLoader Subsystem）

### 2.1 类加载的完整生命周期

```
Loading → Linking → Initialization
           │
     ┌─────┼──────┐
     ▼     ▼      ▼
  Verify Prepare Resolution
```

七个阶段：

| 阶段 | 说明 |
|------|------|
| **Loading** | 通过全限定名获取字节流，在方法区生成 `java.lang.Class` 对象 |
| **Verification** | 校验字节码格式、语义合法性、符号引用验证 |
| **Preparation** | 为类的静态变量分配内存并设置零值（非赋值） |
| **Resolution** | 将符号引用替换为直接引用 |
| **Initialization** | 执行 `<clinit>()` 方法（类构造器） |
| **Using** | 使用阶段 |
| **Unloading** | 卸载（GC 回收 Class 对象） |

### 2.2 类加载器层次结构

```
Bootstrap ClassLoader (C++ 实现, rt.jar)
       │
       ▼
Extension/Platform ClassLoader (JDK 9+)
       │
       ▼
Application ClassLoader (classpath)
       │
       ▼
Custom ClassLoader (用户自定义)
```

**核心机制 —— 双亲委派模型（Parents Delegation）：**

```java
// java.lang.ClassLoader#loadClass 源码简化
protected Class<?> loadClass(String name, boolean resolve) 
    throws ClassNotFoundException {
    // 1. 检查是否已加载
    Class<?> c = findLoadedClass(name);
    if (c == null) {
        try {
            // 2. 委派给父加载器
            if (parent != null) {
                c = parent.loadClass(name, false);
            } else {
                // 3. 委派给 Bootstrap
                c = findBootstrapClassOrNull(name);
            }
        } catch (ClassNotFoundException e) {
            // 父加载器无法加载
        }
        if (c == null) {
            // 4. 自身尝试加载
            c = findClass(name);
        }
    }
    if (resolve) {
        resolveClass(c);
    }
    return c;
}
```

**双亲委派的意义：**
- 保证核心类库不被篡改（如 `java.lang.String` 始终由 Bootstrap 加载）
- 避免类的重复加载
- **破坏双亲委派的场景**：SPI（`Thread.getContextClassLoader()`）、OSGi、Tomcat 的 WebAppClassLoader、热部署

### 3.2 虚拟机栈（JVM Stack）—— 栈帧详解

每个方法调用对应一个**栈帧（Stack Frame）**：

```
┌───────────────────────────────────┐ ← 栈顶
│         Stack Frame N             │
│  ┌─────────────────────────────┐  │
│  │      Local Variable Table   │  │  方法参数 + 局部变量
│  │  Slot 0: this (实例方法)     │  │  按 slot 索引访问
│  │  Slot 1: arg0               │  │  long/double 占 2 slot
│  │  Slot 2: arg1               │  │
│  ├─────────────────────────────┤  │
│  │      Operand Stack          │  │  LIFO, 存放操作数
│  │      (操作数栈)               │  │  字节码指令在此弹出/压入
│  ├─────────────────────────────┤  │
│  │      Dynamic Linking         │  │  指向运行时常量池
│  │      (动态链接)               │  │  将符号引用→直接引用
│  ├─────────────────────────────┤  │
│  │      Return Address          │  │  方法返回后继续执行的地址
│  │      Method Exit Info        │  │  正常返回 or 异常退出
│  └─────────────────────────────┘  │
├───────────────────────────────────┤
│         Stack Frame N-1           │
├───────────────────────────────────┤
│              ...                   │
├───────────────────────────────────┤
│         Stack Frame 1             │
└───────────────────────────────────┘ ← 栈底
```

**字节码执行示例（操作数栈的工作）：**

```java
// Java 源码
int a = 1;
int b = 2;
int c = a + b;
```

```
// 对应字节码
0: iconst_1        // 将常量 1 压入操作数栈       [..., 1]
1: istore_1        // 弹出栈顶存入局部变量表[1]     [...]
2: iconst_2        // 将常量 2 压入操作数栈         [..., 2]
3: istore_2        // 弹出栈顶存入局部变量表[2]     [...]
4: iload_1         // 加载局部变量[1]到栈顶         [..., 1]
5: iload_2         // 加载局部变量[2]到栈顶         [..., 1, 2]
6: iadd            // 弹出两个操作数相加，结果入栈    [..., 3]
7: istore_3        // 弹出栈顶存入局部变量表[3]     [...]
```

### 3.5 对象创建的完整流程

```
new MyClass()
      │
      ▼
 ① 检查常量池中是否有该类的符号引用
      │
      ▼
 ② 类是否已加载、解析、初始化？ ──否──→ 触发类加载
      │ 是
      ▼
 ③ 为新对象分配内存
      │
      ├── 指针碰撞 (Bump the Pointer)
      │   堆内存规整时，用过的和空闲的中间放一个指针
      │   适用于: Serial, ParNew 等带压缩的收集器
      │
      └── 空闲列表 (Free List)
          堆内存不规整时，维护一个可用内存块的列表
          适用于: CMS 等不带压缩的收集器
      │
      ▼
 ④ 内存分配的线程安全问题
      │
      ├── CAS + 失败重试（乐观锁）
      └── TLAB (Thread Local Allocation Buffer)
          每个线程预先在 Eden 区分配一小块私有内存
          线程内分配无需同步，TLAB 用完再 CAS 重新分配
      │
      ▼
 ⑤ 内存空间初始化为零值
    (这就是为什么 int 默认是 0, boolean 默认是 false)
      │
      ▼
 ⑥ 设置对象头 (Mark Word + Klass Pointer)
      │
      ▼
 ⑦ 执行 <init>() 方法 (构造函数)
      │
      ▼
    对象创建完成
```

## 五、垃圾收集（Garbage Collection）

### 5.1 对象存活判定

**可达性分析算法（Reachability Analysis）：**

```
    GC Roots
    ┌──────┐
    │      │
    ▼      ▼
   [A]    [D]        ← 可达, 存活
    │      │
    ▼      ▼
   [B]    [E]        ← 可达, 存活
    │
    ▼
   [C]               ← 可达, 存活


   [F] ← [G]         ← 不可达, 可回收


  GC Roots 包括:
  ├── 虚拟机栈中引用的对象 (局部变量)
  ├── 方法区中 static 变量引用的对象
  ├── 方法区中 final 常量引用的对象
  ├── 本地方法栈中 JNI 引用的对象
  ├── JVM 内部引用 (基本类型 Class, 常驻异常, 系统类加载器)
  └── 被 synchronized 锁持有的对象
```

**两次标记过程（finalize() 机制）：**

```
对象不可达
    │
    ▼
第一次标记 → 是否覆盖 finalize()？──否──→ 直接回收
    │ 是
    ▼
是否已在 F-Queue 中？──是──→ 直接回收 (finalize 只执行一次)
    │ 否
    ▼
放入 F-Queue → Finalizer 线程执行 finalize()
    │
    ▼
第二次标记: finalize() 中是否重新建立了引用？
    │                          │
   是                           否
    │                          │
    ▼                          ▼
  移出回收集合                回收
```

> **注意：** `finalize()` 在 JDK 9 已被标记为 `@Deprecated`，不推荐使用。

### 5.2 垃圾收集算法

```
┌─────────────────────────────────────────────────────────────┐
│ 1. 标记-清除 (Mark-Sweep)                                    │
│                                                             │
│  █████░░░░██████░░████░░░░░                                 │
│    标记存活    清除死亡                                       │
│                                                             │
│  优点: 简单                                                  │
│  缺点: ① 效率不稳定 ② 内存碎片                               │
├─────────────────────────────────────────────────────────────┤
│ 2. 标记-复制 (Copying)                                       │
│                                                             │
│  ┌────────────┬────────────┐                                │
│  │  From      │    To      │                                │
│  │ ██░░██░██  │            │  复制存活对象到 To              │
│  └────────────┴────────────┘                                │
│           ↓               ↓                                 │
│  ┌────────────┬────────────┐                                │
│  │            │  ██ ██ ██  │                                │
│  │  (清空)    │    To      │                                │
│  └────────────┴────────────┘                                │
│  然后交换 From 和 To 角色                                    │
│                                                             │
│  优点: 无碎片, 分配快(指针碰撞)                               │
│  缺点: 空间利用率 50%                                        │
│  应用: Young Gen (Eden + 2 Survivor, 8:1:1)                  │
├─────────────────────────────────────────────────────────────┤
│ 3. 标记-整理 (Mark-Compact)                                  │
│                                                             │
│  █████░░░░██████░░████░░░░░                                 │
│       ↓ 移动存活对象到一端                                    │
│  ████████████████░░░░░░░░░░                                 │
│                                                             │
│  优点: 无碎片                                                │
│  缺点: 移动对象需要更新引用, STW 时间更长                      │
│  应用: Old Gen                                               │
├─────────────────────────────────────────────────────────────┤
│ 4. 分代收集 (Generational)                                   │
│                                                             │
│  根据对象存活周期将堆分为 Young / Old                         │
│  Young: 存活率低 → 复制算法                                  │
│  Old:   存活率高 → 标记-清除 或 标记-整理                     │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 垃圾收集器全景对比

```
                    Young           Old            整体
                   ─────────     ─────────      ─────────
  Serial          单线程复制      单线程标记整理    STW
  ParNew          多线程复制      ↓ 配合CMS        STW
  Parallel Scavenge 多线程复制    多线程标记整理    吞吐量优先
  ─────────────────────────────────────────────────────
  CMS             -              并发标记清除      低延迟
  G1              Region化       Region化         均衡
  ZGC             -              -                超低延迟
  Shenandoah      -              -                超低延迟
```

### 5.4 CMS 收集器详解

```
初始标记 ──→ 并发标记 ──→ 重新标记 ──→ 并发清除
(STW)       (与用户线程    (STW)       (与用户线程
 极快         并行)         较快         并行)

时间线:
────────────────────────────────────────────────────────→
   │      │                │      │
   │ STW  │   Concurrent   │ STW  │  Concurrent
   │      │                │      │
   ▼      ▼                ▼      ▼
  Init    Concurrent      Re-    Concurrent
  Mark    Mark            Mark   Sweep

缺点:
• CPU 敏感: 并发阶段占用 CPU 资源
• 浮动垃圾: 并发清除阶段产生的垃圾只能下次回收
• 内存碎片: 标记-清除算法导致
  → -XX:+UseCMSCompactAtFullCollection
  → CMS 提前触发 Full GC 的阈值: -XX:CMSInitiatingOccupancyFraction=92
```

### 5.5 G1 收集器（Region 化内存布局）

```
┌────────────────────────────────────────────────────┐
│                   G1 Heap                          │
│                                                    │
│  ┌────┬────┬────┬────┬────┬────┬────┬────┐        │
│  │ E  │ E  │ S  │ H  │    │ O  │ O  │    │        │
│  ├────┼────┼────┼────┼────┼────┼────┼────┤        │
│  │ O  │ E  │    │ H  │ H  │    │ E  │ O  │        │
│  ├────┼────┼────┼────┼────┼────┼────┼────┤        │
│  │    │ S  │ E  │    │ O  │ O  │ E  │    │        │
│  ├────┼────┼────┼────┼────┼────┼────┼────┤        │
│  │ E  │    │ O  │ O  │    │ E  │    │ O  │        │
│  ├────┼────┼────┼────┼────┼────┼────┼────┤        │
│  │ O  │ E  │    │ E  │ O  │    │ S  │ E  │        │
│  └────┴────┴────┴────┴────┴────┴────┴────┘        │
│                                                    │
│  E = Eden  S = Survivor  O = Old  H = Humongous    │
│  (空白 = 未使用)                                     │
│  每个 Region 1~32MB, 可动态充当不同角色              │
└────────────────────────────────────────────────────┘

G1 回收过程:
  Young GC → 并发标记 → Mixed GC

  1. Young GC (STW): 回收所有 Eden + Survivor Region
  2. 并发标记:
     ┌──────────┐   ┌──────────┐   ┌──────────┐
     │ 初始标记  │──→│ 并发标记  │──→│ 最终标记  │
     │ (STW)    │   │          │   │ (STW)    │
     └──────────┘   └──────────┘   └──────────┘
  3. Mixed GC: 回收 Young + 部分高垃圾比例的 Old Region
     → G1 维护每个 Region 的回收价值 (价值 = 回收获得空间 / 回收耗时)
     → 优先回收价值最高的 Region
     → -XX:MaxGCPauseMillis=200 (默认目标停顿时间)

核心参数:
  -XX:+UseG1GC
  -XX:G1HeapRegionSize=N  (Region 大小, 1~32MB, 2的幂)
  -XX:MaxGCPauseMillis=200
  -XX:G1NewSizePercent=5  (Young 最小比例)
  -XX:G1MaxNewSizePercent=60 (Young 最大比例)
```

### 5.6 ZGC（超低延迟收集器）

```
ZGC 核心技术:

1. 着色指针 (Colored Pointers) — 64位指针中嵌入 GC 元数据
   ┌─────────────────────────────────────────────────┐
   │ 0│ unused(16) │ flags(4) │ 44-bit address       │
   │  │            │ ┌──────┐ │                       │
   │  │            │ │Final │ │                       │
   │  │            │ │Remap │ │                       │
   │  │            │ │Marked│ │                       │
   │  │            │ │M0/M1 │ │                       │
   │  │            │ └──────┘ │                       │
   └─────────────────────────────────────────────────┘
   → 允许在指针上完成 GC 状态标记, 无需访问对象头

2. 读屏障 (Load Barrier)
   → 访问对象时检查指针颜色, 必要时修正(remap)

3. 并发重定位 (Concurrent Relocation)
   → 对象移动几乎完全并发执行

4. 多重映射 (Multi-Mapping)
   → 同一物理内存映射到多个虚拟地址

ZGC 停顿时间: < 1ms (不随堆大小增长)
  -XX:+UseZGC
  -XX:ZCollectionInterval=N (主动触发间隔)
```

### 6.2 happens-before 规则

```
┌────────────────────────────────────────────────────────┐
│           Happens-Before 八大规则                       │
├────────────────────────────────────────────────────────┤
│                                                        │
│  1. 程序次序规则: 同一线程内, 前面的操作 HB 后面的操作   │
│  2. 监视器锁规则: unlock 操作 HB 后续的 lock 操作       │
│  3. volatile 变量规则: 写操作 HB 后续的读操作            │
│  4. 线程启动规则: start() HB 线程中的每个操作           │
│  5. 线程终止规则: 线程中所有操作 HB 其他线程检测到终止   │
│  6. 线程中断规则: interrupt() HB 被中断线程检测到中断    │
│  7. 对象终结规则: 构造函数 HB finalize()                │
│  8. 传递性: A HB B, B HB C → A HB C                   │
│                                                        │
└────────────────────────────────────────────────────────┘
```

### 6.3 volatile 底层实现

```
volatile 变量的读写:

写操作:
  lock addl $0, 0(%%rsp)   // 写入后插入 StoreLoad 屏障
                            // (x86 架构的实现方式)

汇编层面的内存屏障:
  ┌──────────────────────────────────────────┐
  │ StoreStore 屏障  → 写操作前               │
  │   禁止上面的写和下面的写重排序              │
  ├──────────────────────────────────────────┤
  │ StoreLoad 屏障   → 写操作后               │
  │   禁止上面的写和下面的读重排序              │
  │   (开销最大, x86 用 lock 前缀指令实现)     │
  ├──────────────────────────────────────────┤
  │ LoadLoad 屏障    → 读操作前               │
  │   禁止上面的读和下面的读重排序              │
  ├──────────────────────────────────────────┤
  │ LoadStore 屏障   → 读操作后               │
  │   禁止上面的读和下面的写重排序              │
  └──────────────────────────────────────────┘
```

### 6.4 synchronized 底层实现

```
synchronized(Object) {

}
// 编译后生成 monitorenter / monitorexit 指令

锁升级过程 (JDK 6+, 不可逆):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

无锁 → 偏向锁 → 轻量级锁 → 重量级锁

┌───────────────────────────────────────────┐
│ 1. 偏向锁 (Biased Locking)                │
│   • 只有一个线程进入同步块                  │
│   • Mark Word 记录线程 ID                  │
│   • 后续该线程进入时无需 CAS                │
│   • 开销: 几乎为零                         │
│   • JDK 15 已默认禁用 (-XX:+UseBiasedLocking)│
├───────────────────────────────────────────┤
│ 2. 轻量级锁 (Lightweight Locking)          │
│   • 多个线程交替进入 (无竞争)               │
│   • 在线程栈帧中创建 Lock Record           │
│   • CAS 将 Mark Word 指向 Lock Record     │
│   • 自旋等待 (Adaptive Spinning)           │
├───────────────────────────────────────────┤
│ 3. 重量级锁 (Heavyweight Locking)          │
│   • 竞争激烈时膨胀为 Monitor 对象           │
│   • 涉及 OS 的 mutex lock                  │
│   • 线程阻塞 → 上下文切换                   │
│   • 开销: 很大                             │
└───────────────────────────────────────────┘

Monitor 结构 (ObjectMonitor):
┌─────────────────────────┐
│ _header       (Mark Word)│
│ _count                   │
│ _waiters                 │
│ _recursions              │
│ _owner        → 持有锁的线程│
│ _EntryList    → 阻塞等待队列│
│ _WaitSet      → wait()集合 │
└─────────────────────────┘
```
