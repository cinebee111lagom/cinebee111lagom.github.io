LLM 容量核心是 **显存 = 权重 + KV Cache + Radix 缓存结构 + 余量**，不是只看参数量。

## 容量模型

```
权重显存 ≈ 参数量 × 字节/参数（FP16≈2，INT4≈0.5）
KV 显存 ≈ 并发 × 序列长 × 模型相关常数
可用缓存 ≈ 总显存 × util - 权重 - 安全余量
```

| 手段 | 效果 |
|------|------|
| 降最大上下文 | 显著降 KV |
| 降最大并发 | 降占坑 |
| 量化 | 降权重 |
| TP | 权重分摊 |
| 提高前缀命中 | 等效提升可用吞吐 |

## 规划流程

1. 压测单实例可持续 QPS / token/s（分场景）  
2. 峰值业务量 × 安全系数 1.3~1.5  
3. 得出副本或卡数  
4. 预留热备或快速扩容额度  

## 治理动作

| 信号 | 动作 |
|------|------|
| 长期排队 | 扩副本或升规格 |
| 偶发 OOM | 降 util/seqs/len |
| GPU util 长期 <20% | 缩容或合并池（谨慎） |
| 命中率高但仍排队 | 算力不够，不是缓存问题 |

## 周报

- 每模型：QPS、TTFT、排队、命中率、GPU 利用率  
- 预测：按下季度增长估卡数  

## 反模式

- 只按「多少亿参数」买卡  
- 把 Radix 命中红利算进最坏容量（容量应按冷缓存估）  
- 长上下文与短 Chat 混池互相拖死  

**显存余量建议保留 ≥8~10% 防碎片与尖峰。**
